# GLM-5.2 量化版 / 昇腾 910C：MoE 推理负载均衡实验方案

- 日期：2026-11-02；第二版，已按 `845de4c` 结果复核及“当前只有一卡资源”修订。
- 状态：已有单机 EP16 探索结果；本次新增的是验证设计，没有运行本版补测，没有确认新增性能收益。
- 研究依据：用户提供的《EPLB问题.pdf》（7 页，末页为学长建议）；历史快照 `1a4fddfb9b53ae464ad04b2c38a856a2c050ce8d`；结果快照 `845de4c172e30ece633ddb36efdb604c49731888`；文末一手论文和实现。PDF 未随方案上传。
- 目标：在保持原始逻辑专家选择和可接受数值误差的前提下，用有限额外显存改善真实服务时延或吞吐，并说明收益来自计算、通信还是等待减少。
- 当前执行入口：先读第 0 节逻辑修正，再按第 13–14 节做 CPU 离线核对及单 NPU 验证；第 15 节按证据选择新解法。第 5–10 节保留为恢复多卡资源后的目标蓝图，不能当作现在可直接运行的任务单。
- 当前资源：按一张昇腾卡且仅一个可用 NPU 设备保守规划。现场记录实际可见设备／die，不把多个进程当作多台设备，不要求加载整个 GLM-5.2 服务。B300 不默认可用。
- 执行范围：这是一份供执行者逐阶段验证的方案，不代表已具备所需适配实现，也不代表可以连续启动所有阶段。进入下一阶段要先记录上一阶段的结果和通过理由。

## 0. 先修正推理，再设计下一次实验

**本版要保证的是结论与证据匹配，不保证一定测出正收益。** 当前可以完成“布局是否按设计、任务是否相同、量化路径是否正确、本地计算是否值得拆分”；跨 rank 通信、真实等待和完整服务收益必须留到多卡恢复后确认。

| 已发现的逻辑问题 | 修正后的判断 | 下一条可证伪证据 |
|---|---|---|
| E1 报告说副本位于 rank0/1，映射却在槽256/257 | 按对应版本连续槽规则，272/16=17，两个槽均属rank15；仍需核验实际镜像是否改过规则 | 导出加载后的 slot→rank→logical 表及实际接收计数；映射修正不预示收益必然出现 |
| 把 EP64“无副本已接近下界”沿用到 EP16 | 每rank4专家变为16；单专家工作量下界的上限从8变为2，不能沿用旧结论 | EP16 layer49固定交换 e43↔e0、e40↔e240：两份汇总计数已有 R≤2.3223/2.2861 的可行上界；它不是延迟预测 |
| 把预装副本组称作所有在线方法的 oracle | 只代表指定槽预算、候选副本、计划、格式与执行路径的可实现参考 | 对照计划必须满足真实约束；在线组用相同计划，才能拆规划／搬运成本 |
| R降低等于变快，或TTFT不变等于目标层没收益 | R是任务代理；局部效率、通信及目标层占比都会改变时间效果 | 同时测完整局部执行段、多卡完整层、服务指标，三层结论分别命名 |
| “B没有稳定优于A”就宣布没有空间 | 未证明收益与已证明达不到目标是两种结果 | 采用第13节的三态区间判定，不以一次不显著结果否定路线 |
| A_adapter配置了槽位就是空操作 | 原adapter实际允许副本接任务 | 保留同一已加载副本／workspace，只在派发选址时禁止额外槽；这是待适配控制，不能只改JSON冒充完成 |
| 固定scale回放通过即可说明量化安全 | 固定scale会绕过重分组改变激活量化边界的问题 | 固定量化输入与生产重量化路径分两阶段验收 |
| 算子累计时间就是关键路径 | SFA的1.594s是156次累计；全rank总时长相近也能来自等待 | 短全rank依赖时间线；单卡只能解释本地算子链 |
| 换alltoall验证了去重，E1负结果关闭E4 | 后端切换不是去重开关；无副本也可以研究通信计算流水 | E3/E4按自身字节／重叠证据独立决定 |

保留旧负结果为“该实际配置未显示明显TTFT改善”，不删除或伪装修正前的记录。其表格数字可以复算，设计解释则需收窄。旧结果依据见 [845de4c 汇总](https://github.com/InternetMan-Wuju/Sync-Share/blob/845de4c172e30ece633ddb36efdb604c49731888/shared/current_exp/20261102_load_balance_e0/RESULTS_OVERALL.md)、[映射](https://github.com/InternetMan-Wuju/Sync-Share/blob/845de4c172e30ece633ddb36efdb604c49731888/shared/current_exp/20261102_load_balance_e0/mappings/e1_layer49_top2.json)、[官方槽位规则](https://github.com/sgl-project/sglang/blob/v0.5.18/python/sglang/srt/eplb/expert_location.py#L642)。

本轮按以下优先级分配资源：CPU核对完整计数与映射 → 单卡量化正确性 → 单卡真实内核成本曲线 → 仅选择有空间的两个候选做局部比较。没有真实hidden就先用明确标记的人工输入；没有完整路由就只做摘要能支持的分析，不为补齐表格编造数据。第14节给出缺数据时的分支。

### 1.1 已有结果能说明什么

agentX 历史结果：

| 指标 | A0：原始布局，无 recorder | C：EPLB、每层增加 64 个副本槽 |
|---|---:|---:|
| 全程输出吞吐 | 90.9 tok/s | 88.1 tok/s |
| TTFT p50 | 20.32 s | 17.00 s |
| TPOT p50 | 50.3 ms | 51.4 ms |
| TPOT p95 | 63.3 ms | 74.2 ms |
| E2E p95 | 46.22 s | 52.59 s |

TTFT 中位数改善约 16.3%，全程输出吞吐下降约 3.1%。这些是历史观察，不能单独归因于专家计算或通信。输出吞吐的分母包含 prefill、调度、重排等全程成本。

同一历史计数口径下，无副本最热专家下界约 6.359846、stock 可行布局代理约 6.365543，间隙约 0.0896%。这是完整专家不可分、同类设备、token 线性成本模型中的工作量代理，既不是实测延迟下界，也不是已证明的严格最优。原始窗口 .pt 未包含在镜像中，本轮没有独立复算全部样本。

### 1.2 需要修正或重新验证的解释

1. **累计均衡不等于逐层变快。** 整层 rank 置换保持每层的 rank 负载集合和最大值不变。两层 `[100,10]、[100,10]` 改成 `[100,10]、[10,100]`，累计更均匀，逐层热点工作量仍为 100+100。若测层间偏移，只把它当拓扑/争用对照，不先声称其能消除层内热点。
2. **重排管理开销是混杂因素。** B_agentX 重排计时合计约 50.39 s，占实验墙钟约 5.32%，与吞吐下降约 4.85% 同量级；其中含采集落盘、求解、权重更新与同步，不等于精确全服务停顿。
3. **采集行不保证对齐。** phase-window 补丁按各 rank 的阶段独立追加、跳过 idle，再按行 all_reduce；不同 rank 的记录次数不同时，同一行未必是同一次 EP forward。需要重新采集，不能把旧行号直接当同步 step。
4. **逻辑计数不能恢复真实副本流量。** 旧图中的副本物理热度有等分重建假设。下一轮必须采集接收端实际 slot 计数。
5. **历史权重健康状态需核实。** Q4 默认模型路径在其他归档中有损坏记录；10 月 12 日的恢复通过私有加载外挂完成，公共文件未改。Q4 脚本未显示该外挂。不能断言损坏造成了热点，也不能默认旧热点代表健康 checkpoint。
6. **量化和统计口径不能混用。** 历史 decode 的除以 8 修正不能无条件沿用；接收 API 中名为 use_fp8 的兼容参数也不证明 A3 实际发送 FP8。
7. **选副本必须按 (layer_id, expert_id)。** 不同层同号专家是不同权重，不能用跨层合计的 expert ID 选复制对象。旧报告 top8 随机重合比例基准应为 8/256=3.125%，不是 25%；0.25 是交集专家数的期望。

## 2. 研究路线及适用条件

| 路线 | 解决的问题与机制 | 不采用时的限制 | 本方案取舍 |
|---|---|---|---|
| UltraEP | 根据当前 router 后的实际负载，联合规划副本及任务配额；跨层复用副本缓冲 | 历史布局无法直接响应当前突发热点；单热专家仍集中到一处 | prefill 主路线，先做有预算的节点内临时复制。官方 GPU 实现及实验性 SGLang 集成不是现成的 910C 量化支持 |
| MoonEP | 在线按 home group 分配任务，再分解到专家；集成直接写入专家分组位置的 dispatch/combine | 分流、分组排列与复制若割裂实现，会增加拷贝和同步 | 借鉴 planner 与通信组织；原版均衡承诺依赖输入与有效路由契约，不能直接套到不等长 DP 输入 |
| EPIC：Balancing and Beyond | 综合设备与网络负载，研究传输去重、拓扑路径和按专家组重叠 | 即使 token 均衡，重复传输与等待仍存在 | decode 主要参考；论文评测为 H20/H800、FP8、稳态 decode，不能迁移其收益数字 |
| ReLibra | RL rollout 已知后续训练路由，跨 batch 重排、节点内逐 microbatch 复制、跨层缓冲复用 | 缺少提前路由信息时，规划与复制不能自然隐藏 | 借鉴缓冲与拓扑约束；普通在线推理不具备完整未来路由先验 |

当前路由可精确决策，不等于免费决策：全局计数交换、规划、权重准备和依赖等待均要计入。UltraEP 在获得路由信息后确定性地产生计划，并不意味着完全没有跨 rank 通信。不能把本层 router 完成后才决定的复制，算成已与本层之前结束的 attention 重叠。

截至 2026-11-02，MoonEP PR #40 为 Open，Ascend 分支包含 Ascend910_93/A3 的 MTE 路径；A5 的 URMA/UDMA 路径不适用于 A3。已检查的 NPU 权重预取接口要求 contiguous BF16，不能直接接入 modelslim/NZ 打包权重；通信激活格式也需单独核对。现有 NPU planner 要求 E%P=0、临时槽位 B=E/P，不能不改实现就扫 B=1/2。以上是代码检查结论，不代表本机编译或端到端正确性已通过。

## 4. 通用测量与正确性约定

### 4.1 计数和延迟

- 路由记录至少包含公共 EP invocation ID、source rank、layer、forward mode、有效 token ID/掩码、逻辑专家、物理 slot、布局/副本版本。各 rank 可以有不同本地阶段或 idle 状态，不能各自跳过后再按行号拼接。
- 以原始有效 token–expert 任务为单位核对守恒：单个 MoE 层通常为 8N；完整 forward 为 Σ_l 8N_l，75层有效行数相同时为75×8N；裁剪子图按实际保留任务数计算。N_l取实际router有效输入，不能直接用请求输出目标数替代。排除 padding、-1、attention TP 的重复表示，并确认 top8 ID 不重复。专家TP分片另记执行任务，不能强行当成逻辑任务重复并除掉。
- 每条有效任务恰好执行一次，输出使用其原 router 权重；每个逻辑专家各副本接收量之和等于其原始负载。不能靠填入重复或随机专家凑满 top8。
- 使用设备事件或 msprof 关联关键路径。先确认跨 rank 时间对齐能力；同时报告各 rank 局部区间和最晚完成者。不要为了计时在正式路径添加改变行为的全局 barrier。
- 通信 kernel 区间可能包含等待；有重叠的 kernel 时长不能直接相加。主指标是固定依赖边界之间完整层/step 的完成时间。
- 单层基准区分一次性初始化、warmup/图编译和稳态。正式计时关闭高开销 profiler/落盘；用少量独立 profile 解释原因，并记录 profiler 的影响。
- 请求级 decode 时间应先逐请求相减再聚合；不能用 p50(E2E)-p50(TTFT) 计算 p50(decode)。

### 4.2 量化与结果

- 区分专家权重量化、激活计算量化、通信量化。基线 INT8 通信、候选 BF16 通信的差异必须单独报告，不能全部归因于负载均衡。
- 导出实际运行层的完整专家张量清单：packed weight、scale、可选 zero-point、bias/修正项、排列及内部格式。先校验搬运字节和布局，再测输出。
- 以相同量化计算路径的原始单层输出为直接参考，记录最大/分位绝对误差、相对误差及非有限值；误差容差在看优化结果前确定，并结合基线重复运行的误差与质量要求。
- 若激活量化按组/块计算，重分组会改变 scale 边界，必须专项验证。浮点归约顺序变化不保证逐位相同。
- 完整模型补充固定自然语言样本与任务质量对照。仅“1+1 回答正确”不能替代数值或质量验收。

### 4.3 内存与统计公平性

- 单层因果实验固定输入、有效任务、资源、权重视图和工作空间；必要时给无副本组预留等量未使用槽位，隔离分配/容量差异。预装时间在计时外，但额外内存必须报告。
- 服务验收采用同一总 HBM 预算，报告实际 KV 容量、并发和 batch 分布；无副本部署基线可以利用节约的内存。不能将“故意空置内存”的控制组当成最终部署基线。
- 布局/阈值选择使用独立校准 trace，验证使用后续或留出 trace。预知全部路由的 oracle 只给收益空间，不作为可部署成绩。
- 先做 pilot 测量波动，再固定输入规模和重复数。恢复多卡后，服务对照从3对独立、交错重启的运行做pilot；3对不是统计充分性保证。单卡局部核验按第13节确定进程／测量块。不能区分波动时报告证据不足，不挑最好一轮。
- 报告各轮数值、配对差异和区间；共享同一 batch 的请求/层不能当作完全独立样本夸大置信度。最低有用收益由 U12 预先填写，不在看到结果后调整。

## 5. E0：可信基线、冻结布局与开销拆解

**问题。** 旧吞吐变化混合了布局、采集、求解、搬运和调度。未拆开时不能决定是否值得开发逐层在线方案。

**前置条件。** U1–U4 完成；确认当前服务可用，形成自然语言校准与留出负载；先小样本验证计数，无需立即全量采集 75 层。

**布局对照。** 原始布局、校准 trace 学到的无副本布局、预置副本布局。先冻结它们，保持 recorder 配置一致，关闭周期重排，分别测 prefill、连续 decode、PD 混合。

**管理开销对照。** 对同一个冻结映射增加“统计/求解但不改变映射”的诊断组；必要时分开落盘，测纯管理成本。真正动态更新放在单独组，它同时改变布局与搬运成本，不能把两组差异全部算成管理开销。冻结布局组也验证实际没有重新计算/搬运。

**记录。** 每层真实接收任务数、GEMM 起止、dispatch/combine 完成、复制与更新区间、设备/链路资源、请求时间线；完整层时间和开销暴露位置。

**判断。** 冷 rank 的 combine 等到热 rank GEMM 结束才完成，优先检查计算拖尾；GEMM 完成接近、跨节点传输仍占据关键路径，优先 E3。冻结布局有收益但动态管理抵消收益，先做低频/收益触发更新，再决定是否做更频繁在线复制。

**退出产物。** 健康基线 manifest、对齐且守恒的短 trace、三种执行阶段的时间构成、候选 2–3 层及选择依据。下界只作为工作量指标重新计算，不把它标成加速倍数。

## 6. E1：一节点、一层的复制收益与成本分离

**假设。** 将某个热专家的一部分任务交给相同权重的副本，减少的关键路径时间能够覆盖当前路由计数、规划、量化权重搬运及额外通信。

### 6.1 固定输入与单节点边界

保存一个健康 forward 的输入 hidden、top-k IDs、router weights、量化参数/scale、有效任务掩码和布局。选择 E0 中有代表性的热点层，并保留至少一层不明显失衡的负对照；输入规模取现场实际 prefill 分布的小、中、大档，不将客户端输入长度等同于每 rank 实际 chunk token 数。

完整 EP64 每 rank 4 个主专家；一个 16-rank 节点原有 64 个逻辑专家。节点内子图可以保留这些专家，并重放来自全部 64 source rank、原本发往它们的任务，由本地重放器注入。必须明确这保留了哪部分负载、改变了哪些源端与跨节点网络路径。若仅保留本节点 source，则负载分布也改变，另标为局部案例。

裁剪后的每个 token 有效专家数为 0–8，不能直接当 MoonEP 固定 S×K 输入。可选：支持有效任务掩码的子图重放器；或单独构造 E=64、K=8 的微模型检验 MoonEP 算子，但后者不是原始 GLM 子图。不得用重复/随机专家填满路由。子图只核对保留专家的加权输出贡献；完整输出与网络行为要在 EP64 阶段重新验证。

### 6.2 对照矩阵

| 组别 | 每轮在线规划 | 每轮复制权重 | 目的 |
|---|---:|---:|---|
| A 原始路径 | 否 | 否 | 当前完整层/子图成本 |
| A_adapter 临时槽空操作 | 否 | 否 | 与B加载相同副本及元数据、保留相同工作空间；只在派发选址时强制走原owner槽，识别接入成本 |
| B 预装副本＋预计算计划 | 否 | 否 | 固定输入下重分配的收益空间；副本和计划在计时外准备 |
| C 在线规划＋预装副本 | 是 | 否 | 测量路由统计交换和 planner 成本 |
| D 在线规划＋真实复制 | 是 | 是 | 真实在线净收益，包含权重就绪等待 |

B/C/D 对固定 trace 使用相同规划规则和副本集合；C 的预装副本须覆盖本次计划实际需要的副本。不能在改变路由后继续沿用旧 oracle。复制、就绪等待和必要格式转换都包含在 D 的计时边界内。

EP16增加每rank一槽时，保留原专家归属的canonical位置为 `p(e)=17*(e//16)+e%16`，rank r 的额外槽为 `17r+16`。A_adapter与B使用相同physical→logical表、相同已加载权重；A_adapter禁止任务去额外槽，B只开放计划需要的副本。不要修改weight loader的全局候选来假装禁用分流，否则连权重加载和内存控制都改变了。原生dynamic另设B_dynamic组。单卡先验证这套索引和本地派发／合并，真正多rank对照待资源恢复。

自定义有预算方案扫每 rank 共享槽 q=1、2、4，主专家原位置保持不变。未修改的 Ascend MoonEP 按其 E/P 契约使用槽位数；不能只改参数变成 q=1/2。q 是每个接收 rank 的容量，不代表一个热点专家只能有 q 个全局副本。

### 6.3 指标与停止条件

记录完整层/子图时间、最晚完成 rank、计数交换、规划、复制字节与暴露等待、格式转换、dispatch/GEMM/combine、实际 slot 接收量、峰值物理 HBM。R 改善是解释指标，不能代替时间收益。

- 正确性门失败：任务遗漏/重复、scale 对错、格式不兼容、输出误差超标，立即停止性能结论。
- A_adapter 显著慢于 A：先定位接入成本，避免把它误判为复制算法成本。
- B 的收益区间上界仍低于预设最低有用收益：停止该层/shape/预算/计划/实现的在线投入。区间跨门槛则证据不足，可以按资源预算暂缓，不能写为无收益空间。收益区间下界超过门槛且正确性通过，才进入C/D。
- B 快、C 不快：先缩减规划/元数据开销或提高输入规模触发门槛。
- C 快、D 不快：先处理复制/格式转换、少复制、选择性常驻；不要直接扩大副本数。
- D 稳定快且正确性通过：进入 E2 的动态共享缓冲路线，并在完整 EP64 复验。若仅 B 正确且稳定快、D 不回本，可进入 E2 的选择性常驻路线；无需等待在线复制获益。节点内成立不证明跨节点成立。

现有 expert_location_updater 包含 NZ→ND、临时 buffer、分批通信等待和回写，适合参考参数清单，不应直接视作每层低开销复制实现。实现接入还需要同步协调 logical→physical 映射、dispatch 计数、GEMM 槽位和 combine 逆映射，不能只替换 top-k ID。

## 7. E2：跨层共享缓冲、选择性常驻与混合策略

**问题。** 每层永久添加副本使空间随层数累积；共享槽减少常驻空间，但每层准备权重的时间仍存在。

若 75 个 MoE 层专家大小一致，完整专家含 scale 等实际占 W 字节，每 rank 基础 routed expert 权重为 75×4W=300W：

| 方案 | 每 rank 额外副本权重 | 相对基础 routed expert 权重 |
|---|---:|---:|
| 每层各一个常驻槽 | 75W | 25% |
| 跨层共享 q=1 | W | 0.33% |
| 跨层共享 q=2 | 2W | 0.67% |
| 跨层共享 q=4 | 4W | 1.33% |

这些不是总 HBM 比例。实际各层大小不同则槽位按最大物理存储需求分配；并发占用 c 套槽位时，额外副本空间按 c×q×max(W_l) 计，另外加元数据、通信缓冲和工作区。不能只用逻辑 numel×dtype 忽略内部布局。跨层复用减少空间累积，不减少必需的逐层传输。

**入口与对照。** 动态共享缓冲及混合策略中的动态部分，要求 E1 的 D 正确且稳定获益；选择性常驻只要求 B 已证明有收益空间，允许在 D 搬运不回本时进入。前者从少量层验证临时副本，后者验证少数层常驻副本，再决定是否组合。常驻布局固定后仍要计入真实分流成本，不能沿用预知留出路由的 oracle 计划。按实测节省时间/新增字节选层，独立 trace 验证，并在完整 EP64、同总 HBM 预算下报告 KV 容量变化；每层不同副本数若不受当前框架支持，明确标为适配工作，不能当作现成参数。

**生命周期。** 每个槽记录 layer、batch/微批、expert、版本与最后消费事件；任何上一使用者仍在读取时不得覆盖。先关闭跨批重叠验证，再打开实际所需重叠。发现冲突则停止，增加独立槽位或串行依赖后重新计时和计内存。

**触发规则。** 根据 E1 建立粗粒度实测成本表，仅当预测节省的完整关键路径时间超过规划、复制和新增通信暴露成本时启用。当前层真实路由可用于确认需求；提前预取只能使用当时可得信息，未来 trace 预知方案只作 oracle。所有参与 collective 的 rank 必须一致选择本次执行路径，不能各自决定跳过。

**拓扑扩展。** 先测节点内复制，再完整 EP64。若仅允许专家在归属节点内复制，设该节点固定承担工作量 S_j、可服务 rank 数 p_j，则 max_j(S_j/p_j) 是简化工作量下界；节点总量差异过大时，节点内均衡无法获得全局均衡。此式不包含实际非线性 GEMM、链路和 attention 成本，不是时间下界。

**通过标准。** 所选层和留出输入上有稳定净收益，实际额外 HBM 在 U12 预算内，完整 EP64 正确性与图/shape 行为通过；否则保持已验证的小范围策略或停止扩展。

## 8. E3：decode 通信去重与拓扑路径

**问题。** 同一个 token 的多个目标专家位于同一远端节点时，逐专家发送会重复占用跨节点链路；计算均衡本身不消除这种成本。

冻结逻辑 top-k、router weights、物理布局和量化格式。先确认当前后端是否已按目的 rank/节点去重，再用有效路由统计：m_t 为 token t 的远端专家目标数，d_t 为对应不同远端节点数。只有当前逐专家发送且 dtype 一致时，主体 payload 的理论减少比例才是 1−Σd_t/Σm_t；若分母为零，则没有跨节点去重空间。metadata、scale、padding、节点内转发及既有去重另算。

例如 6 个远端专家在 3 个节点，主体输入 payload 可从 6 份变成 3 份；这不代表通信时间或端到端时延减半。返程还需验证局部加权聚合和数值误差。

**对照。** 确认实际安装包后，回放相同路由，比较当前 LL 与已支持的分层路径。仓库候选 `ops/hierarchy` 可作为入口，但名字不证明具有 EPIC 去重语义，空 recv hook 也不能证明支持细粒度重叠。先验证能力和正确性，再做性能比较。

**指标。** 有效发送/接收字节、链路负载、通信等待、额外设备资源占用、完整 decode step、TPOT/ITL 尾延迟。冻结布局的节点内/跨节点置换可作为拓扑控制实验，不能称为消除单热专家下界。

**停止条件。** 已有去重、重复字节比例低，或减少的远端传输被节点内转发/同步/资源争用抵消时，不继续开发同类内核。微基准快但完整 step 慢时不进入 E5 候选。

## 9. E4：decode 按专家组流水

**问题。** dispatch→GEMM→combine 串行产生暴露等待；直接把小 token batch 再切小会降低算子效率并重复读权重。按专家维度分组可以保留每个专家的全部 token。

原EP64每rank4专家，先比较一组4个与两组各2个；EP16每rank16专家时则从一组16与两组8开始，并按实际活跃专家调整。单卡只测分组带来的局部计算／launch成本，不声称测到跨rank通信隐藏。多卡恢复后才观察能隐藏多少通信。该差值仅是一个成本项，完整结果仍由时间线决定。

需要按组到达/完成通知、分组 GEMM、按组 combine、正确缓冲生命周期与图捕获支持。只开 multi-stream 或顺序调用两次 dispatcher 不构成已实现流水。当前候选 ops 的空 recv hook 不能充当现成能力。

**停止条件。** 新增小 GEMM、launch、同步与资源争用超过隐藏通信的收益，或缺少正确的完成通知时，停止扩组。只有完整 step 和尾延迟稳定改善才进入 E5。

## 10. E5：完整服务验收

1. 固定健康模型、逻辑请求与输出控制参数；记录实际输出 token 数。纯机制回放可固定输出任务量，真实服务质量测试允许正常输出，但必须报告长度变化，不能隐藏 EOS 差异。
2. 分开固定输入微基准、prefill、连续 decode 和 PD 混合；固定/记录 KV 长度、缓存初态、chunk、图捕获及 batch 分布。
3. 复现 agentX 并发 8 的历史形态；再按实际服务目标测适当并发或固定到达轨迹。闭环并发测试中快组会接收更多后续请求，策略效果须结合固定 trace 和独立留出验证解释。
4. 在同一总 HBM 预算下比较，报告 KV 容量与可支持并发，不能只比较专家权重空间。
5. 报告 TTFT p50/p95、逐 token 延迟 ITL p95、请求平均 TPOT 的分位数（明确两者不同）、E2E、输出 tok/s、失败率、满足 SLO 的请求率/吞吐、峰值 HBM。
6. 各轮对照交错运行，保留逐轮数据和差异区间。按第13节区分收益成立、达不到预定最低收益、证据不足；后者不写成无效。局部改善但违反U12的尾延迟/质量/内存约束，不认定成功。

全程不承诺论文中的收益比例；只有本机相同条件的对照支持现场结论。

## 13. 新增采集规范：先建立可复查的证据链

### 13.1 当前单卡可以证明到哪里

| 证据类别 | 当前可做 | 允许的结论 | 不允许的结论 |
|---|---|---|---|
| CPU离线 | 检查映射、完整路由计数、配额和布局约束 | 某合法布局的任务分布、计数上界、离线计划可行 | 实际通信量或多卡加速 |
| 单NPU实际测量 | 抽取专家的量化正确性、GMM链、局部分组与重排成本 | 指定内核／输入／权重工作集状态下的局部时间和内存 | 完整GLM质量、EP16/64完整层时延、真实HCCL等待 |
| 单卡校准的模型估计 | 用各rank工作量预测本地计算时间及可能可用的通信预算 | 带假设、误差和缺失项的候选排序 | 多卡oracle或部署成绩 |
| 多卡恢复后 | 实际physical接收、通信、全rank时间线、完整服务 | 限定拓扑／负载／预算的净收益 | 未测试拓扑、量化或负载的收益 |

即便一张物理卡暴露两个设备，也先完成单设备基线；双设备互联测试需独立标注，不能外推跨节点。不要在同一NPU启动16个“rank”伪造EP16性能。

### 13.2 两套任务账和最小字段

**语义任务账**回答“模型真正需要算什么”；**执行成本账**回答“设备实际处理了多少，包括padding”。前者排除填充和重复表示，后者保留真正消耗时间的填充。只删掉padding会把语义算对，却无法解释耗时。

| 文件／粒度 | 必需字段 | 验证用途 |
|---|---|---|
| `manifest.json`／一次运行 | run_id、计划版本与源码/so哈希、实际内核名、设备型号与可见设备数、驱动/CANN/torch_npu、专家张量来源/恢复manifest、量化布局、种子、输入hash、配置hash、计时边界 | 别人可以确认运行的到底是哪种实现；版本号相同不保证补丁相同 |
| `expert_state.json`／目标专家 | layer/expert、全部权重与scale/offset/bias/修正项、shape/dtype/stride/内部格式、存储字节、共享元数据所属者、分片归属、存储独立性 | 排除漏scale、权重别名和错误量化布局 |
| `tasks`／短正确性样本 | token身份/绝对位置、top-k位置、logical expert、router weight、physical slot、slot所属rank、valid标志、映射版本 | 精确查漏、重复、错位、错误加权；单卡虚拟rank必须标为离线标签 |
| `counts`／调用×层×rank/slot | 原有效行数、有效任务、各专家/slot任务、padding行、容量桶、drop/overflow | 同时核对有效任务守恒和实际成本；原始计数先保留，不先除以EP/TP |
| `timings.csv`／测量块 | session/pair/block、配置、shape、专家行数向量、活跃专家数、计时对象、设备时间、host时间、预热状态、采集模式、错误码、峰值allocated/reserved | 按正确重复单位比较性能；分清GMM与完整局部链 |
| `numerics.json`／输入×组 | 基线A/A误差、非有限值、最大绝对误差、NRMSE、有效非近零位置的相对误差分位数、量化scale差异、首个不一致阶段 | 定位是加载、分组量化、GMM还是合并出错 |
| `index.json`／证据清单 | 每个原始文件的hash/大小/保存位置、复算入口、缺失项及原因 | 原始trace保留到结论复核完成；只上传小表，权重和hidden不进Git |

单层完整专家执行且top8不同的条件下，`Σ_e c_e=8N_valid`，同一专家的所有副本有效任务之和等于其逻辑任务数。若做专家TP分片，增加“同一逻辑任务对应哪些分片”的单独契约，不用8N检查所有分片执行次数之和。

NRMSE在这里定义为 `||Y_candidate-Y_reference||₂ / max(||Y_reference||₂, ε)`，ε及近零位置规则在比较前固定。它便于比较输出尺度不同的样本；同时保留最大绝对误差，避免归一化掩盖异常位置。置信区间用于表达独立重复的不确定范围，不能靠增加同一次运行内的相关token数把区间虚假缩窄。

多卡恢复后再加公共EP调用ID、本地序号、source组、local phase/idle、实际graph桶。公共ID必须从现有调度/通信上下文验证，不能假设API存在，也不能靠新增全局barrier来创造它。无法建立唯一对应时，只报告窗口汇总，不把各rank本地行号强行拼成逐步数据。

### 13.3 统计与退出规则：预先决定，不能看结果再挑

当前资源边界由本方案给出默认值，避免为未定参数阻塞小实验：

- **目标：**优先筛选prefill局部计算优化；decode用小M作为反例，不作整服务收益承诺。
- **内存：**设备初始化后记录基线与实际可用HBM；新增目标权重、独立副本、workspace及激活峰值先限制在此时可用HBM的70%内。这是试验预留策略，不是硬件安全保证。除allocated/reserved外同步记录设备级可用HBM变化，覆盖CANN／内核私有分配；有其他进程变化时不能把全部差值归于本实验。超过预算即缩小驻留专家集合，不挤占其他进程。
- **主指标：**固定输入下完整本地专家链，含量化、GMM1、激活/重量化、GMM2、必要本地排列恢复；GMM单项只用于解释。
- **筛选门槛：**本轮默认最低有用局部收益 `δ_local=5%`。这是筛选研发投入的建议门槛，不是已有收益预测，也不是将来服务SLO。小于5%的真实改善可以记录，但不优先投入定制内核。
- **采集影响：**先做采集关闭／轻量计数开启的A/A，以及一次单独重profile。若计时影响超过1%或区间无法排除1%，正式成绩全部用采集关闭结果；1%取5%目标的五分之一作为诊断标准，不把它当统计定理。
- **重复：**3对独立进程初始化先做pilot，AB/BA交错；随后冻结候选、输入、预热规则和样本数。本轮每个入选候选先预算10对独立确认运行，pilot若表明精度不足，可在确认前提高到最多20对。到上限仍不清楚则保留未决，不无限追加到“显著”为止。

同一session里设置多个测量块估计稳态波动，每块执行足够重复，使批量计时区间至少100ms；实际调用较长时按完整调用计。先把编译／首次分配与稳态分开，pilot确定覆盖每个shape的预热量，确认阶段不能按结果临时改。只有测量边界使用已确认可用的同步／事件；不逐算子同步改变流水。设备事件与host围住的局部链各报告，不混为一个时间。

确认前锁定一个主case：优先用校准集中选定的layer49真实逐调用shape／专家向量；没有逐调用数据时用M=1024的单专家人工输入，只得机制结论，不能把四请求汇总的4062行当一次真实调用。每块时间除以完整调用次数，T_i取该运行全部有效稳态块的等权算术平均；错误块保留并使该case失败，不能静默剔除。其他shape分别报告，不在看结果后混合加权成一个总分。

`G_i=1-T_candidate,i/T_reference,i` 是第i对独立运行的收益，主统计量为所有配对G_i的算术平均。报告全部配对值及按独立运行配对bootstrap得到的95%区间，事前固定重采样种子和次数；块内调用不能伪装成几千个独立样本。10/20对都是预算，不保证区间足够窄。选择很多策略后，只让入选的最多两条在未参与选择的输入上做确认；不能在同一数据上反复挑赢家。某组策略要求多专家case而当前仅能做单专家时，保留原先冻结的多专家case待测，不用不适用的默认case替代验收。

| 结果 | 判断 |
|---|---|
| 任务丢失/重复、错误专家、非法存储、非有限值或正确性失败 | 停止性能结论，先修复 |
| 收益区间下界 > δ_local | 支持该局部链达到本轮筛选门槛；不等于多卡收益 |
| 收益区间上界 < δ_local | 支持该受限方案达不到5%目标；不等于收益严格为零 |
| 区间跨门槛 | 证据不足；按预算结束，不能宣布有效或无效 |
| 只有估计的多rank最大时间改善 | 记为“待多卡验证候选”，不能应用上述规则冒充硬件收益 |

数值方面先做至少20次同输入A/A观察：结构、完整权重字节及任务对应要求严格一致；对路径本应位一致的阶段要求位一致。若原实现存在非确定性，先冻结误差比较规则，再比较候选与A/A分布；超出原波动必须定位，不因“生成答案看起来正常”放行。落在A/A波动内仅允许继续局部性能筛选，不能替代GLM质量验收。真实服务的质量容差、TTFT/ITL/SLO与同HBM预算要在恢复多卡后的确认实验前冻结。

### 13.4 通信和时间证据的分级

多卡阶段分别记录：①由有效任务、dtype、唯一目的rank/node推导的有效payload；②软件实际张量／内核处理量，包括padding与metadata；③经验证覆盖该路径的链路计数器字节。无法读到第③类就标不可观测，不用理论量冒充真实链路量。

只有与数据/依赖未就绪建立对应的区间才叫等待。Free、Idle、communication总时间或零Transit均不能直接替代等待。跨rank时钟未经校准，不用不同机器的时间戳计算精确关键路径；保留本地区间和因果序列，明确尚不能精确拆分的部分。单卡不采集或虚构跨rank等待。

## 14. 当前可执行的单卡验证清单，以及多卡恢复后的补测

### S0：零NPU成本的映射与完整路由核对

**问题／不用的后果：**布局或计数错了，后续再精确的计时也不能回答原设计。先保留旧配置，再检查修正版，不覆盖原记录。

输入为三份mapping、已有服务保存的实际槽位规则、calibration/holdout原始路由文件及请求hash。若旧运行态槽位表缺失，当前只作配置与代码契约检查，运行态核验留到M0；不为此启动完整模型，也不阻塞独立的S1。原.pt曾记录在执行机 `logs/20261102_081322/eplb_windows/`，约70MB；取回已有文件不需要启动大模型。只有前10热专家摘要时，不补造其余246个计数，也不声称能重建token共选关系。

实验：对旧mapping和按rank交错的mapping输出每槽归属；确认primary位置、合法副本、每rank槽数和参数状态。回放完整计数比较原布局、冻结无副本交换、固定容量LPT、合法副本均分、按rank剩余负载分配。所有布局只用校准集选择；第二份输入若参与了挑选，则降为开发数据，重新保留最终评估输入。

**单卡可以验证的陷阱样本：**把一个任务故意重复／遗漏、把两个物理槽映到错误逻辑专家、构造padding行。这些仅在隔离的离线数据副本中注入，检查验证器能否报出具体任务，不能改变生产权重或用错误样本计性能。

通过标准为精确的任务多重集合相等、布局合法、映射与加载规则一致。汇总计数相同不足以证明token级无遗漏；只有计数文件时结论限定为计数守恒。产物是 `layout_check`、`conservation_check`、完整256专家负载表、每个计划的约束检查和未决项。

### S1：抽取专家，验证完整状态与本地复制

**问题／不用的后果：**完整服务装不下一卡并不妨碍验证一个专家；但绕开恢复层、少带scale或调用另一个内核会制造假结论。

从已有可信恢复加载流程抽取layer49的e43/e40及一个冷专家，首先只驻留一个专家及其独立副本。按实际可用HBM再扩大，不假设同时能放整层256专家。核对第13节完整张量清单、内部格式和所有参数；原checkpoint的损坏记录仍需恢复层覆盖，不能直接读取损坏原块。

确认实际采用当前modelslim的NPU MoE算子链；若只能退化成普通matmul，作为数值参考或独立算子实验，不能写成生产MoE内核性能。记录副本是否独立存储；共享不可变scale可以说明，但“只多一个tensor视图”不能算真正复制实例。

做两阶段正确性：

1. **固定量化输入。** 同一量化激活和scale，一次全交原实例，与按0/100、50/50、90/10比例交原实例和副本的结果比较，恢复原token顺序。包括空分支、1行、非对齐行数。拆分的两支在单NPU顺序执行，不记为跨设备并行加速。
2. **真实量化流程。** 从同一未量化hidden出发再做上述拆分，记录每阶段scale和输出，检验分组变化是否改变量化边界。顺序改变要让token的scale、专家smooth参数和router weight一起正确对应。

若没有旧forward保存的真实hidden，使用固定种子的人工输入，并标 `synthetic_activation=true`。它可验证这些输入下的实现，不代表真实GLM激活分布、质量或性能。待真实hidden可得后必须复验。

再用8个不同逻辑专家构造一个小top-8加权合并检查：副本替代原任务，不能多加一份输出。内存不足时逐专家生成参考贡献，这仅用于正确性。通过后才进入性能测量。不得给这种子集检查取名“完整模型正确性通过”。

### S2：测单卡真实计算成本，检验token数量是否是合适目标

**问题／不用的后果：**固定启动、权重读取和tile填充使时间不一定与token数成正比；盲目均分可能激活更多专家实例，反而更慢。

第一轮固定生产维度、packed格式和dtype；M取 `{0,1,8,16,32,64,128,256,512,1024,2048,4096}` 中内存可容纳者。0只做边界正确性；真实观测最大M更小则止于实际范围。观察到阶梯后，在该边界前后补1行的点，不能先假定昇腾tile就是GPU论文的128。

先测单专家完整局部链，再测同总有效行数、不同活跃专家数／分布：均匀、一个热点、两个热点、热点加多个小组、真实每rank负载。合成分布用于诊断内核，不是改变模型路由的优化成绩。必须记录每组真实专家向量，不能只记总M。

每个点记录量化/布局、GMM1、激活/重量化、GMM2、恢复顺序以及完整链耗时。分段profile在独立短运行采集，正式主成绩不插逐算子同步。若全链已融合且不能分段，保留全链，不强拆出假分项。

测两种缓存情境：反复同权重／shape，以及轮换多个实际专家集合。纯计算对照的轮换集合须预先驻留，分配/repack/H2D单列；明确轮换发生在块内每次调用还是块间，避免100ms块内重复把轮换模式测成单权重热循环。装不下的工作集不假称已测冷权重。报告工作集大小及是否超过设备缓存；没有验证缓存状态时分别称“重复权重”和“轮换权重”，不擅自称冷缓存。人为清cache会引入额外工作，不纳入生产成绩。

输出 `F(expert_token_vector, active_experts, shape, dtype, path)` 的实测表。先用留出组合验证查表/拟合预测，再用于S3；预测误差若与拟议收益同量级，不用模型宣布策略优劣。无需先追求复杂回归，也不能默认各专家独立时间相加等于grouped内核时间。

### S3：在固定副本预算下，比较均分、配额和耗时分配

**问题／不用的后果：**副本存在不代表平均派发最优。一个副本所在rank若还有其他热专家，应少给它任务。另一方面，小任务再拆分会增加活跃实例与小GEMM成本。

先在CPU上、同一合法副本集合内比较：原owner、均分、考虑其他固定负载的token配额、使用S2表的耗时配额。每个计划必须满足每个逻辑任务完整分配、仅使用其合法副本、槽/容量约束；配额落为整数后重新核对，不能拿连续LP结果直接声称实际达成。

小例子只解释机制：两个rank已有任务100和0，另有100个可分流任务。均分后为150和50，全部给第二个则为100和100；这不增加副本。真实目标应同时约束新增目的地与非线性时间，不能把这个线性例子当硬件加速。

在单NPU逐个回放原本各rank的本地专家工作量；只在所需真实专家可正确加载且路径一致时计入。分别保留每个本地时间，不把顺序总和当EP时间。`max_r F_r`仅是“不含通信/同步/争用”的计算模型估计，甚至不是有缓存和融合变化时的严格理论下界。

报告预计计算可省多少、误差范围、额外活跃副本、padding、新增目的rank/node、可能增加的payload。缺token级路由时只能给目的地范围，不能从专家边际计数推导实际去重字节。把预计节省写成“未来全部额外成本可消耗的预算”，不声称已扣除了通信。

**筛选：**模型误差已能吞掉改善、或明显增加活跃权重而无本地收益时不优先移植；有空间才排入多卡确认。单卡无法证明在线统计、全局配额或远程传输能回本。

### S4：局部算子与分片反例，首轮最多选两条

默认先选“热点单独GMM＋其余grouped”和“保持量化边界的token行分组”；只有S2显示明确局部尾部才考虑定制tile调度。对照仍执行同一组合法任务，包含额外launch、排列、激活与中间写回，不能只报快的GMM一项。行分组在同卡顺序运行可测本地拆分开销，不代表其他rank分担后的净收益。

若内存允许、量化状态清楚，再做专家FFN中间通道两分片的正确性反例：先保持原完整通道的量化scale，按两片顺序算并求和；再比较各片独立重量化。前者检验数学拆解，后者暴露scale边界变化。若原scale需要先执行全通道计算才能获得，该对照只能作正确性参考；候选性能必须计入真正获取scale的成本。单卡测各片局部成本，不把两片同时运行的理想时间写成实测。

跨层buffer只做单设备生命周期检查：两个不同层/专家状态交替装入同一槽，检查旧读者完成前不覆盖、版本匹配和输出一致。只测本地copy/repack/事件的成本；若只是指针切换或底层存储共享，要单独命名。同卡复制不能替代远端HCCL搬运或跨rank并发正确性。

### M0–M3：恢复多卡后只补单卡无法回答的问题

| 门 | 最小对照与采集 | 通过后才允许的结论 |
|---|---|---|
| M0 真实调用与计数 | 短prefill；实际有效batch1与较大batch的decode；检查实际graph桶和padding，条件允许再开/关图；保留全rank任务/接收计数 | 热点与真实分流计数可信；请求并发不等于实际batch |
| M1 完整层机制 | A原布局、R无副本冻结布局、A_adapter、B_plan；B有空间再比B_dynamic/耗时配额；固定真实全rank输入、原逻辑top-k与量化路径 | 特定布局/shape下的完整层收益；同时保留本地计算和通信成本 |
| M2 在线成本或独立通信路线 | B/C/D相同副本/计划，计统计、规划、搬运和就绪；E3独立测去重字节，E4独立测分组重叠 | 在线净收益，或通信路线自身收益；不能由其他路线失败替代验收 |
| M3 目标服务 | 回到EP64、真实agentX、相同总HBM，冻结主指标/SLO/预算，固定到达轨迹与独立留出，交错重启 | 原问题在指定服务条件下改善 |

M1先用layer49和一个不明显失衡层，一个实际prefill shape通过后再加小/大shape与decode，不第一轮扫描所有75层。多卡profile短窗口覆盖前一依赖、router、dispatch、GMM、combine和下一消费者；全部参与rank的原始窗口保留到复核完成。正式性能运行关闭重采集。

跨层缓冲复用解决空间随层数累积；在线复制能否回本仍由M2决定。单卡阶段不得将M0–M3标记为PASS，也不把它们设为阻止当前S0–S4推进的前置条件。

## 15. 重新审视解法：哪些值得试，先用什么证据筛掉

保留原第2节UltraEP／MoonEP／EPIC／ReLibra研究路线，新增下面的判别。优先保持逻辑top-k、专家函数及router weights不变；修改router bias、丢任务、降低top-k或换更低精度属于改变模型行为的另一个项目，不能拿其加速证明纯系统均衡成立。

### 15.1 已有副本的负载感知分流：LPLB思路，先做可实现配额

解决“副本按50/50分配，但两个目标rank的其他工作量不同”。没有这层决策，增加副本也会继续拥挤。固定副本后决定每份接多少任务，不搬权重，不改变逻辑专家。单卡S3先验证配额及计算空间；多卡计入真实统计与派发开销。

官方SGLang已有LPLB，但公开实现使用CUDA与Math-DX；PR明确无CUDA等条件下启动失败。**不能在当前910C上直接启`lp`并期待工作。** 同时，公开实现将LP结果转为抽样概率，实际小batch分流并不自动等于整数配额；本方案要另测实际计数。[LPLB实现说明](https://github.com/sgl-project/sglang/pull/24515)、[对应版本选址入口](https://github.com/sgl-project/sglang/blob/v0.5.18/python/sglang/srt/eplb/expert_location_dispatch.py)。

推荐的昇腾实验顺序是离线合法整数计划 → 预装副本回放 → 简单节点内quota分流 → 最后才决定是否移植完整求解器。调度前需要全局计数的策略必须计入该通信；利用历史统计的廉价策略必须测分布漂移。不是把未来路由oracle免费放入生产路径。

### 15.2 按真实时间分流：避免小GEMM和权重激活成本

解决“token均衡、时间仍不均衡”。TEMPO研究指出活跃副本、权重读取和tile填充会使计算成本呈非线性；其结果也说明通信主导时收益会消失。本文只借鉴实测成本驱动的目标，GPU的token阈值／tile大小／收益不能套用910C。[TEMPO v2](https://arxiv.org/html/2608.13057v2)。

现场方案用S2测到的NPU成本表，在相同副本数下比较token目标与时间目标。特别测试“热专家拆两份、冷专家保持集中”，而非所有专家都尽量散开。若S2/S3表明均分制造更多小矩阵或读取更多权重，这条路线比直接增加副本更有判别价值。

预测目标可写为“最晚本地完成时间＋新增通信暴露成本”；当前单卡仅标定前项，后项保留为多卡待测，不把未知通信设为零后宣布赢家。周期重排可采用收益触发与滞回，只有预计后续累计节省超过实际搬运/停顿才更新；未来流量未知时用当时已有信息预测并在留出流量上验证。

### 15.3 热专家内部切分：改变“专家不可拆分”的前提

同一token的专家FFN中间通道可以拆为两部分，普通SwiGLU形式为：

```text
Y = Σ_j [SiLU(X·W_gate,j) ⊙ (X·W_up,j)] · W_down,j
```

按对应中间通道同时切gate/up输出和down输入，每个设备持一部分权重，最后合并部分输出。如果移除原完整实例，总专家权重不必翻倍；保留完整回退实例则必须计额外内存。新增输入复制、输出归约和scale同步不能省略。MoEShard为专家张量切分提供一手参考，但其GPU encoder实验不证明GLM量化推理适用；“只给少数热专家配置更高TP度”在这里是待研究的扩展。[MoEShard](https://arxiv.org/html/2503.08467v1)。

量化是关键障碍：若中间激活按token整行求scale，分片后独立求最大值会改变尺度。保持原尺度需要全通道信息，例如跨分片max归约，或固定输入回放先提供原scale。A3动态量化的行最大值规则见[官方API](https://github.com/Ascend/op-plugin/blob/master/docs/zh/custom_APIs/torch_npu/torch_npu-npu_dynamic_quant.md)，当前SGLang实际激活路径还需与[封装源码](https://github.com/sgl-project/sglang/blob/v0.5.18/python/sglang/srt/hardware_backend/npu/moe/activation.py)及运行镜像核对。

单卡先做S4的两片数值验证和局部成本，不能证实分布式加速。恢复至少两设备后，与“完整专家单设备”和“两个完整副本按token分流”公平比较。若完整链收益区间上界低于门槛，停止该shape的分片适配；下界超过门槛才研究每专家不同TP度；跨门槛则保留未决。当前没有核实可直接启用的910C配置。

### 15.4 NPU内部工作块调度：让一张卡更有效地执行热点

解决同卡多个专家大小悬殊、局部执行单元拖尾的问题；它不让其他rank帮忙，因此不能宣称消除rank间总工作量差异。先测当前GMM是否已经跨专家调度充分，再考虑热点单独处理或跨专家tile任务队列。

SGLang NPU封装使用grouped matmul并传入专家行数，但量化／融合变体不同，实际路径必须记录。[NPU matmul封装](https://github.com/sgl-project/sglang/blob/v0.5.18/python/sglang/srt/hardware_backend/npu/moe/matmul.py)、[Ascend GMM接口](https://github.com/Ascend/op-plugin/blob/master/docs/zh/custom_APIs/torch_npu/torch_npu-npu_grouped_matmul.md)。单卡S2/S4就能判别局部时间；若完整链无改善，不因为GMM某一个kernel变快就写新调度器。

TileLang Ascend有grouped调度构件，但它不是现成ModelSlim替换内核；必须保持原量化归约边界、scale和格式，不能为了切块方便改变每token尺度。[调度构件源码](https://github.com/tile-ai/tilelang/blob/main/tilelang/ascend/language/tile_schedule.py)。这是适合单卡资源继续推进、且不必先解决多卡权重复制的一条路线。

### 15.5 共享专家工作分配：Waterfill，但先查是否有可移动工作

Waterfill改变共享专家工作的执行位置，保持routed top-k不变，目标是把已有的共享工作交给更空闲的rank。它依赖共享专家派发/融合及合法完整权重；把原先分片的共享专家变为完整副本可能增加内存，不能宣称天然零成本。[官方说明](https://www.lmsys.org/blog/2026-06-26-waterfill-lplb)、[Waterfill PR](https://github.com/sgl-project/sglang/pull/19290)。

当前服务探针的`disable_shared_experts_fusion=true`，未验证GLM量化共享路径能直接适配。先导出共享专家是否存在、是否完整驻留/分片、单卡耗时和现有重叠；共享工作若本已被隐藏或移走的工作太少，就不优先移植。单卡只能测这部分成本及合并数值，实际“填谷”仍要多卡。

该办法不能凭空拆掉routed热专家本体，只能减少热点rank上同时承担的其他可移动工作；必须分别报告两者，不能拿shared工作的均衡冒充routed热点消失。

### 15.6 请求、分块、拓扑与实例布局：系统层的补充路线

**请求与分块。** 长prefill占用调度预算会影响decode；chunk大小、准入和长度分组值得独立比较。但如果某专家对几乎所有token都很热，混合更多请求不能消除该专家的总工作量。没有完整模型时只能离线分析到达轨迹及旧路由，不能用单专家测试推断TTFT。网关在多个完整服务实例间按队列/缓存选路，解决的是实例排队，与单实例内部EP热点不同。[SGLang网关说明](https://github.com/sgl-project/sglang/blob/main/sgl-model-gateway/README.md)。

**通信与专家组流水。** E3去重、拓扑感知布局、分组到达即计算、分组combine不依赖一定做复制。单卡可测拆组新增本地成本，不能测HCCL重叠；恢复多卡后才与可隐藏的实际通信比较。没有可用完成通知与图兼容语义时，不能把多stream开关当作已实现流水。

**并行度。** 在固定64个设备下，一个EP64实例与多个EP16/32实例的总模型副本、KV容量和排队不同，必须比较总SLO内吞吐。更小EP降低token失衡并不等于资源效率更高。对应版本的DeepEP/Ascend FuseEP配置规则会将EP与TP关联，不能直接设“TP64/EP32”就宣称得到专家TP2；实际进程组和最终生效参数必须核验。[配置规则](https://github.com/sgl-project/sglang/blob/v0.5.18/python/sglang/srt/arg_groups/overrides.py)。

现有Ascend功能表也不能证明所有GPU优化均可用：检索时two-batch overlap仍标为计划项，single-batch overlap标GPU专用，prefill CP的模型支持有限。因此当前不把这些开关作为GLM-5.2／910C的即用方案。[Ascend功能表](https://github.com/sgl-project/sglang/blob/main/docs/docs/hardware-platforms/ascend-npus/reference/support_features.mdx)。

### 15.7 当前资源下的优先级与最终决策

| 优先级 | 现在做什么 | 为什么先做 | 何时停止／转向 |
|---|---|---|---|
| P0 | S0映射/计数；S1完整量化状态和任务合并 | 先保证任何后续结果对应正确问题 | 结构/数值不通过时不生成收益结论 |
| P1 | S2本地成本曲线；S3合法配额与耗时目标 | 能解释“均衡反而慢”，为副本策略和NPU算子都提供依据 | 模型误差吞掉改善则不排序，补真实组合点 |
| P1 | S4热点GMM组织或token行分组，最多两条确认 | 单卡可直接给出局部净收益，研发成本较低 | 完整局部链达不到门槛则保留负结果，不盯单kernel成绩 |
| P2 | 两片FFN量化验证、共享专家成本、单槽生命周期 | 对无额外常驻副本、有限buffer等路线排除明显障碍 | 需要改变语义或局部额外成本过高则暂缓 |
| 多卡恢复后 | M0–M3；选择性常驻/临时复制、去重和流水 | 跨rank成本与原EP64目标必须实际测 | 三态收益门＋质量/内存/SLO约束，不把未测项写成失败 |

本轮最有价值的交付不应是一张“R更漂亮”的图，而是一份可复查的小证据包：旧映射与修正映射的真实区别、任务验证器能抓住错误的记录、完整量化链的数值比较、NPU计算成本表、最多两个候选的局部实测，以及明确列出的多卡未知成本。

自检：一个方案把最热rank的token数减半，却让每个热专家多激活一份权重、产生更多小GEMM。只有一张NPU时，你能实测哪些成本，哪些只能留为模型估计，哪些必须等多卡？答案应能对应S2/S3/M1中的具体字段。
