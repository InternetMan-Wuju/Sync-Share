# Prefill 全组 K=1：正式计时与回本区间实验

日期：2026-11-22。审阅基线：`b8320e5a842211132768c85d534f3ab28f91a153`。

本轮只研究 Prefill。目标是回答：**一个专家收到多少 token、分出去多少时，两张卡一起做才比一张卡做完更快？** 先把这个问题测清，再决定是否接入自动决策和完整模型。

## 1. 已知结果，以及为什么需要这一轮

[上一轮报告](../shared/current_exp/20261122_global_k_rework/REPORT_FOR_REVIEW.md)已验证真实量化专家可以安装进全组 K=1 槽，并在两卡手工分流后得到一致输出。但现有计时结果是负收益：

| 单个专家收到的 token 数 n | 原路径中位数 | 临时复制后分流 | 已准备好副本后分流 |
| --- | ---: | ---: | ---: |
| 6 | 0.9836 ms | 2.5919 ms | 1.7343 ms |
| 512 | 1.0156 ms | 2.8723 ms | 2.0183 ms |

这些数字属于专家子链的两卡实验，不能称为完整 MoE 层耗时或服务 TTFT。60 次执行是 20 组、每组 3 种模式，并非 60 组配对实验。

审阅发现三个需要分开解决的问题：

1. 当前程序为拆分耗时，在每个小步骤前后强制等待 NPU；这能帮助定位，却会改变实际运行节奏。
2. 原路径也执行了不需要的 token 索引拆分，应清理这个基线负担。
3. 512 个任务减到 256 个，源卡计算中位数只从约 0.3844 ms 降到 0.3735 ms。任务少一半，不代表耗时少一半，需要测计算曲线。

源卡与目标卡的计算在现有两进程代码里有重叠的可能；不能继续写成“两卡专家链必然串行”。是否重叠及重叠多少，用短时间线核实。

## 2. 固定范围，避免一次改太多

- 两张昇腾 910C；全组真实额外专家槽 **K=1**；固定一个目标 owner，目标卡没有其他专家计算负担。
- 继续使用真实 GLM 的 layer49 / expert43、当前 ModelSlim W8A8 和现有完整专家计算链。记录实际模型身份与软件版本，不能仅依据目录名认定模型版本。
- 保持原量化状态、源卡权重布局和目标槽布局，包含必要格式转换。每个副本状态为 37,810,176 bytes；临时传输缓冲和工作区另外记账。
- 先手工指定分流数 q，暂不把自动门槛和搜索接入 NPU 计时。因此本轮数字**不包含自动规划成本**，不能作为整套 Online 功能加速率。
- 本轮不做 Decode、K=2、跨节点、32 卡、多请求并发、完整服务 TTFT，也不为了得到正结果无限增加测试规模。
- 保留旧目录与原始样本，新实验写到 `shared/current_exp/20261122_global_k_breakeven/`。

这里 n 是**当前这个专家实际收到的 token 任务数**，q 是交给目标卡的数量，源卡继续做 n−q 个。一个输入 token 会选择多个不同专家；不能把所有专家的 top-8 任务总量当成一个专家的任务量。

## 3. 第一步：把诊断计时和正式计时分开

维护同一条功能路径的两个计时模式，先用 n=6、512 和 q=n/2 检查。

| 模式 | 做什么 | 用来回答什么 |
| --- | --- | --- |
| 诊断计时 | 保留逐段计时所需的同步；只对少量样本采集时间线 | 时间花在计算、传输还是等待上？ |
| 正式计时 | 去掉仅为诊断插入的逐段同步，保留执行正确性所需依赖 | 完成同样工作，真正需要多久？ |

正式计时必须遵守：

1. 三种模式都从统一协调端发起本次工作前开始，到完整输出回填、目标端完成本次操作、槽可安全归还为止结束。使用同一端时钟，不相减两台设备的未校准时间戳。
2. 临时复制模式包含权重打包/转换、跨卡传输、目标槽安装与 ready、token 分发、两边计算、结果返回、回填及必要同步。开始前该槽不得已有可用匹配副本。
3. 已有副本模式允许计时外安装并确认 ready；记录安装费用，不能把“预先准备好”写成“复制免费”。为保持可比性，本轮仍按单次使用结束后归还的边界测；不据此声称已实现跨请求自然复用。
4. 原路径直接计算完整 n 个任务，不执行无用的 q 拆分、外部槽准备或副本状态安装。公共控制握手可以保留，并说明它使这仍然是实验程序耗时。
5. 不能删除保障通信完成、跨 stream 依赖、权重 ready 和安全复用的等待。异步提交结束不等于本次工作结束。
6. 诊断与正式模式的功能、数据、准备/归还边界一致，只改变测量方式。首次加载和编译另记；不要混入“临时复制费”。

先统一清理新两种模式的原路径，再比较诊断与正式计时。旧结果单独保留，不把同时修改基线和同步方式产生的差值全部归因于同步优化。

可加一个不运行专家的控制握手诊断，用于解释固定成本；**不得从正式结果中人工减去这个时间**。短时间线只用于解释重叠，正式样本不开详细 profiler，不把两卡重叠阶段简单相加。

## 4. 第二步：测“token 增多，计算到底增加多少”

先做单专家容量扫描：n = **512、1024、2048、4096、8192**。6 个任务仅作为接口回归点。

对源卡实际使用的专家链和目标卡实际使用的槽专家链分别测量：预热后完成 n 个任务需要多久。二者布局、卡或计算准备不同，不能共用一条假设曲线。只测完整专家计算链本身；另将 Python 准备、索引和通信列入两卡完整实验。

- 每个形状先做 3 次预热，再固定记录 12 次，保留全部正式样本；输入种子、dtype、布局、分配策略及计时边界写清。
- 各形状都要编译/预热；临时复制模式也应预热算子，之后清空副本状态再测。它测的是“本次需要复制”，不是进程冷启动。
- 优先复用已有真实 hidden 或 routing 记录。若只有合成 hidden，明确称“真实权重上的合成任务容量扫描”；数据分布和出现频率的代表性尚未验证。
- 如果已有自然 Prefill 路由计数，附上单专家 n 的范围用于判断测试规模是否常见；没有则如实留空，不为此先启动完整服务工程。

选择配额时可以参考：

```text
乐观的计算节省 G(n,q)
  = 源卡独自做 n 个的时间
    − max(源卡做 n−q 个的时间, 目标卡做 q 个的时间)
```

这是目标卡空闲、两边计算充分重叠时的参考，**没有扣复制、输入分发、返回、准备和等待成本，不是最终净收益，也不是普适严格上界**。所需的 q、n−q 子规模要实际测量；不默认耗时随 token 数线性变化。

## 5. 第三步：用完整两卡时间找回本点

容量扫描完成后最多选 3 个 n：

1. 始终包括 512 和 8192 两端；若最大规模因资源问题无法完成，记录原因并使用本轮已成功完成的最大规模。
2. 中间增加一个“半分时 G 最大”的规模；只在成功完成扫描的 1024、2048、4096 中选择，平局取较小者，重复点合并。先确认源卡/目标卡的半分计算曲线已测齐。选择规则先固定，不能看正式提速结果后改点。
3. 每个 n 测 q=n/4、n/2、3n/4。补测这些 q 对应的计算子规模，只作解释，不替代完整两卡计时。

每个 (n,q) 都比较三种模式：原路径、临时复制、已有匹配副本。固定输入、专家状态、q 与内存策略，在同一组里配对运行。

- 每个点 12 组，每组 3 次执行。用两个输入种子，每个种子覆盖三种模式的全部 6 种顺序；顺序预先固定，避免永远让某个模式后运行。
- 最多 3×3×12×3=**324 次正式执行**，不含预热和确认复测。原路径不使用 q，但需与本组其他模式配对。
- 每次正式运行都检查输出与原路径一致、token 数守恒、没有漏算/重复回填、槽身份与状态正确。检查放在本次输出完成后的计时外；不能为通过检查改变被测计算。
- 记录最大绝对误差、相对误差和非有限值；先检查能否延续上轮 max_abs=0。如出现差异，停下解释误差来源，不自动放宽容差追求通过。
- 记录每次实际搬运字节、已准备好副本的身份、槽占用、额外分配和 allocator reserved 峰值。总内存不能只报 36.06 MiB 的槽本体。

以逐对差值为准：

```text
本组净节省 = 本组原路径耗时 − 本组分流耗时
> 0：这一组赚了；< 0：这一组亏了。
```

表格至少给：三种耗时中位数、逐对净节省的中位数与范围、变慢组数/总组数。不要用“两列中位数相减”冒充“逐对差值中位数”。12 组不声称生产 p95 或请求尾延迟。

**有限确认规则：**某个模式若有 12/12 组净节省为正，从满足条件的点中选最小 n，再选首轮逐对净节省中位数最大的 q，平局取较小 q。用新进程、新输入种子再做同样 12 组；每种副本模式最多确认一个点。两轮均 12/12 为正才称“本轮稳定回本候选点”，仍只对该子链、该负载有效，不宣称统计保证。存在正负混合就报告不稳定；没有候选也正常结束，不追加无限搜索。临时复制与已有副本分别判断。

## 6. 并行做少量 CPU 修正，暂不接入正式 NPU 路径

当前独立整数 oracle 已能揭示错误，但找出错误不等于搜索器已经修好。本轮仅做以下有明确反例的小修正：

1. **补分流候选。** 除 1、一半、全部外，加入源/目标预计完成时间接近时的整数配额及相邻整数。必须修复 `[12,4]` 的 q=4 漏解；混合专家和分块曲线再用独立 oracle 检查，不能宣称少量交点候选保证全局最优。
2. **相同总时间就不动。** 预计净节省必须严格大于安全余量才执行。将 `[4,0]`、复制费 2 的原 toy 模型平局反例加入回归，禁止仅因计算部分更小就选择零净收益复制。
3. **去重并控制搜索规模。** 等价状态不重复扩展，按案例报告搜索时间、候选遗漏和 beam 剪枝遗漏，避免把不同案例混成一个生产延迟分位数。
4. **补槽释放的竞争保护。** 上轮串行结果不因此失效，但当前“先 synchronize 再 release”不能阻止另一使用者在其间提交新任务。释放时先阻止新使用者进入，再等待已有使用和设备任务完成，最后归还；用可控交错测试覆盖。遵循现有锁规则，避免等待时死锁。先通过 CPU 回归再用于新脚本。

保留独立 oracle，不让它调用待测搜索器的评分/转移逻辑。toy 成本单位与真实毫秒分开。上述 CPU 修改报告自己的时间成本，不能当作本轮 NPU 已实测的自动决策收益。

## 7. 结果决定下一步，本轮到此停止

| 正式两卡结果 | 能说明什么 | 后续建议，须另开一轮执行 |
| --- | --- | --- |
| 已有副本在全部测试点仍亏 | 就算先准备好权重，目前分流路径也未回本 | 根据时间线检查 token 传输、返回、回填与控制等待；若计算节省本身很小，也要承认该任务规模不适合分流 |
| 已有副本赚，临时复制亏 | 有条件使用副本能回本，复制费仍挡住首次使用 | 研究真实跨调用复用和复制门槛，不能预先假定热点会持续 |
| 临时复制出现稳定回本候选点 | 该专家子链在这些规模下能覆盖本次复制费 | 先接框架原生完整单层输出，再接自动决策、K=2，最后测完整请求 TTFT |
| 差值正负混合 | 当前样本不足以支持稳定提速 | 报告波动、配对样本和影响因素，不宣布成功，不擅自追加大规模实验 |

原生框架完整 MoE 输出、shared expert、所有专家的 dispatch/combine 和服务 TTFT 仍是后续边界。本轮与原路径一致，首先证明的是当前手工完整专家子链的一致性。
