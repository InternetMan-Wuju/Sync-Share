# Prefill K=1：空编号路线的最小可行性证明

日期：2026-11-22。基线：`595428ca960c4c04da5e5dde0c44e372cd5b8377`。

用户本轮最关心：**“两卡都登记相同数量的编号，但整个卡组只增加一份真实专家权重”这条路线究竟通不通。** 本轮优先交付运行证据，不再重复容量扫描或调算法寻找提速。

## 1. 要验证的方案，用一句话说清

原模型有 256 个逻辑专家。两卡各登记 129 个通信编号，其中一个编号为空、不接任务、不分配专家状态；另一个新增编号指向唯一真实副本。**258 个编号，257 份真实专家实例，额外权重槽 K=1。** Router 仍然只有 256 个逻辑专家，top-k 仍然是 8。

本轮使用以下明确映射，避免均匀编号变化后把 rank1 的专家送错卡：

| owner | 本地编号 | 通信编号 | 实际内容 |
| --- | --- | --- | --- |
| rank0 | 0…127 | 0…127 | 原逻辑专家 0…127 |
| rank0 | 128 | 128 | 空编号：不可执行，不存专家状态 |
| rank1 | 0…127 | 129…256 | 原逻辑专家 128…255 |
| rank1 | 128 | 257 | 当前层 expert43 的唯一副本，来自跨层共享池 |

特别注意：原逻辑 expert128 现在对应通信编号129，不能沿用旧的物理编号128。expert43 的部分任务可以发到257；同一个 top-k 项只选原件或副本之一，不能追加第九项或重复算两次。

这张表是**待实现、待验证的合同**，不是对现有接口能力的描述。

## 2. 为什么上轮结果还不能回答这个问题

[上轮报告](../shared/current_exp/20261122_global_k_native_dispatch/REPORT_FOR_REVIEW.md)提供了 FusedMoE 和 EPLB 元数据要求均匀分片的源码证据。但其 `interface_contract_probe.py` 只读静态审阅结果并检查 `257 % 2`，没有调用真实构造、dispatch 或 combine。

因此，现有证据只说明 **257 个实例不能直接通过现成配置接入**，尚未验证本轮258编号方案。只看到原生分配器按129个位置分配权重，也不能直接判本轮失败——修改这部分分配行为正是本轮允许做的工作。

当前手工 K=1 子链已能正确执行，但持续驻留仅基本持平。本轮要把“接法可行”“显存达标”“实际提速”分别判断；不以是否提速替代可行性结论。

## 3. 授权范围、资源和停止边界

- 只用两张空闲910C、原测试镜像、真实 ModelSlim W8A8 专家；Prefill normal 路径，目标层49/50，目标副本expert43。不干扰其他服务。
- **明确允许**在隔离 harness 或可关闭补丁中，修改 Python 层的逻辑/通信编号映射、权重分配入口、零任务组过滤和原权重库/外部槽的 runner 适配。不要因需要这些小范围适配就直接停止。
- 继续调用当前安装的真实原生 dispatcher/combine 和真实量化/GMM 算子。允许适配器把原专家和外部槽分开执行后按原顺序合并；额外操作及适配范围必须披露。
- 不重写设备通信/计算内核，不升级整套软件，不启动全模型服务，不扩大到更多卡、Decode、K=2或多请求并发，不研究新门槛/搜索器。
- 不允许靠给每卡或每层增加一份真实权重来满足布局；也不能用自写 send/recv 成功替代原生协议通过。
- 总预算3小时：环境与256/257对照约30分钟；258协议约45分钟；真实计算、存储与跨层复用约75分钟；整理证据和推送约30分钟。预算耗尽表示“未完成”，不表示路线不通。

## 4. P0：真实256阳性对照，真实257失败位置

在当前实际镜像重新提取代码与参数，记录 import 路径、源码及扩展哈希、软件版本、NPU型号和本轮强制选用的 Prefill 后端。不要用 low-latency 分支断言替代 normal 路径证据。

先构造小型原生接口 harness，不加载完整模型：

1. **256对照：**实际调用所选 FusedMoE/metadata 构造以及原生 Prefill dispatch/combine，运行一个小型往返。保存实际调用参数、类型、返回形状和通过证据。
2. **257定位：**实际调用对应构造，保留原始异常栈和精确失败条件。预期断言失败可以由测试捕获，但必须证明调用确实发生；不能只打印预设的失败字符串。
3. 允许 CPU/meta 构造用于定位，但它只能标为定位证据，不能替代两卡 NPU 的256阳性往返。

若256在同一环境也失败，先区分导入、配置、通信或资源问题。未建立阳性对照时，不能把258失败归因于占位方案。禁止通过删掉所有断言、伪造返回值或修改已生成的审阅JSON让测试通过。

## 5. P1：258编号的真实原生协议验证

直接调用同一安装后端的实际分发/合并接口，先使用少量token和可人工核验的专家标签计算。可绕过上层固定分配器建立最小适配对象，但要说明仍复用了哪些原生组件、绕过和修改了哪些组件。

协议测试可以不加载真实专家权重；标签输出须能区分“送到了哪个逻辑专家”，不能全部采用恒等输出，否则发错专家也会看似正确。

必须检查：

- 全部256个逻辑专家都有且只有一份主实例，只有expert43多一份副本；空编号不进入任何逻辑专家的副本候选列表。
- 两个rank都作为原token发送者；任务身份至少含 `(发送rank, token位置, top-k位置, 层, logical expert)`。独立核对实际收发/执行的身份集合及重复次数，不只验 `n−q+q=n`。
- 强制覆盖逻辑专家0、43、127、128、255及跨rank边界；每个token选择8个不同的逻辑专家，原top-k权重保持不变。
- 覆盖不分流、部分分流、将expert43任务全部发给副本；目的卡原有专家同时有任务；副本零任务；某rank零任务但仍参加必要通信。
- 合并回原发送者的正确token位置；权重恰好应用一次。对照独立构造的预期结果，保存任务级身份核对及加权输出误差。
- 合法输入中空编号收到任务数始终为0。故意把一个任务发给空编号，应在进入不匹配集合通信之前让所有rank一致拒绝；不能默默丢掉或用另一专家的权重计算。
- 若空位编码为负数，验证所有索引操作不会把它当作“最后一个专家”。

误差容忍应在比较前按实际dtype和正常256对照确定，不为通过而事后放宽。通过P1只能称“258编号的原生分发/合并协议通过”，不能称真实GLM计算或K=1显存已经通过。

## 6. P2：真实权重计算，以及空编号不分配专家状态

P1通过后，才接真实 W8A8 完整专家链。优先复用已验证的量化、GMM、激活和副本状态加载代码，但实际输入和输出必须经过P1通过的原生分发与合并。

最小适配方向：**主专家权重库保持原来的真实容量，唯一额外槽单独存储；runner依据计数处理有效主专家与外部槽，并恢复分发要求的结果顺序。** rank0空编号不应进入需要读取权重的计算组。

这允许改变 Python 层对象/调用组织，不要求当前 runner 原封不动支持外部槽。但不能将主专家权重库与槽拼成新的整层大权重 tensor，也不能先分配129份权重再切掉一份，伪装成“只增加一个槽”。

真实计算验证要求：

1. 保持真实维度、真实量化scale/offset及格式处理；不能用小矩阵、全1 scale替代。
2. 至少让expert43副本和目的卡原有专家同时接任务。所有本轮有任务的专家都加载对应真实权重；可只回放有限专家集合，但须列明集合，其余为零任务，不称完整层覆盖。若只分配有限主专家，GO须限定为“有限活跃专家的原生协议、真实量化链与K=1复用可行”，不能声称已实存257份专家或验证完整128/128主权重库；要作后者声明，必须另有真实完整主库分配证据。
3. 对同一输入分别运行无分流参考和有分流候选；验证任务身份、实际权重身份、结果及加权合并。reference不能调用待测编号映射来生成自己的“正确答案”。
4. 先验证零分流、部分分流、全部转副本；目标槽未ready、generation/层/专家失配必须被拒绝，不能让不匹配权重参与计算。
5. 明确说明是“原生通信＋Python runner适配＋真实NPU算子”走通，还是仅手工子链走通；后一种不能判本轮路线通过。

如果实际设备接口要求每个通信编号都绑定完整权重，须记录该调用及约束；先检查能否在已授权适配范围内压紧有效计算组、拆开主库/外部槽调用并恢复顺序。若仍无法满足，才能作为本轮接法的具体阻塞。

## 7. P3：存储审计与两个真实层复用

**K=1必须由实际存储证明，不能只打印 `pool.capacity=1`。** 原单槽状态37,810,176 bytes仅作参考；当前ND/NZ、padding和对齐后的实际字节数重新记录。

存储清单至少包含：模型权重、scale/offset、唯一槽、格式处理后的权重、相关缓存和临时张量。逐项记录设备、shape/stride、dtype、格式、底层storage身份/字节数、data pointer和offset。按底层storage去重，既不能把多个view重复计费，也不能漏掉clone或隐藏副本。列明实际加载的主专家数量、分配的主库容量，并保证与无副本基线一致。

同时记录每rank实际 allocated、reserved及峰值；峰值从构造之前开始，不能等释放多余大权重后才测。支持时附设备侧进程HBM。取样点为构造前后、权重后处理后、首次计算、安装后、跨层切换后和清理后。

分别列出：

| 内存类别 | 要求 |
| --- | --- |
| 原专家主权重 | 与无副本基线对应，不算新增槽 |
| 唯一真实副本 | 全组仅一份可执行的持久专家状态，空编号没有另一份 |
| 编号表/计数 | 可以增加，记录真实字节；不宣称全部附加内存严格O(1) |
| 转换/传输临时buffer | 允许固定、有界、生命周期清楚的必要缓冲，数量和峰值单列 |
| 通信/算子workspace、allocator缓存 | 记录增量和峰值，不能靠只报槽本体隐藏总成本 |

禁止把第二份持久可执行副本改名成workspace；禁止通过全bank拼接、克隆、每层预制ND副本或先分后删实现假节省。仅给空位填零、不给它派token，都不等于省了权重存储。

对layer49/50执行真实 **49→50→49，至少3轮**：

- 每次安装对应层的真实权重及量化状态，不能只改layer标签。
- 唯一槽底层storage复用，generation/内容哈希随安装正确变化；每次输出与该层原路径一致。
- 旧层任务完成后才能覆盖；最终安全归还。记录同步/ready的实际保障，不靠CPU返回推定设备完成。
- 每次切换后的存储清单应解释所有新增项，额外持久专家权重容量不随切换次数或层数增长。
- 只宣称两层实测复用，不宣称75层全跑过；结合分配入口审计，说明是否存在逐层创建额外权重的路径。

## 8. 性能是可选附项，不影响功能可行性判定

只有P0～P3全部通过且仍有预算，才在已有主点 `n=8192,q=2048` 做一个小型对照。必须使用相同原始发送者、输入/逻辑路由、已驻留状态和输出终点；统一计入本次映射、分发、真实计算、合并、必要同步和使用引用归还。

最多12对无分流/占位副本分流：两个输入种子，每种子6对，其中3对先跑无分流、3对先跑副本分流；预先打散顺序并保留全部样本。正式计时不开profiler。安装成本另列，不宣称首次复制收益。无法建立公平边界或时间不足，就写“性能未测”。

不重新扫描n/q、不调自动算法、不启动新一轮profiler。即便比原路径慢，也应写“接法可行，当前性能未获益”，不能把可行与提速混为一谈。

## 9. 最终判定必须有对应证据

| 判定 | 必须满足什么 |
| --- | --- |
| **GO：这条接法走通** | 正常256原生阳性通过；258原生协议、真实量化计算、空编号零专家状态、全组唯一槽及两个真实层复用全部通过。说明适配代码和已测范围；性能单列 |
| **NO_GO_IN_SCOPE：当前环境及允许改动范围内，此接法不通** | 256阳性通过、258已实际尝试，记录明确运行失败/硬接口约束，以及已尝试的允许适配为何无法消除它。提供最小失败调用与栈；不扩大成硬件或任何未来实现都不可能 |
| **INCONCLUSIVE：证据不足，尚不能判断** | 环境/资源失败、超时、只有源码/算术检查、仅构造成功、真实GMM或存储审计/复用未完成。逐阶段标注已通过部分和未完成部分 |

不能因为默认FusedMoE分配129行就宣布NO_GO；这是本轮要适配的地方。也不能因为258通信往返成功就宣布GO；大权重分配和真实计算还要过关。
