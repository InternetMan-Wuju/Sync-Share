# EP32 验收：单次 DeepEP 改道与带补丁的在线 EPLB

基线 `c7be01b3f34567b9cf8c2b75d51a81d4972de759`，上一轮实验实现为 `7536d20`。32K 挂起已修复，原版、静态 EPLB 和本地回填版已各跑完三档。服务里仍需证明我方副本接手任务后原专家实际少算，以及原生 EPLB 挂载 NPU 兼容补丁后真实完成在线重排。本轮以正确运行和完整响应为验收条件，耗时和显存用于建立基线。[上一轮报告](../shared/current_exp/20261123_global_k_native_service_dispatch/REPORT_FOR_REVIEW.md)

## 1. 正式比较的三组

| 组 | 服务配置 | 本轮验收 |
|---|---|---|
| 原版 | 原生 SGLang 与 DeepEP，EPLB 关闭，冗余为 0 | EP32 三档完整响应，提供同输入基线。 |
| EPLB + 冗余 | 原生 EPLB 在线策略，带已有的 NPU 兼容补丁，每层全组 +32 冗余位置 | 32 rank 完成至少一次实际权重重排，更新后的布局生效，随后跑完同一批保留输入。 |
| 我方可配置 K | 原主专家加全组 K 个真实共享槽，真实任务在 DeepEP 发出前改道 | 选中的任务由副本接手，原专家计算数相应减少，同一次通信的 combine 返回正确结果。 |

静态 EPLB 布局和本地回填继续作为诊断结果。出现失败分别保留证据，正式结果矩阵按实测状态填写。小规模按 die 取设备，**全量用两台机器的全部 32 个 die 组成一个 EP32 组**。

## 2. 我方路径从已通过的单轮通信接入

EP16 回放已在同一份 top-k 表中改任务去向，用同一次 dispatch 收到的任务做主专家和副本计算，再交给该次 dispatch 对应的 combine。当前服务的失败试验另构造了只发副本的 dispatcher，最后仍调用原路径并把对应权重置零。修正后以单轮通信的方案验收，实际核对主专家算了多少。[成功回放](../shared/current_exp/20261123_prefill_eplb_three_way/scripts/replay_ep16.py#L188) · [当前服务代码](../shared/current_exp/20261123_global_k_native_service_dispatch/plugin/k_service.py#L128)

1. 先用少量 die 和一个目标层，在真实服务入口获得逻辑 top-k 后改写本次 dispatch 的目的编号。维持原本的 token 与 top-k 位置、逻辑专家和 router 权重。主专家和副本通过同一个 dispatcher 发送，在接收端按实际排列和专家分组计算，输出按本次接收顺序交回同一次 combine，核对 shared expert 路径。沿用上轮修复后的全组槽状态决定与代际绑定，直到设备完成才允许复用。
2. 先复现已通过的 DeepEP NORMAL/alltoall 路径，并核对当前镜像实际选到的策略。成功回放与失败服务还存在 dispatch 容量、输入布局、dispatcher 数量及 combine 元数据差异。若仍报 `Invalid attr=601`，比较同一小用例的输入形状与 dtype、通信编号范围、接收分组与行数、量化 scale、dispatch handle 和 combine 参数。逐项验证差异，记录第一个失败阶段。沿用等宽通信编号时，真实额外权重存储总数要等于配置 K。原生冗余参数在我方组为 0。
3. 小规模用实际服务验证关闭路径或 K=0 的输出对照、K=1 的非零改道、K=2 双槽同层参与，以及 layer49/50 的跨层复用。保留 q=0、零任务 rank 和同层连续命中的回归。核对任务身份至少含发送 rank、token、top-k 位置、层和逻辑专家。用实际接收与计算记录证明每个真实任务只算一次，并同时给出原专家的减少量、副本的增加量和正确合并的设备输出。首版继续采用已验证的固定 owner。若只支持每 owner 一个槽，启动时明确校验。
4. 上 EP32 后至少验证一次副本激活跨节点到达。分别复测同一份 32K 隔离请求与 8K→16K→32K 连续请求，确认四个 Prefill chunk 和最终响应均完成。首 token 若和原版不同，保留原版重复波动、首选 logits 及层误差；按最终累计 token IDs 核对输出序列。允许预先说明的数值容差，逐例记录偏差。

## 3. 在线 EPLB 装已有补丁并验收真实重排

上轮 `eplb_online` 启动了在线 EPLB 与 +32 冗余，现有启动脚本未挂载 updater 补丁。历史补丁让搬运使用 ND 连续缓冲，搬完写回原权重格式。另有 torch_npu 批量 P2P 兼容修复，以及减少转换峰值的 lazy-send 版本。历史成功记录所在环境为 v0.5.18、零冗余，本轮目标是 v0.5.20、EP32、+32。[上轮启动脚本](../shared/current_exp/20261123_global_k_native_service_dispatch/scripts/serve_ep32.sh#L20) · [NPU 双补丁说明](../shared/history_exp/01_EP64统一服务_2026-09/sglang_npu_eplb_patches/README.md) · [lazy-send 记录](../shared/history_exp/05_EPLB冗余专家_1P1D_2026-09-28/README.md#L59) · [历史在线成功](../shared/history_exp/07_PD共置与EPLB负优化_2026-10-11/pd_colloc_20261011/README.md#L54)

1. 对照本轮容器内实际加载的 `expert_location_updater.py` 和 torch_npu P2P 接口，沿已有补丁移植必要的兼容改动，保留原生布局算法和重排触发策略。若当前 P2P 仍需历史批量收发修复，按当前版本移植对应改动。两台节点记录运行时加载路径、补丁哈希和适用范围。对设备格式转换先做一次小规模真实权重收发。
2. 在 EP32 启用 `--enable-eplb --ep-num-redundant-experts 32`。使用与保留输入分开的校准流量触发重排。核对 256 个逻辑专家、288 个物理位置、每 rank 9 个位置。若遇临时显存不足，检查可用显存和转换峰值，优先验证历史分批转换方案。记录更新前后映射、实际搬运专家和权重生效证据、各 rank 完成状态及 `rebalance end`。确认更新后请求能完整返回，并记录真实物理位置的接收任务数。
3. 用同一服务运行已重排后的三档保留输入。重排耗时和稳定服务计时按各自的边界记录，若计时中又触发重排，标记相关样本。保留静态布局历史数据供诊断，正式第二组按在线组结果填报。
