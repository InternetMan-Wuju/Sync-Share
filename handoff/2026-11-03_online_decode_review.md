# EPLB后续会议报告：Online与Decode大EP结果复核

**复核日期：**2026-11-03。**场景：**GLM-5.2 W8A8／昇腾910C／SGLang。
**本次证据：**服务器提交 `b7ec624`，run `20261103_051202`。本地审阅代码、JSON、CSV并独立复算，没有重新运行NPU。
**承接任务：**①选一个online方法，回答效果与overhead；②少卡decode trace测量，再模拟大EP。

## 1. 可以带到会议上的结论

| 问题 | 本轮进展 | 结论边界 |
|---|---|---|
| Online方法及效果 | 参考UltraEP的当前计数复制与整数配额；960／64→512／512；单卡静态布局回放计算代理0.31577→0.24782 ms，下降21.52% | 人工输入、两个逻辑专家；planner、复制、执行尚未串成在线闭环；候选双专家链数值对照仍缺 |
| Online overhead | 两专家CPU参考planner约1.04 µs；37,769,216 B已格式化状态重复本地复制约74.99 µs | 分项计时，不是在线层总开销；未含全局计数交换、远端传输及通信增量 |
| Online净收益 | 分项中位数的串行模型余量为−8.08 µs | 不能确认稳定负收益；当前只能说尚未证明正净收益 |
| Decode大EP | 人工batch8六格中，EP32／64出现几十微秒／层的计算空间；batch1没有证明稳定正收益 | 是人工路由上的eager单卡代理；真实trace六格和多卡通信未完成 |

**总判断：这是一轮有原始证据的局部机制实验，两项任务都获得了定量进展，但尚不能按“online净收益已验收、真实decode大EP模拟已完成”汇报。**

原PDF中的现象是：增加副本后TTFT改善，但输出吞吐没有同步改善。因此本轮关心节省的计算能否覆盖规划、状态准备、通信和等待。负载更均匀不是最终验收指标。

## 2. Online：21.5%和−8.08 µs分别怎么得到

### 2.1 当前测到的是静态布局的计算空间

初始rank0处理960个e43任务，rank1处理64个e40任务；候选把448个e43任务交给rank1。任务数均衡为512／512，但接收方执行两个专家，耗时不一定均衡。

| 指标 | 原布局，额外槽零任务 | 候选布局 |
|---|---:|---:|
| rank0局部专家链 | 0.315766 ms | 0.227662 ms |
| rank1局部专家链 | 0.223706 ms | 0.247821 ms |
| 两者最大值 | 0.315766 ms | 0.247821 ms |

同一张NPU顺序测量后，取两侧时间最大值，估计假设能够并行时的计算部分：

`Δcompute = 0.315766 − 0.247821 = 0.067945 ms`，相对下降21.52%。

该方向上的约68 µs空间有数据支撑；它不是完整服务加速，也不是已经执行的双卡关键路径。[online原始数据][online_data]

### 2.2 成本账应保留，但避免把分项相加当成整链实测

| 项目 | 数值 | 实际计时范围 |
|---|---:|---|
| CPU planner | 1.039 µs | host已有两个计数后的简单配额计算；不是通用UltraEP规划器 |
| 本地state copy | 74.985 µs | 已格式化、已驻留源，复制到已有独立槽；重复块计时 |
| 独立format cast | 124.468 µs | 仅两次格式转换；加载、拼接、转置在计时外；转换结果没有进入后续链 |
| 全局统计、远端传输、dispatch/combine增量 | 未测 | 需要实际接入与多卡证据 |

若假设planner和本地复制都串行暴露，则分项中位数的余量为：

`67.945 − 1.039 − 74.985 = −8.079 µs`。

算术正确，但应报告为**串行分项点估计，尚未证明正净收益**。按五个计时块分别重建计算差，再扣同一中位copy/planner，余量为−11.659、−0.071、−8.328、+0.405、−7.996 µs。此敏感性检查不是置信区间，也不是整链测量；它说明负号尚不稳健。

候选rank1在正／反计时顺序下相差约8.9 µs，与−8.08 µs余量相当。均匀case中配置相同的A/A也出现2.915 µs偏差；两组各自块范围不重合，不能简单称为“落在已测3 µs随机波动内”。

copy已经复制格式化状态，因此不能默认再付124.468 µs格式转换。若研究另一条需要重新转换的路径，应先连接实际数据流再测；当前只能把它作为独立微基准。[实现][online_code]、[正式计时][timings]

### 2.3 三项尚未闭环的实现问题

1. **候选双专家链未做完整输出对照。** `online_npu.py:114–126`桥接的是单专家bank；实际计时的rank1是[e40,e43]。9／8分流也只调用同一个e43 bank两次，没有验证复制目标槽、e40混合任务与恢复顺序的组合。现有单专家误差0／4.63e−6和9／8逐位一致可以保留，不能代表完整候选正确性通过。
2. **PASS门禁不检查关键误差。** `online_npu.py:143–145`未约束timed-versus-dense误差、split相等和单行结果；正确性失败也没有在性能采样前立即终止。当前记录的小误差不因此失效，但COMPLETE不能作为完整验收凭据。
3. **planner与执行是分开的。** `online_npu.py:200–217`直接写死A/B配额，planner另行记账；copy在此前独立测量。还没有实际执行“收到计数→规划→检查槽状态→复制或跳过→按配额运行”。均匀case的零copy是账本判断，不是连续状态切换中的实测调用次数。

本轮仅重新检查gate offset；e40/e43其余投影offset为零有旧S1证据，引用时应标明复用旧记录。Decode其余代表专家不能自动继承该验证。

## 3. Decode：六格算术正确，解释需要调整

### 3.1 六格复算

固定同一逻辑输入跨EP，使用无副本连续映射；人工batch1有8个任务，人工batch8有64个任务。每rank保留16／8／4个槽，非空向量内部保留零槽。

| 全局batch | EP | 活跃rank | R范围 | 计算代理中位数/ms | 配对逐step节省的中位数/µs |
|---|---:|---:|---:|---:|---:|
| 1 | 16 | 6–7 | 4–6 | 0.201650 | 基线 |
| 1 | 32 | 6–8 | 4–8 | 0.206132 | −4.482 |
| 1 | 64 | 7–8 | 8–16 | 0.221820 | −20.169 |
| 8 | 16 | 15–16 | 1.5–2.25 | 0.262769 | 基线 |
| 8 | 32 | 26–29 | 2.5–3 | 0.242314 | +40.129 |
| 8 | 64 | 38–44 | 3–4 | 0.221820 | +40.949 |

48个step的槽向量、总数、活跃rank及`R=max(rank任务)/(总任务/EP)`均复算一致。[decode原始数据][decode_data]

EP32／batch8这里的40.129 µs是`median(T16[s]−T32[s])`。表中两列中位数直接相减只有20.455 µs；二者不是同一种统计量。原报告15.27%采用“配对差中位数／基线时间中位数”，不能解释为表中0.262769→0.242314的直接降幅；后者为7.78%。

### 3.2 不应将batch1写成已经证明退化

小工作类型的块间漂移大于batch1宣称的差值。按相同block编号重新构建各rank最大值，再做逐step配对，得到：

| batch | EP | 各计时块内，逐step配对节省的中位数/µs |
|---|---:|---|
| 1 | 32 | +1.538、+1.224、−4.482、+3.252、−24.445 |
| 1 | 64 | +2.780、+1.668、−21.532、−21.507、+0.321 |
| 8 | 32 | +32.881、+59.731、+38.620、+40.270、+37.026 |
| 8 | 64 | +34.925、+60.895、+39.706、+41.090、+63.980 |

这只是对聚合方法的敏感性检查，各EP仍非同期多卡执行，不是置信区间。它支持：

- batch1：没有证明稳定正收益，也没有证明固定退化2.22%／10%。
- 人工batch8：几十微秒计算空间的方向较稳；不能把40 µs当精确、普遍的通信预算。
- 原点估计下最小逐step节省为EP32的17.029 µs、EP64的38.625 µs。中位数预算不能保证每一步回本。

eager事件区间包含设备执行及可能的host提交间隙，没有分离固定启动、Python提交和权重访问，不能断言平台区由某一种硬件成本主导。

### 3.3 六格的模型假设和报告错误

- **所谓holdout不是独立预测验证。** dev和holdout工作类型都先加入表并实测，再分组汇总。只能称两个输入分组；不能据此称模型泛化误差通过。
- **空rank耗时被直接设为0。** 非空向量内的零槽保留了，但全零rank没有实测；当前模型假设其专家链被跳过，未验证生产行为。
- **槽位置换验证范围有限。** 每个EP只测一个工作类型，不能证明全部multiset都可无误差复用，尤其未覆盖所有瓶颈小类型。
- **报告中的置换百分比与JSON不一致。** 原报告写0.061%／0.320%／0.210%；最终JSON实际为0.0687%／1.2319%／0.0629%。三点均低于其5%阈值，但不构成普遍等价性证明。

上述边界影响外推可信度，不否定已记录的局部计时。[decode实现][decode_code]

## 4. 真实decode trace仍有可利用的证据

### 4.1 能确定什么

旧dump的layer49有64个记录step，每步128个任务、33–44个非零专家，最热专家12–15个任务。计数并非全部为16的倍数，因此排除了“同一个token的8个专家各简单重复16次”。

`128 / 8 = 16`仅给出与“16个路由token”相容的解释。尚未排除padding、多个来源汇总等含义，不能直接认证为16个有效服务token。[CPU记录][cpu_data]

人工batch8每步有53–60个非零专家，最热专家只占2–3／64，即3.13%–4.69%；真实记录最热专家占12–15／128，即9.38%–11.72%。这些不是匹配batch的性能比较，但足以说明本轮人工均匀路由不能代表真实热点分布。

### 4.2 缺token top8不等于真实计算模拟无法继续

缺token级路由确实阻止了把原始批次无损拆成batch1／8，也阻止了精确通信去重和输出恢复。

**但固定无副本映射下，逐专家直方图已足以生成原始批次的每rank工作向量。** 对每step、每个目标EP，把属于该rank的专家计数放入对应槽即可。计算总任务与R不需要知道哪些专家由同一个token共同选中。

因此下一步最省事的真实trace补充，是导出原始64×256计数及其记录语义，保持128个记录任务／step，直接做EP16／32／64三格。先核验padding／聚合契约；未核验时标“原始记录任务”，不标“有效batch16”。复用已有工作类型计时，缺覆盖的类型补测或留空，通信去重仍留空。

当前仓库只有总数、非零数、最大计数摘要，没有64×256完整直方图；本机无法替服务器完成这三格。需要导出原dump中的小型计数矩阵，而不一定需要重新运行完整模型或先采齐全部token路由。

## 5. 原报告八个核查点的回答

| 核查点 | 复核结果 |
|---|---|
| planner范围 | 从host两个计数开始，未含D2H与全局交换；代码和说明一致 |
| extra slot公平性 | A/B共用rank1双专家bank，A额外槽为零任务；不等于显式证明底层workspace分配完全相同 |
| max-rank计算边界 | A/B同一局部链，算术正确；仍为单卡顺序回放代理 |
| local copy每步是否必付 | 未建立实际生命周期，不能确认；副本缓存命中、跨step复用及重叠需按实际路径计账 |
| counts multiset去重 | 同EP保留槽总数；仅三点位置验证，缺所有关键类型与空rank行为的覆盖 |
| R定义 | 全体rank均值作分母，复算通过；高R可由任务不可分造成 |
| 真实dump是否batch16 | 与16个路由token相容；有效batch、padding和聚合语义尚未确定 |
| 哪些需多卡／生产路径 | 远端复制、全局交换、dispatch/combine、竞争及整层净收益；生产graph与EP64服务时延另需对应证据 |

## 6. 最小补齐顺序

本轮实验已结束；以下是下一轮的优先项，不要求自动续跑。

1. **Online先补真实数据流与数值门禁。** 同一组e43/e40输入经过实际planner、目标槽复制、双专家执行和恢复，与两个独立专家参考比较；让planner返回值驱动布局；hot/uniform连续切换时记录copy次数、字节和槽版本。将误差与split正确性写入断言，失败立即停止性能。
2. **只对关键差值补稳健计时。** 先用相同配置A/A识别约3 µs偏差；对真正候选测连起来的本地路径，再讨论−8 µs的符号。格式转换仅按实际需要计入，不重复加账。
3. **Decode先复用真实直方图。** 原128tasks／step三格比继续扩人工case更贴近任务；保留完整计数、padding契约、全零rank处理和关键工作类型复测。
4. **多卡可用后补净收益。** 单卡优先回答计算空间与本地成本；远端overhead、重叠与服务TPOT依然需要实际多卡／生产路径。
