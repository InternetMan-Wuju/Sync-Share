# Prefill 三组对照：原版、原始 EPLB 加冗余、可配置的全组 K 槽

日期 2026-11-23，基线 `7bfa44b9ea45881f8d8b1017e8341aa27157f4e2`。

本轮先把方案实现、跑通、算对。小规模按 die 验证，随后用两台机器的全部 32 个 die，在同一个 EP32 组上完成三组 AgentX Prefill 对照，必测 8192、16384、32768 输入 token。记录耗时与显存，作为后续优化的基线。功能通过和数值正确是本轮验收条件，任何性能结果都如实报告。

## 1. 三种方案

| 方案 | 实际执行方式 |
|---|---|
| 原版 | 同版本 SGLang 和原生 DeepEP，使用模型原布局，EPLB 关闭，额外 routed expert 数为 0。 |
| 原始 EPLB + 冗余 | 启用目标镜像原生 EPLB 和该配置支持的最小正冗余。用较早的校准流量统计负载，交由原算法选择布局、安装权重并按原生映射分发。 |
| 我们的全组 K 槽 | K 是启动时可调的参数，表示一个 EP 组共享的真实额外专家槽总数，可跨层复用。初版可以固定各槽的 owner。按当前批逻辑路由将部分热点专家任务移到对应副本。验证实际装槽、分流、计算、合并和槽复用，单独记录装槽与切换耗时。 |

三组保持同一模型、量化、机器、EP/TP/DP 拓扑、DeepEP 模式、输入及 logical top-k 和 router 权重。第二组的布局、复制对象和流量分配由原生策略决定。我方先用固定配额或手工计划验证完整执行路径，正式输入至少有一个真实装槽且 q>0 的热点样例。q=0 和回退也要验证，并记录触发原因。把启用、分配槽、实际重排及实际副本任务分别记下来。

可另跑第三组 q=0 诊断，副本保持就绪，沿用其编号和执行入口。这一项只帮助分辨接入开销和分流节省，三组主结果始终按上表呈现。

## 2. Die、EP 与冗余

每台机器有 16 个 die，两台共 32 个 die。按一 die 一 rank 配置时，EP 是同一个专家组里的 rank 数。小规模可以取少量 die 做接线与数值验证。全量三组均使用两台机器的全部 32 个 die，组为同一个 EP32，启动后保存 rank → 节点 → die 映射与 32 rank 参与 Prefill 的证据。

对于每层 256 个 routed expert，目标镜像的原生物理专家布局要求每个 EP rank 位置数相同。设原生每层的额外物理专家数为 `N_extra`，则要求 `(256 + N_extra) % EP == 0`。在 EP 整除 256 的这些配置里，最小正 `N_extra` 就是 EP。分别指定 EP 与原生冗余数。我们的 K 独立配置，各 owner 的真实槽数之和等于 K，同时可调度的副本数最多为 K。

| 场景 | 设备与拓扑 | 原版每 rank | 原生 EPLB 最小冗余 | 我们的真实额外槽 |
|---|---|---:|---|---|
| 小规模接线和数值检查 | 按需取少量 die，例如 EP2 | EP2 为 128 | EP2 为全组 +2 | 可配置 K，至少验证 K=1 和 K>1 |
| 全量正式对照 | 2 台机器的全部 32 个 die，共一个 EP32 | 8 | 全组 +32，每 rank 1 个 | 全组共 K 个，记录配置值和各 owner 实际分配 |

EP32 的历史启动组合是两个节点都使用 `--tp-size 32 --ep-size 32 --dp-size 1 --nnodes 2`，各自设节点 rank 0/1，并使用同一分布式初始化地址。按实测镜像、die 可用性、网络和模型显存核实启动参数。若 EP32 有阻塞，保留错误和已完成的小规模证据，全量状态标为阻塞。

原生 EPLB 的 EP32 起始配置为 `--enable-eplb --ep-num-redundant-experts 32`，以执行镜像核实参数、recorder、rebalance interval、算法和映射。上一轮 258 编号是 EP2、K=1 原型。扩展时按实际 K 和 owner 布局确定每 rank 所需的通信位置数。若沿用等宽通信编号，未分配真实槽的编号只占位置，逐 rank 核对真实权重张量、别名及空编号任务。小规模跑至少两个 K 值，验证参数改变时物理槽数随之改变，并实际覆盖两个槽可同时使用的用例。EP32 正式对照开跑前选定并记录一个 K 值，以三组主对照为先。

参考 [目标镜像布局核查](../shared/current_exp/20261122_global_k_native_dispatch/REPORT_FOR_REVIEW.md#12-为什么没有做-c1-原生接入) 和 [EP32 历史启动脚本](../shared/history_exp/08_MTP推测解码续_2026-10-11/Q1MTPExp/scripts/serve_mtp_2n.sh)。

## 3. 输入长度与热点

**全量必测 8K、16K、32K。** 正式请求的实际输入长度分别为 8192、16384、32768 token。在两台机器共 32 die 的同一个 EP32 组内，每个长度都完成三组。先过 8K 数值和运行验证，再推进 16K 与 32K。某一档受上下文、KV、通信容量或资源限制时，记录受阻的组、失败阶段和实测最大长度。

- 优先在服务器找已有 AgentX 数据和回放工具。先查看历史 `/home/chengyetai/workspace/current_exp/eplb_pd_agentx_20260928/data/agentx_16k_512.json`、[历史 AgentX 说明](../shared/history_exp/05_EPLB冗余专家_1P1D_2026-09-28/README.md) 及 [Arrow 缓存索引](../shared/current_exp/20261109_ep16_online/20261109_061333/INPUTS.json)。这些是历史位置，执行时核实。32K 从原始长度足够的 AgentX 样本中选取。若数据只提供长度和块哈希，沿用确定性 token 物化，记录 trace ID、生成规则和指纹，明确标注 AgentX 派生输入。正式运行由真实模型计算 hidden 和路由。
- 每档按模型基线路由挑选热点和普通样本。固定文本或 token IDs、tokenizer revision、输入指纹、输出长度与并发。校准输入与正式评估输入分开，EPLB 用较早窗口生成布局，我方的副本选择与配额规则也在正式计时前确定。
- 记录请求长度、chunk 容量、每次实际执行的 chunk 长度、源卡和目标卡总 routed 任务数、最热专家的真实任务数，以及最后一个 rank 完成的时间。对同一批次可写 `R = max(L_i)/(sum(L_i)/EP)` 表示最忙 rank 是平均负载的几倍，同时保留测得的耗时。把输入从 8K 拉到 32K 时，同一热点专家的任务有可能被分到多个 chunk。若需单独测试更大的 chunk，在三组一起调同一上限并另报对照。
- 把「整个请求有 32K token」「某个 Prefill chunk 有多少 token」「某个专家本次收到多少任务」分开记。只有后两个量能直接解释一次分发和计算的变化。
- 捕获与性能分开。小规模用合成输入也可完成接线与数值测试，正式结果登记服务器 AgentX 来源与真实请求输入指纹。

## 5. 时间和显存怎么算

- 单层统一用「逻辑路由就绪、开始本次必要控制」到「两端相关设备操作完成、combine 输出可消费」。正式计时包含真实 dispatch、原生 EPLB 或我方所需的映射、控制通信与核对、主/副本计算、combine 和完成等待。若 q 由在线决策生成，统计和规划计入；固定 q 的结果明确标注固定配额。逐行输入审计、参考计算和详细 profiler 使用单独验证轮次。
- 三档优先各完成三组的配对运行与输出检查，再补重复测量。正式计时可从每个输入 10 组配对起步，交替顺序并保留原始样本、同一输入指纹和真实动作计数。报告整体中位数、样本数和逐组时间差 `T原版 - TEPLB`、`T原版 - T我们`、`TEPLB - T我们`。差异接近波动时写无法区分。
- 记录稳态延迟、EPLB 更新/重排耗时、我方安装/格式转换/复制和替换耗时。装槽和副本参与计算属于功能验收，回本分析和优化留到后续。
- 一并给出各 rank 的专家主库、真实副本、占位、源 flat、格式临时区、通信工作区与 reserved/allocated，记录共同阶段与独立峰值。扩展到更长输入时带上 KV 与并发设置。附上最慢 rank 的任务和计时，解释瓶颈来自计算、通信还是等其他 rank。
- 服务数据使用匹配配置的真实请求，报告从发出请求到首个内容 token 的 TTFT，以及 Prefill 吞吐和设置。层级延迟与服务 TTFT 用各自的边界和单位。
