# Prefill 三组对照：原版、原始 EPLB 加冗余、全组 K=1

日期 2026-11-23，基线 `7bfa44b9ea45881f8d8b1017e8341aa27157f4e2`。

本轮比较三种方案在同一批 Prefill 输入上谁更快、各自需要多少显存、时间差来自哪里。先跑通完整的 layer49 MoE 回放，再进入相同拓扑的服务级测量。执行端收到用户转交的提示词后按本文推进，每阶段保留可复算的证据。

## 1. 三种方案

| 方案 | 实际执行方式 |
|---|---|
| 原版 | 同版本 SGLang 和原生 DeepEP，使用模型原布局，EPLB 关闭，额外 routed expert 数为 0。 |
| 原始 EPLB + 冗余 | 启用目标镜像原生 EPLB 和该配置支持的最小正冗余。用较早的校准流量统计负载，交由原算法选择布局、安装权重并按原生映射分发。 |
| 我们的全组 K=1 | 一个 EP 组只额外存放一份真实专家权重。首轮固定槽 owner，用校准阶段选定的热点专家；测量时按当前批逻辑路由，从原专家移出一部分任务交给该副本。先测副本就绪时的路径，单独记录装槽和切换成本。 |

三组保持同一模型、量化、机器、EP/TP/DP 拓扑、DeepEP 模式、输入及 logical top-k 和 router 权重。第二组测原生算法本身，布局、复制对象和流量分配由原生策略决定。第三组允许按既定条件返回 q=0，并记录原因；热点至少保留一个固定配额的受控分流用例，用于确认真正走到了副本。启用按钮、分配槽、实际重排和实际使用副本分别记录。

可另跑第三组 q=0 诊断，副本保持就绪，沿用其编号和执行入口。这一项只帮助分辨接入开销和分流节省，三组主结果始终按上表呈现。

## 2. 两台机器、NPU 数、EP 与冗余

每台机器有 16 个 NPU，两台最多 32 个 NPU。用一个进程对应一个 NPU 时，EP 是同一个专家组里的 rank 数。先前说的「两卡」是从一台机器取两个 NPU、用 EP2 做小实验。本轮明确区分两个 NPU 和两台机器。

对于每层 256 个 routed expert，目标镜像的原生物理专家布局要求每个 EP rank 位置数相同。设原生每层的额外物理专家数为 `N_extra`，则要求 `(256 + N_extra) % EP == 0`。在 EP 整除 256 的这些配置里，最小正 `N_extra` 就是 EP。EP 的配置和额外专家数要分别指定。我方的 K=1 是全组跨层共享容量，服务测试仍核对实际存储与同时存在的副本数。

| 场景 | 设备与拓扑 | 原版每 rank | 原生 EPLB 最小冗余 | 我们的真实额外槽 |
|---|---|---:|---|---|
| 接线和数值检查 | 1 台机器中 2 个 NPU，EP2 | 128 | 全组 +2，每 rank 1 个 | 全组 +1，固定在一个 owner |
| 正式首轮 | 1 台机器中 16 个 NPU，EP16 | 16 | 全组 +16，每 rank 1 个 | 全组 +1，固定在一个 owner |
| 跨节点复测 | 2 台机器共 32 个 NPU，EP32 | 8 | 全组 +32，每 rank 1 个 | 全组 +1，固定在一个 owner |

服务 EP16 的历史启动组合是 `--tp-size 16 --ep-size 16 --dp-size 1 --nnodes 1 --node-rank 0`。EP32 的历史组合是两个节点都使用 `--tp-size 32 --ep-size 32 --dp-size 1 --nnodes 2`，各自标节点 rank 0/1，并使用同一分布式初始化地址。按实测镜像、空闲 NPU、通信连通性与模型显存核实实际参数。独立启动的两个 EP16 进程组仍各自拥有 16 rank 的专家组。EP32 如遇启动或跨节点通信阻塞，保留错误与可用的 EP16 结果。

原生 EPLB 的历史开关可从 `--enable-eplb --ep-num-redundant-experts <EP组大小>` 核对，实际 recorder、rebalance interval、算法和映射以执行镜像的源码或参数帮助为准。上一轮原生适配的 258 编号是 EP2 的原型。推广到 EP16/32 时，如果仍用均匀的通信编号布局，可分别有 272/288 个通信编号，其中只有一个额外编号对应真实权重，其余为无权重的占位编号。先用接口和实际分配验证这种布局是否可行，逐 rank 核对编号映射、实际权重张量/别名、空编号任务和唯一物理槽。三组按实际配置报告 R、持久显存、峰值和通信代价。

参考 [目标镜像布局核查](../shared/current_exp/20261122_global_k_native_dispatch/REPORT_FOR_REVIEW.md#12-为什么没有做-c1-原生接入) 和 [EP32 历史启动脚本](../shared/history_exp/08_MTP推测解码续_2026-10-11/Q1MTPExp/scripts/serve_mtp_2n.sh)。

## 3. 输入长度与热点

**建议 8K → 16K → 32K 输入 token。** 先用 8K 跑通三组数值、布局和监测，再用 16K/32K 查长请求时的拐点。三组都能支撑时，可加 64K 做有限复测。长档受上下文、KV/通信容量或资源限制时，记录最大可比较长度和失败原因。依据目标 tokenizer 的实际 token 数标记档位。

- 每个可行档选一组自然热点和一组普通 Prefill 输入。固定文本或 token IDs、tokenizer revision、输入指纹、输出长度与并发。校准输入与正式评估输入分开。B 用较早窗口训练布局，C 的常驻对象与配额规则也在正式计时前确定。评估输入保持真实模型产生的 hidden、top-k 和权重。
- 记录请求长度、chunk 容量、每次实际执行的 chunk 长度、源卡和目标卡总 routed 任务数、最热专家的真实任务数，以及最后一个 rank 完成的时间。对同一批次可写 `R = max(L_i)/(sum(L_i)/EP)` 表示最忙 rank 是平均负载的几倍，同时保留测得的耗时。把输入从 8K 拉到 32K 时，同一热点专家的任务有可能被分到多个 chunk。若需单独测试更大的 chunk，在三组一起调同一上限并另报对照。
- 把「整个请求有 32K token」「某个 Prefill chunk 有多少 token」「某个专家本次收到多少任务」分开记。只有后两个量能直接解释一次分发和计算的变化。
- 捕获与性能分开。优先利用已授权的完整模型环境取实际路由，记录数据来源与捕获指纹。缺少真实捕获时先跑合成 smoke，正式长输入和收益留待补证据。

历史 [单专家回本扫描](../shared/current_exp/20261122_global_k_breakeven/REPORT_FOR_REVIEW.md) 和 [驻留副本复测](../shared/current_exp/20261122_global_k_native_dispatch/REPORT_FOR_REVIEW.md#32-持续驻留81922048) 无稳定正收益。本轮改变的是完整主库、原生 dispatch/combine 与真实输入，旧 P2P 数据保留作参照。

## 4. 先打通完整单层，再测正式拓扑

1. 复用 [7bfa44b 的输入保真、owner 与内存证据](../shared/current_exp/20261123_global_k_adapter_repair/REPORT_FOR_REVIEW.md)。在原生 layer49 路径建立完整的主专家库和相同主专家 grouped GMM，核对实际权重格式、量化参数和 shared expert 处理。三组共用逻辑路由，保持 routed 任务多重集及权重不变，逐组比较输出。若只覆盖 routed 子层，结果标题标为 routed MoE 回放。
2. 两个 NPU 先验证原版 256、EPLB 258、我们的 258 通信编号与一个实际槽。确认空编号只用于显式 padding，实际 expert input 等于原 hidden，分流任务从原执行位置移除，combine 输出与原版一致。对非正常 owner 或旧 generation 保留回归。两 NPU 只是验证入口，正式 EP16/EP32 各自有独立的三组对照。
3. 原始 EPLB 要有校准窗口的原生算法、更新前后映射、安装完成和物理专家命中证据。若只能在单层回放中调用原生算法并安装其输出布局，标记为「原生策略布局回放」，并明确更新器是否实跑。若重排或安装失败，该组记录失败及阶段。若新布局正确生效但某条正式样本未命中副本，如实记录其任务数。
4. 确认 EP16 的完整主专家分组、显存余量、原生路径和输出，再跑正式输入矩阵。EP32 在两台机器的设备可用且共同环境跑通后独立复测，保留跨节点流量与耗时。每个拓扑内保持设备集合、精度、batch/concurrency、chunk、prefix cache 与加载参数一致。服务 TTFT 和 Prefill 吞吐只在三组同范围服务均可执行时作对照，否则交付对应的单层结果与具体阻塞。若我方只接 layer49，服务结果明确标注仅该层开启，逐层记录 EPLB 的生效范围。

上一轮 [EP16 历史对照](../shared/current_exp/20261116_compare_eplb/RESULTS.md) 的冗余组没有完成重排，强制重排的独立运行因 HBM 不足退出。先确认执行镜像中使用的 updater，记录分支、运行时文件哈希和必要的兼容补丁，并在开启长请求前留出更新的瞬时显存。

## 5. 时间和显存怎么算

- 单层统一用「逻辑路由就绪、开始本次必要控制」到「两端相关设备操作完成、combine 输出可消费」。正式计时包含真实 dispatch、原生 EPLB 或我方所需的映射、控制通信与核对、主/副本计算、combine 和完成等待。若 q 由在线决策生成，统计和规划计入；固定 q 的结果明确标注固定配额。逐行输入审计、参考计算和详细 profiler 使用单独验证轮次。
- 每个输入/拓扑至少 10 组配对，交替三组顺序并保留原始样本、同一输入指纹和真实动作计数。分别报告各组整体中位数/p95 和逐组时间差 `T原版 - TEPLB`、`T原版 - T我们`、`TEPLB - T我们`。差异接近噪声时写无法区分。有持续优势的点用独立进程和预留输入复测。
- 稳态已准备布局的延迟、EPLB 更新/重排的额外阻塞、我们的安装/格式转换/复制以及替换成本分别计时。两种方案若比较含更新的总成本，要用同一段有顺序的真实流量，按实际发生的事件和次数汇总。我们的驻留路径稳定获益后再测冷装净收益和复用多少个 chunk 才回本。
- 一并给出各 rank 的专家主库、真实副本、占位、源 flat、格式临时区、通信工作区与 reserved/allocated，记录共同阶段与独立峰值。扩展到更长输入时带上 KV 与并发设置。附上最慢 rank 的任务和计时，解释瓶颈来自计算、通信还是等其他 rank。
- 服务数据使用匹配配置的真实请求，报告从发出请求到首个内容 token 的 TTFT，以及 Prefill 吞吐和设置。层级延迟与服务 TTFT 用各自的边界和单位。
