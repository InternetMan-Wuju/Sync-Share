# Prefill K=1：统一执行路径、格式与显存验收

日期：2026-11-22。基线：`607121e3ca87c4514a234b99d36f69a89383b211`。

**本轮要回答：同一个真实计算入口，能否既正确分流，又处理空卡，还能遇到错误时让两卡一起停下；它实际需要多少显存。通过后，剩余时间做一次固定规模的速度对照。**

## 1. 承接什么，补什么

[上轮报告](../shared/current_exp/20261122_global_k_placeholder_proof/REPORT_FOR_REVIEW.md)已证明有限活跃专家下的258通信编号、真实W8A8计算与唯一槽跨层复用。保留这个结论，不重复做源码/257算术检查。

本地复核发现需要补齐的实际缺口：

| 已有证据 | 尚缺什么 |
| --- | --- |
| 独立协议脚本能拒绝空通信编号128 | 真实计算入口先dispatch、后报错，尚未集成跨rank一致拒绝 |
| 独立padding脚本能让零合法任务rank参加通信 | 真实W8A8入口收到128仍报错；合法内部padding与非法真实任务没有统一区分 |
| 每卡每层4个真实主专家、一个目标槽 | 不足以覆盖top8全部落在一张卡上的真实计算；主库仍为有限集合 |
| 同槽7次安装、49/50内容与输出正确 | 验收程序中的槽数量、循环次数、阶段PASS部分写死，缺样本可被漏检 |
| 一份槽为37,810,176 bytes | 源卡另有等大flat发送缓冲；总运行开销不能只报槽本体 |
| 调用了真实权重处理代码 | 两rank日志有内部格式禁用、回落base format警告；未记录实际format/stride/alias |

上轮输入是合成hidden和人为top8，不能称真实router输入。当前主专家逐个调用GMM，尚不是完整原生分组runner；这些边界延续到新报告，除非本轮确有新证据。

- 暂不加载完整128/128主库，不启动全模型服务，不做Decode、K=2、跨节点、多请求并发或新门槛/筛选算法；不重写设备内核、不升级整套软件。

## 3. A：只有一个实际执行入口

正常分流、空输入、padding、负例和后续计时都调用同一个adapter，不再把几份独立脚本的通过合并成“完整通过”。建议结构如下，具体参数按安装接口实现：

```text
原始hidden、逻辑top8、权重、层与副本计划
→ 检查本地映射、目标槽身份/ready/代际
→ 两rank汇总是否允许继续
→ 仅由adapter内部产生必要padding
→ 原生dispatch
→ 识别padding并跳过，真实任务执行真实W8A8
→ 恢复原生combine所需行序和计数
→ 原生combine，剥离padding，返回原始合法token对应结果
```

保留原映射：rank0主专家comm0…127、空comm128；rank1主专家comm129…256、副本comm257。**逻辑expert128合法，它映射到comm129；禁止的是误发到空comm128的真实任务。**

### 3.1 两rank共同决定是否继续

本地发现可预期错误时先记录状态，仍参加约定的跨rank状态汇总；两rank得到同一拒绝结果后，都不进入dispatch。检查本轮涉及的逻辑/通信编号、owner、layer、expert、generation和ready。不能一张卡提前抛异常、另一张卡进入集合通信。

只有本次确有真实任务送到副本时，才要求对应槽ready，并检查“本次请求的层/专家/代际”与槽租约相符；不能仅证明租约在池内有效。q=0与全空输入允许根本没有安装副本，不为通过guard强制占槽。必要控制通信属于实际路径，后续计时包含它。

### 3.2 内部padding与真实任务分开记录

- padding只由adapter生成，正常输入无权把自己声明为padding；零weight本身不能成为使用空编号的许可证。
- 使用明确的内部身份/索引记录padding来源、目标及数量，并在原生排列后保持可识别。不能靠“hidden全零”“weight为零”或“遇到128就跳过”推断身份。
- 可以使用空编号或现有有效通信编号承载内部padding；不强制所有padding送到rank0。目标rank没有空编号时，仍需验证零接收任务的处理。padding进入通信后必须在专家计算前剔除，恢复输出时补回正确零行。
- 不为padding分配权重或申请副本，不改变真实top8及权重；返回结果中不保留padding。任何新增索引/控制通信必须披露。
- 两rank全部无合法输入时，可以一致早退，不强行制造专家任务。仍须通过同一入口并记录双方一致决定。

### 3.3 最小功能矩阵

| 用例 | 验收点 |
| --- | --- |
| 双卡有输入，q=0、部分、全部转副本 | 主专家和副本都经过统一入口；实际任务身份与独立参考吻合；另验未安装任何副本时q=0仍成功 |
| rank0无输入；rank1无输入 | 另一张卡发来的任务仍能被正确接收计算；返回各自原始输入数量的结果 |
| 全部真实专家任务只在rank0算；只在rank1算 | 真正零专家任务rank正确参与；不能仅用“没有输入”代替这项 |
| 两rank都无输入 | 双方一致返回空结果，真实专家和副本调用均为0 |
| 仅一rank误发空comm128，包括零weight伪装 | 两rank一致拒绝，均未进入dispatch；不把非法任务当padding吞掉 |
| 副本未ready；layer不匹配；generation过期 | 由同一入口拒绝；不是只运行旧槽池单测 |

非法输入分别从两rank注入；目标槽相关故障在对应owner注入。非法comm128通过统一adapter的显式测试注入点，在逻辑→通信映射之后、跨rank状态汇总之前修改，不能误禁合法logical128，也不能另写一条绕过adapter的负例路径。每种预期负例后，在同一进程中接着跑一个合法用例，证明通信顺序未被破坏。记录真实dispatch调用计数，不能写死 `dispatch_not_called=true`。父进程为每个用例设有界超时（建议60秒，可按设备初始化实际成本调整并预先记录）；超时终止本轮子进程并标FAIL，不当作成功拒绝。不扩展成任意HCCL故障恢复系统。

top8仍须为8个不同逻辑专家。当前每卡4个主专家不够做“全部任务只在一张卡”的真实用例；允许按需给目标卡增加有限主专家至至少8个，或采用7个主专家加expert43副本的合法组合。全部用对应真实权重，记录各用例主库集合；不能重复选4个专家凑top8。各对照的主库配置一致。

独立参考沿用主专家owner计算加全组汇总，适配不等长/零输入；不调用候选通信映射产生答案。检查每个真实任务 `(sender, token, top-k位置, logical expert, layer)` 恰好一次、原位置返回、路由权重只用一次、输出有限、padding实际专家调用为0。原生物理编号另记，允许原件/副本不同。

对同一输入同时保存“候选vs独立参考”和“分流vs同入口q=0”的误差。预先确定容差并记录误差定义，沿用上轮容差须明确标为暂定工程容差；不为通过而放宽。所有阶段统一检查绝对误差、约定的相对误差与非有限值，复用阶段不能少检查一项。输入/路由仍为合成时明确标注。

## 4. B：确认格式，把显存账算完整

### 4.1 格式依据

优先只读现有服务启动脚本、配置和安装镜像的真实权重处理实现，确认生产是否允许内部格式、实际如何处理ModelSlim权重。无服务或配置不足时写“生产格式未确认”；不能凭上轮警告猜生产一定使用NZ，也不能为了通过擅自改变整机配置。

在隔离进程中，对主专家加载后、发送前、目标槽安装后和计算后，记录 `w13/w2/scales/offsets` 的真实NPU格式码、shape、stride、dtype、data pointer、storage pointer/bytes和offset。记录转换前后是否共享底层存储。查询接口不支持时提供实际错误与缺项，不填猜测值。

以能核实的生产设置执行一次同输入q=0/部分分流及空卡真实计算。槽可使用与主权重不同的合法格式，但必须确实被算子支持，相关转换和运行成本计入。若只能base format成功，结论限定base format；生产配置未知、格式失败、尚未尝试分别标注。

### 4.2 存储与峰值

修正无用的flat重复分配；不要假定 `sample`/格式转换必然产生副本或必然是view，必须核对其storage。完整记录：

| 类别 | 怎么记录 |
| --- | --- |
| 原主专家权重 | 实际集合、格式、按storage去重的容量 |
| 唯一目标槽及其执行权重view | 实际分配计数、owner、storage；不能靠常量1证明 |
| 源卡flat发送缓冲 | 字节数、创建/释放或复用时间；保留全程就称常驻发送缓冲 |
| 格式转换、安装中间状态、sample | 与主库/槽是否alias，独立存储占多少，生命周期和峰值 |
| 输入/输出、参考路径、索引和padding | 分类列出；参考验证独有内存不当作线上必需开销 |
| 通信和算子workspace、allocator缓存 | 当前allocated/reserved与峰值；无法归属的增量单列，不假装全部解释完 |

从构造之前保留全流程峰值，并记录主库后、安装后、首次计算后、每次换层后和释放后的当前值。支持时补设备侧进程HBM；`reserved`不能当作仍存活的权重容量，设备free变化也不能全归因本进程。

同主库/同输入配置，以独立新进程跑无副本基线与K=1候选的内存对照，避免分配器历史混入。分别报告稳态、安装峰值、计算峰值；不要把不同时刻各rank峰值之和称为同时发生的集群峰值，可标保守上界。

在统一入口执行 **49→50→49三轮**：共7次安装、6次切换后计算，每次记录源/目标hash、预期层、实际层、严格递增generation、storage身份、任务守恒和输出误差。旧计算设备完成后才能覆盖，最终池内在用引用为0且租约归还。这里证明两层交替复用，不称两层串接模型forward。

允许固定、有界的发送和格式临时空间，但全组可调度的额外持久专家槽仍为1，不因层切换增加。37,810,176 bytes是旧格式payload参考，不强制实际带padding/对齐的存储必须恰好等于它。若格式适配需要额外持久执行权重，必须显式报告并重新判定资源目标，不能改名workspace掩盖。

## 5. C：通过必测项后，只做一个可解释的速度对照

当前4/4专家分布的输入，两卡任务本来一样多，搬expert43只会让目的卡更忙。因此不能原样放大它并用负结果否定“利用冷卡”。如果A、B未通过或预算不足，C明确NOT_RUN。

本轮固定一个**合成热点**，不做输入规模/配额扫描：

| 量 | 定义与固定值 |
| --- | --- |
| 全组输入token N | 8192；默认两发送者各4096，不是每卡8192 |
| top-k | 每token选择8个不同的真实专家 |
| 主专家归属 | rank0有6个活跃专家，rank1有2个；包含rank0的expert43 |
| 全组专家任务 | 8192×8=65536 |
| expert43任务 n43 | 8192 |
| 分流 q43 | 2048，两个发送者各分1024，目的地为唯一驻留副本 |
| 搬前两卡真实任务 | 49152 / 16384 |
| 搬后两卡真实任务 | 47104 / 18432 |

这是人为构造的热点，不是真实router流量，也不是自动复制决策算法。报告上述每个计数的实际值；不能把8192个输入token与8192个专家任务混用。先验证后端容量与每rank dispatch上限适配4096输入及padding，不能沿用上轮64上限就硬跑；若需要分chunk，记录边界且所有对照相同，不再扫描chunk参数。

优先使用安装后端的主专家**分组计算**，比较三条路径：

| 路径 | 用来回答什么 |
| --- | --- |
| B0：256编号、无副本、原生主专家分组计算 | 相同后端下的无副本基线 |
| B1：258编号、q=0、同样主专家分组计算 | 统一adapter/占位本身花多少时间 |
| B2：258编号、q43=2048、唯一副本已驻留 | 分流是否覆盖新增开销、相对B0是否净提速 |

可以为主专家使用合法紧凑bank或后端支持的权重列表，禁止每轮把主bank与槽拼成新的整层大权重。三条路径必须采用相同的主专家计算方式、权重、格式、通信后端、输入与原发送者；不能故意把B0逐token执行或加额外等待。若来不及接入分组计算，本轮C标NOT_RUN，记录“逐专家原型不足以给出原版性能结论”，不再启动另一套大规模诊断。

计时从相同逻辑路由/hidden已就绪开始，到全部合法输出可用、必要设备等待与使用引用归还结束。候选路径的映射、固定配额分流、全rank校验、padding、dispatch、真实计算、combine、必要同步都在边界内；独立参考、完整任务审计、JSON/hash写盘在计时外。不能预先做好候选独有映射或省掉必需guard来获得好看数字。

副本提前安装并明确标为驻留条件；安装不计入该次计时。若另测安装，应把调试hash/参考计算与真实复制准备时间分开，不沿用上轮含调试操作的 `install_ms` 充当真实成本。没有冷复制对照，不报告首次复制净收益。

最多12组三路径配对：两个输入种子，每种子把B0/B1/B2的6种顺序各运行一次；预先列出顺序并保留全部样本，各路径预热规则相同。每次B0、B1或B2单独测量开始前，两rank先完成上一轮设备工作并共同对齐；对齐放在计时外，随后各自开始计时。每条路径的局部完整设备完成时间在计时后汇总，取两rank最大值作为该次全组完成耗时估计；不直接比较未校准的跨卡绝对时间戳。正式计时不开profiler。

报告每组 `B0−B2` 净节省、`B1−B2` 分流节省、`B1−B0` 接入成本，并给出中位数、四分位、正收益次数、按种子/运行顺序拆分的结果。两种子方向不一致则写不稳定；12组不支撑生产显著性保证。正结果也只限该合成热点、有限主库与驻留条件。

## 6. 验收器必须由实际证据判定

- 检查完整用例名单、实际记录数量、每rank参与情况及本轮run_id；不能拼接上轮残留JSON生成新PASS。
- 从真实存储清单计算槽数与字节，检查7次安装、指定层序列、generation严格递增、6次切换结果及最终释放。双方事件数量必须相同；不能用 `zip` 截断后静默忽略缺项。
- 空结果列表、缺模式/缺rank/缺步骤应为FAIL或NOT_RUN；不能让 `all([])` 变成通过。每阶段状态从该阶段检查生成，不写死PASS。
- 加最小验收器回归：删一条复用记录、缺一个rank、打乱generation或把状态设为未ready，汇总必须拒绝给整体GO。仅改拷贝的测试fixture，不修改实际原始记录。

报告分别给三个结论：

| 结论 | 判定口径 |
| --- | --- |
| 功能 | 统一入口全部合法/空任务/预期负例及跨层复用通过，才是功能GO；注明真实权重、合成输入、有限主库 |
| 格式与资源 | 写明生产格式匹配/未确认/失败，以及一槽是否达标、额外缓冲和峰值；不能用槽payload代替总成本 |
| 性能 | NOT_RUN、未获益、不稳定或有限场景获益；与功能结论独立 |

若统一入口实际失败，给最小复现、异常栈、两rank状态及已尝试修正，判定“当前实现未通过”。只有明确接口阻塞且本轮允许的适配无法解决，才可限定为NO_GO_IN_SCOPE；不扩大到任何实现都不可能。环境、时间或证据不足写INCONCLUSIVE。生产格式未确认时，不写“生产接入已通过”。

## 7. 交付和停止

新目录：`shared/current_exp/20261122_global_k_unified_adapter/`。

交付一份 `REPORT_FOR_REVIEW.md`，开头用人话回答：“同一条路径是否完整可用、总额外显存多少、快了没有、下一处具体阻塞是什么”。附统一adapter/必要补丁、`reproduce.sh`及实际生成的：

- `CASE_RESULTS.json`：本轮run_id、逐rank用例、真实任务/padding计数、dispatch调用计数、数值及负例后恢复。
- `FORMAT_AUDIT.json`、`STORAGE_AUDIT.json`：配置依据、真实格式/alias、分类存储与独立进程基线/候选峰值。
- `LAYER_REUSE.json`、`VERDICT.json`：原始安装序列、释放状态、逐阶段状态及范围。
- `TIMINGS.csv`：仅在真正计时后生成；未测就在判定中写NOT_RUN。保留顺序、种子、各rank时间、组时间和全部原始样本。
- 环境/源码/模型元数据哈希、必要原始日志及MANIFEST；模型权重、大型张量留服务器，附路径和哈希。

复现入口至少有 `functional`、`format-memory`、`reuse`、`validate`，性能完成才提供 `perf`。`all`必须真实执行本轮必测阶段，预期负例明确捕获，意外失败非零退出；阶段未做要写NOT_RUN，不能读历史结论冒充重跑。

完成或到时，清理本轮资源，提交并推送main，返回commit、报告、复现命令及三个结论，然后停止。不自动启动下一轮。
