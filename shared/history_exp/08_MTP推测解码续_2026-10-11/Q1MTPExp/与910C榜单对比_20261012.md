## 3. 怎么读这张表

1. **TPOT 我们差 2.5~3.5 倍**（127~171ms vs 51~56ms）。注意 MTP 本应**降低**每 token 延迟
   （9-28 实测：MTP 关 472ms → 开 127~186ms），但仍远慢于榜单的非 MTP 基线。
   → 最大嫌疑是 **Decode Graph 被关**（榜单是开的），其次是 `DeepEP normal`。**这一条必须验证清楚**，
   否则我们的 MTP 数字都建立在一个"慢环境"上，跟别人的基线没法比。
2. **TTFT 差异主要来自 KV 池容量**：
   - 本机 16 卡 KV 池只有 **29568 token**（9-28 同配置实测 43008）；
   - 4 条 16K 输入 = 65536 token > 29568 → 排不下 → 后来者排队 → TTFT 被撑到 98~116s；
   - 榜单 3.1 的 221s TTFT 同理（并发 32 + KV 限制）。
   → 比较 TTFT 必须带上"并发 + KV 池容量"。
3. **吞吐（tok/s/NPU）**：我们 1.74 vs 榜单 3.1 的 5.82（差 3.3×）；但并发差 8 倍（4 vs 32），
   batch 效率差很多 → 要公平比就得**同并发**再测。
4. **我们目前连文档的 MTP 目标都没碰到**：AL 2.45~3.34（目标 2.0±5%）、
   TPOT 127~171ms（目标 P50<33ms）、TTFT 1~116s（目标 P50<15s，只有 1K 输入那几组达标）。
   **差距主要来自配置，而不是 MTP 本身。**

## 4. 结论 / 下一步

1. **先解决"MTP × Decode Graph × DeepEP auto"的兼容性**：
   - v0.5.18 + `deepep auto`：Decode Graph 捕获崩（`aclnnMoeLowLatencyCombineV2`），
     关掉 graph 后 **MTP draft 前向仍撞同一内核**；
   - v0.5.16 + `deepep normal` + graph 关：MTP 能跑（= 9-28 与本次），但性能基线差 2.5~3.5 倍。
   → 要么找到"MTP + graph 开"的组合（换镜像 / 换 deepep 模式 / 打补丁），
     要么**明确声明**：MTP 实验只在"graph 关"的前提下做 ON/OFF 相对比较，不与榜单绝对值对标。
2. **KV 池容量要单独攻**：32K 输入已被拒收，**100K 前缀（文档用例 1）在单机 16 卡根本放不下**。
   需要 HiCache / KV offload / 更多卡，或把用例降到 32K。
3. **正式 MTP 实验的三条硬要求**（对齐榜单口径）：
   - 同并发下比（至少复现榜单 3.2 的并发 2 与 8k/1k 的并发 32）；
   - 报数时注明 `DeepEP 模式 / Decode Graph 是否生效 / KV 池容量`；
   - MTP 的收益只报 **ON vs OFF（同配置）** 的差值，绝对值单列并注明环境。
