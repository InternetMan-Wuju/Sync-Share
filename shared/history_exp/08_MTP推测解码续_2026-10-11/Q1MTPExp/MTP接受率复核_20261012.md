# MTP 接受率复核（2026-10-12）

本报告使用保存的逐请求数据、实际 v0.5.19 镜像源码，以及从20节点只读复制的游兴业脚本。原始数据没有改写。SGLang 原生 random-ids 的短复测已完成，结果见第8节；23节点服务已停止、容器保留。

## 1. 当前能确定的结论

1. **历史长输出的 AL≈4 有明确的循环输出证据。** 2026-09-28 同一输入在 MTP OFF 和 ON 都重复 `[168,111,238]`；ON 的21184个输出只有3种token，草稿接受率99.92%。循环在关闭MTP时也存在，不能归因于MTP凭空创造了它。
2. **本次高接受率仍混入明显循环。** 32K/1K中一条1024输出只有1种token，AL=3.969；1K/2K中一条2048输出只有8种token，AL=3.908。旧客户端只检查“从第一个token起完全周期重复”，漏掉先有短前导、后面才循环的输出。
3. **计数高不等于计数造假。** 本次四组20条请求的直方图、verify次数、草稿计数、实际输入输出长度均复核通过。它说明记录的计数彼此一致，不能据此证明模型数值完全正确或输出质量合格。
4. **我们自写的独立随机ID不是SGLang random-ids。** 在实际v0.5.19镜像及游同学v0.5.16容器里，SGLang先随机选起点，再连续递增ID；我们逐token独立采样。这是确实存在的数据偏差，但不足以单独解释全部高接受率。
5. **AL并非越接近2越正确。** MTP=3时，AL包含主模型带来的额外token，通常最多接近4。参考接受率若采用本文的无条件口径，`0.498+0.345+0.267+1=2.110`。参考材料没有给出完整模型、采样和测量定义，不能把2.0当成通过换输入必须凑出的结果。
6. **当前NPU验证实现有平台差异。** 实际镜像 `eagle_sample()` 的分支是 `is_all_greedy or ... or _is_npu ...`，NPU直接使用argmax做贪心验证；非贪心的概率验证在另一分支。不能假设调高temperature就与GPU上的概率推测采样一致。本次temperature=0，因此该分支与本次请求的贪心设定一致。
7. **原生短复测没有把AL自动降到2。** 精确ID方式AL=2.876；官方默认text方式AL=2.338，但输入由1024变成1106/1088token。旧独立随机对照AL=2.783。输入口径差异已经证实，接受率仍高的全部成因尚未逐项隔离；两条样本不能推断普遍高低。

## 2. MTP到底测什么

主模型负责最终判断，草稿头先预测接下来3个token。验证时依次检查这个草稿前缀，遇到第一个不通过的位置就停止接受后面的草稿，再由主模型提供一个token。完全命中时一轮可前进4个token；全部不命中时通常仍能前进1个token。

如果输出已经变成 `A,B,C,A,B,C,...`，草稿和主模型都容易继续预测这个模式，接受率可以接近100%。这个数对当前退化输出是实测值，但不能代表正常业务请求的接受率。相反，重复也不保证三个位置全部通过：本次8K/1K中的 `</think>` 重复请求AL只有约2.024，另一个低多样性输出AL约2.165。

因此要同时回答两件事：草稿实际中了多少；这些命中发生在什么输出上。只看AL无法区别“正常内容好预测”和“模型陷入循环”。接受长度也不是吞吐加速倍数，还受到草稿开销、验证开销、通信和batch影响。

## 5. 输入构造和他人脚本的差别

### SGLang原生函数

实际源码 `benchmark/datasets/random.py`：

```python
offsets = np.random.randint(0, tokenizer.vocab_size, size=num_prompts)
input_content = [int((offsets[i] + i + j) % tokenizer.vocab_size)
                 for j in range(input_lens[i])]
```

`random` 分支则读取ShareGPT的第一条用户prompt，重复/裁剪到指定长度；它不等于逐token独立随机，也不等于直接复现原始真实对话。

`random_range_ratio=1`才固定长度；0表示允许从1到目标长度采样。默认没有 `--tokenize-prompt` 时，原生随机ID先decode成文本，再由服务端重新分词；传此参数才直接发送原始input_ids。这两个发送路径也需要区分。

我们的历史/四组输入：`rng.randrange(1,154880)` 每token独立抽取，包含模型的角色、EOS等added token及部分未在tokenizer定义的ID。检查落盘输入已看到 `<|assistant|>`、`<|endoftext|>`、`</think>` 等。这可能改变输入结构，但**不是已证明的唯一根因**：本次1K/2K的循环样本没有added token。

## 6. 源码证据和统计口径

实际镜像ID：`sha256:440300a502360e31e7dcdac11f53bc5575c09d8e1b07e27150c5d195a3f26317`。从本机该镜像的只读layer读取源码，没有另起容器。文件SHA和来源见 `audit_20261012/source_current_image/PROVENANCE.json`。

- [random.py](audit_20261012/source_current_image/benchmark/datasets/random.py)：原生输入构造与text/IDs分支。
- [eagle_utils.py](audit_20261012/source_current_image/srt/speculative/eagle_utils.py)：`eagle_sample` NPU贪心验证及bonus计数；源码中的模拟接受分支仅在显式SIMULATE_ACC_LEN>0才覆盖结果。
- [environ.py](audit_20261012/source_current_image/environ.py)：`SGLANG_SIMULATE_ACC_LEN`默认-1。本次launch与镜像默认环境均未设置此变量，未发现通过这个开关强制接受率的证据。
- [tokenizer_manager.py](audit_20261012/source_current_image/srt/managers/tokenizer_manager.py)：每请求终态接受长度、草稿计数、直方图。
- [serving.py](audit_20261012/source_current_image/benchmark/serving.py)：原生客户端发送参数；benchmark汇总accept_length的服务累计均值来源。

设h[j]为该请求接受j个草稿的验证轮数（j=0..3）：

```text
P1 = (h1+h2+h3) / sum(h)
P2 = (h2+h3) / sum(h)
P3 = h3 / sum(h)
草稿接受率 = (h1+2*h2+3*h3) / (3*sum(h))
AL = 实际输出token总数 / verify总数
```

P1/P2/P3是到达该位置的无条件概率，不能与“已接受上一位后的条件概率”混用。跨请求先累加计数再除。AL近似为 `1+P1+P2+P3`，首token和输出长度截断使边界存在小差异。
