# MTP 接受率为什么高：重新定位问题

本次结论来自历史对话、会议原字幕、保存的逐请求输出、实际镜像验证源码，以及当前模型文件的少量字节核验。新增证据保存在 [root_cause_evidence.json](causal_review_20261012/root_cause_evidence.json)，由 [diagnose_mtp_root_causes.py](scripts/diagnose_mtp_root_causes.py) 在 CPU 上重新计算。没有发送新模型请求，没有修改权重或正在运行的服务。

**需要优先处理的是当前模型权重基线：本机实际模型的第 2、23、41 层注意力权重含 30,900 个 NaN/Inf。历史文档把问题概括为“损坏只在专家、不涉及注意力”，这不准确。** 历史 AL 接近 4 的直接解释是循环输出；本次仍包含循环、忽略正常结束点后的续写，以及与参考数字不同的输入和统计条件。尚不能把剩余差距归结为一个已经证明的 MTP 算法错误。

## 1. MTP 实际在做什么

GLM 的配置有一个 MTP/NextN 层：`num_nextn_predict_layers=1`。设置 steps=3，是把这个草稿模块连续运行三步，提出接下来三个 token，不是模型额外拥有三个独立的主模型。

主模型随后用一次验证前向检查草稿。在本次 NPU 贪心路径中，验证器比较草稿 token 与对应主模型 logits 的 argmax；遇到第一个不一致就停止接受后面的草稿，并提交主模型提供的一个 token。因此一轮通常前进 1～4 个 token。草稿全错仍然能前进，草稿全对最多前进四个。

令 `h[j]` 是接受 j 个草稿的轮数，j=0～3，V 为总验证轮数：

| 指标 | 含义与算法 |
|---|---|
| P1 | 第一位草稿被接受的无条件概率：`(h1+h2+h3)/V` |
| P2 | 前两位都被接受的无条件概率：`(h2+h3)/V` |
| P3 | 三位都被接受的无条件概率：`h3/V` |
| 草稿接受率 | `正确草稿数/(3V) = (P1+P2+P3)/3` |
| AL | `实际输出数/V ≈ 1+P1+P2+P3`，包含主模型额外提供的 token |

首个 prefill token、最后一轮的长度/EOS 截断会造成小的边界差异。跨请求需要先合计计数再求比值。

**AL 测的是草稿在当前主模型输出轨迹上的命中情况。它不证明轨迹正确，也不等于吞吐加速倍数。** 正常、容易预测的内容可以有高 AL；两个推理路径共同进入错误循环，也可以有高 AL。草稿开销、验证前向的开销、batch 和通信决定最终性能收益。

## 2. 历史接近满接受：直接证据足够明确

重新读取 2026-09-28 的完整/截断 output_ids，检测精确周期尾段：至少 64 token、至少重复八次；周期尾段占输出一半以上归入“主要循环”。这只是输出形状诊断，不能把其余组自动叫作正常业务。

| 历史 MTP ON 场景 | 主要循环记录/总记录 | 全组 AL | 主要循环组 AL | 其余组 AL |
|---|---:|---:|---:|---:|
| 1K/32K 目标输出 | 1/2 | 3.998 | 3.998 | 无有效统计 |
| 8K/1K | 11/18 | 3.459 | 3.887 | 2.878 |
| 总32K/300、约60%缓存 | 12/38 | 2.767 | 3.600 | 2.492 |

1K/32K 的有效长请求 ON 输出 21,184 个 token，只有三种 ID，循环为 `[168,111,238]`；OFF 同输入的 5,715 个 token 也完全重复这个周期。第二条记录是窗口末尾极短的补发，不代表另一条完整长请求。

这解释了为什么该长请求草稿接受率达到 99.92%：主模型和草稿都在继续同一个简单循环。**数字是退化轨迹上的实际计数，问题是拿它代表正常任务的效果。** OFF 也循环，说明不能归因于 MTP 独自创造了循环。

同样不能说历史高 AL 全由循环解释：其余 8K/1K 和前缀请求仍有 AL=2.878、2.492；其中还可能有非精确的复述、EOS 后续写或其他实现差异。

历史 9/28 使用只读恢复外挂，对齐了当时参考快照；本次直接加载 `/data_lib/data/models/glm-q`。两轮权重来源不同，不能把今天查到的损坏反向当作当时 AL=4 的已证实原因。

## 3. 本次输入更换并没有解决输出退化

旧的独立随机 ID 补测结果是：8K/1K AL=2.901，32K/1K AL=3.084，1K/2K AL=3.228，前缀场景 AL=2.614。其中 32K/1K 的一条输出只有一种 token，AL=3.969；1K/2K 的一条只有八种 token，AL=3.908。

本次又读取了原生函数完整重跑中**已经完成**的三个场景；1K/32K 长请求在证据采集时仍在运行，不能提前给它填最终接受率。

| 原生 random-ids 完整重跑已完成部分 | 请求数 | AL | 草稿接受率 | 主要循环请求 |
|---|---:|---:|---:|---:|
| 8K/1K，并发4 | 8 | 2.526 | 0.5090 | 6/8 |
| 32K/1K，并发1 | 1 | 2.901 | 0.6336 | 0/1 |
| 总32K/300，并发1 | 2 | 2.804 | 0.6044 | 0/2 |

8K/1K 的四条循环输出分别 AL=3.807、3.894、3.835、3.938；另外两条都是 1,024 个 `</think>`，AL 却分别只有 **1.238、1.585**。两条未检出精确周期的输出加权 AL=2.880。

因此这组数据同时否定两种简化解释：

- “改成官方 random-ids 就能消除循环、AL 自然回到 2”：仍有 6/8 条精确循环。
- “输出重复就必然每个草稿全中”：主模型重复 `</think>` 时，草稿可以经常猜错。接受率取决于草稿与主模型的相互一致性。

该组最初汇总脚本因直方图缺少未出现的尾部零桶而报 `IndexError`。逐请求数据完整，现有目录已由另一次工作恢复汇总并校验通过；本次独立复算得到相同 AL。原始 `[647,164,16]` 对应 `[647,164,16,0]`，这个客户端错误不证明服务端接受计数错误。本次没有重发请求或改写原记录。

输入构造也必须讲清楚。旧自写数据是每个 token 独立从 `1..154879` 抽样，包含角色/EOS等 added token 和 tokenizer 未定义的尾部 ID。实际镜像的原生 random-ids 则随机选起点，随后按词表 ID **连续递增**，在 `tokenizer.vocab_size=154820` 处取模。这是两种不同的序列分布，不能都称作同一个官方 random-ids。原生序列仍然不是有意义的业务问题，出现循环并不意外；它已经排除了“输入抽到added token是全部循环的必要条件”这个解释。

原生工具还有 text 与 exact-IDs 两条发送路径。默认先 decode 成文本，再由服务重新分词；短测中原本的1,024个 ID 变成了1,106/1,088个输入 token，两条加权 AL 从精确 ID 的2.876变成text的2.338。模型收到的输入内容和长度都变了，不能称为只换了HTTP字段。每组只有两条，也不能由此断言默认text总会降低AL。`random` 分支则是从ShareGPT取首条用户正文，再重复/截断到长度，同样不等于原始完整聊天请求。

## 4. 被忽略的具体因素：模型已经结束，客户端仍要求继续

实际 `config.json` 的结束 ID 是：

| ID | token |
|---:|---|
| 154820 | `<\|endoftext\|>` |
| 154827 | `<\|user\|>` |
| 154829 | `<\|observation\|>` |

这些 ID 出现在输出时，`ignore_eos=False` 的生成应在首次命中处结束。正式固定长度压测使用 `ignore_eos=True`，会继续生成。这在负载长度上是明确的实验设定，但测出的内容不再等同于正常结束的单次回复。

新核对的完整输出显示：

| 样本 | 首个结束 token 的输出位置，从0开始 | 其后仍生成的 token |
|---|---:|---:|
| 原生 exact-IDs 短测，第0条，输出256 | 0 | 255 |
| 原生 exact-IDs 短测，第1条，输出256 | 30 | 225 |
| 原生默认 text 短测，第0/1条 | 0 / 7 | 255 / 248 |
| 原生完整 32K/1K，第0条 | 33 | 990 |
| 原生完整前缀32K/300，第0/1条 | 0 / 70 | 299 / 229 |

原生 exact-IDs 短测中，512 个输出有 **480 个发生在首次结束 token 之后**。完整 32K/1K 中 1,024 个输出有 990 个在结束点后；前缀两条的 600 个输出有 528 个在结束点后。部分输出开始模拟下一轮用户或反复描述假想问题。

这证明“强制结束点后续写”已经进入统计；**尚未证明它贡献了多少 AL 增量**，因为这些请求的草稿计数只在终态返回，不能用总直方图恢复结束点前后的准确接受率。也不能据此宣称全部循环由 ignore_eos 引起：不少循环样本根本没有 EOS。

本次标作“真实文本”的旧数据也不是完整聊天请求。`build_quick_datasets.py` 将 ShareGPT 所有角色的正文直接拼接，再截取前 1,024 个 token；未调用 chat template、没有角色边界，可能截在旧 assistant 回复中间。保存的第二条输入尾部就在描述 `MOV AX` 的文章中间。这测的是文本续写，不能据“0条严格周期”就称为正常业务对话验证。

## 5. 当前权重基线存在明确损坏，而且损坏涉及注意力

这次没有重扫 721GiB 模型，只读读取三个 32MiB 块，共 **96MiB**。核实当前文件 header 与保存的张量映射一致，按 safetensors 张量边界解释 BF16 数值，得到：

| 当前模型中的具体张量 | NaN/Inf 数 | 有限但绝对值>1e10的数 |
|---|---:|---:|
| `model.layers.2.self_attn.kv_b_proj.weight` | 4,990 | 6,511 |
| `model.layers.23.self_attn.kv_b_proj.weight` | 25,801 | 36,574 |
| `model.layers.41.self_attn.kv_b_proj.weight` | 109 | 6,934 |
| 合计 | **30,900** | **50,019** |

三个块的本次 SHA256 均与 10/11 已保存的 `/data_lib` 扫描一致，并与当时参考快照不同。它们分别位于：

- `quant_model_weights-00001-of-00181.safetensors`，offset=67,108,864。
- `quant_model_weights-00047-of-00181.safetensors`，offset=0。
- `quant_model_weights-00089-of-00181.safetensors`，offset=0。

这恰好解释了旧扫描的全部非有限值计数。旧 README 里的“坏块在 layer13/16/40/43 的专家，不在注意力矩阵”，不能用来概括全部 333 个差异块；那里列出的少数无法恢复块与整个损坏集合被混在了一起。

本次服务的保存挂载来源就是这个 `/data_lib/data/models/glm-q`，未启用 9/28 的逐块恢复外挂。MTP 层即使与参考一致，也不能保证草稿正确：实际 `GlmMoeDsaForCausalLMNextN` 继承 DeepSeek NextN，草稿前向明确输入主模型的 `previous_hidden_states`，再经 `hnorm` 和 `eh_proj`，主模型异常可以传入草稿。

**这里已确认磁盘 checkpoint 的数值损坏；还没有直接导出服务当前 NPU 内存中的张量或 logits，因此不能把“损坏造成所有循环/所有高 AL”写成已完成的因果验证。** 但它已经使“当前模型数值正常”这一基线假设失效。两条短中文问答正常，只证明这两条输出可读。

实际镜像的 NaN 检查开关 `SGLANG_ENABLE_ASYNC_ASSERT` 和修正开关 `SGLANG_SANITIZE_NAN_LOGITS` 默认都是 False，当前保存启动脚本没有打开它们。没有 NaN 报错日志并不等于没有异常数值。后续诊断应该让异常暴露；把 NaN 改成有限值不能算恢复了原模型。

## 6. 接受率实现与参考口径不能混用

对实际镜像 `sha256:440300a5…f26317` 的验证源码检查发现：

- NPU 分支直接取 target logits 的 argmax，调用 NPU 贪心验证内核；三位依次相等才接受，首个不相等后停止。topk=1 的当前线性草稿配置符合这段内核用途。
- 本轮 temperature=0 与这个分支一致。调高 temperature 也不会让该 NPU 验证自动转成 GPU 上的概率推测采样；因此“调温度把 AL 压到 2”不是可靠的隔离方法。
- 模拟接受率开关 `SGLANG_SIMULATE_ACC_LEN` 默认 -1；保存的启动配置未设置它，未发现显式强制满接受的证据。
- 已保存请求的直方图和 verify/correct/proposed/output 计数相互一致。它只能排除已检查的汇总算术错误，不能代替独立计算 target logits、验证 mask/KV 正确性。

源文件副本与 SHA 见 [source/PROVENANCE.json](causal_review_20261012/source/PROVENANCE.json)。

`docs/MTP.md` 没给参考模型版本、checkpoint、采样策略及位置概率定义。如果 `0.498/0.345/0.267` 是与本次相同的**无条件**位置率，则：

```text
AL ≈ 1+0.498+0.345+0.267 = 2.110
草稿接受率 ≈ (0.498+0.345+0.267)/3 = 0.370
另一组 AL ≈ 1+0.148+0.093+0.056 = 1.297
```

如果三者是**条件**位置率，第一组则对应 `1+0.498+0.498×0.345+0.498×0.345×0.267=1.71568327`。历史对话给出的“约1.7”使用了另一种解释，不能与本次的无条件率混用。材料同时说“AL低点接近0”，也提示其中可能有只计草稿、其他分母或其他统计窗口；通常每轮提交量包含主模型 token 时不能把接近0当作正常长请求的平均推进量。

因此参考 2.11 可用于提出核对问题，不能作为“任何 GLM、任何输入都应该 AL=2”的算法恒定值。DP/Graph 等配置不同可以影响性能和数值路径，但仅列出配置差异不能证明它们导致接受率偏高。

## 7. 还存在独立的推理等价性问题

重新比较历史完整配对请求的原始 output_ids，与旧 CSV 的首次差异位置一致：

| 同输入、temperature=0 的完整 OFF/ON 配对 | 输出不同的请求 | 首次差异位置，从0开始 |
|---|---:|---|
| 8K/1K | 4/5 | 四条都在1，即第2个token |
| 前缀32K/300 | 16/16 | 1～17 |

这值得比“AL是否接近2”更早检查。正确的贪心推测解码应按同一主模型决策推进；实际并行、量化和不同算子路径也可能因舍入及近似改变 argmax。历史 OFF/ON 又在不同节点，所以现有差异不能单独证明验证器错误。

需要在首个分歧点固定相同输入前缀，独立比较常规 decode 与 target verify 的 logits、argmax 及第一/第二名差距，再排查 attention mask、position、KV 和量化路径。仅比较两条已经分叉的长回复的总体质量，不能定位第一次分歧。

## 8. 后续实验顺序应当改变

1. **先恢复可信权重基线。** 获取可信源副本或验证过的原始字节，核实上述注意力张量及受影响块；不能继续把目前 checkpoint 当正常 GLM 的接受率基准。全模型与源校验属于后续恢复步骤，本次未擅自换权重或重启。
2. **再验证执行是否正确。** 先做 hidden states/logits 的有限值检查，再比较同前缀的 target verify 与常规 forward。在当前只跑 MTP ON 的约束下，可以先做内部验证；正式开关等价性检查留待用户恢复 OFF 范围后执行。
3. **固定负载与业务验证都保留完整输入输出。** 团队要求的原生 random-ids 用于固定长度场景；完整聊天模板、允许 EOS 的代表性请求用于检查正常任务。两者分别解释各自输出上的接受率。强制输出长度的压测需报告循环和正常结束点之后的比例。
4. **最后与参考比较。** 对齐原始参考的 checkpoint、输入、EOS、采样、MTP参数、位置率定义及统计窗口，再讨论残余差异，不挑种子或换输入去凑 AL=2。

重新读历史对话和 `lastmeet.txt` 后，应撤回“随机输入的接受率没有意义”“真实文本必然降到2”“只要换random-ids就已找到根因”“DP attention/Graph差异已经解释接受率”等确定性说法。会议原话是“随机产生的也行”，并提出与 B300 测量比较；没有建立普遍的 AL=2 正确性判据。

当前能够交付的定位是：**历史近满接受有循环输出的直接证据；本次仍测到了循环和大量 EOS 后续写；当前注意力权重有已确认的数值损坏；计数算术未发现造高证据；验证路径是否完全正确、各因素贡献多少仍需在可信权重上隔离。** 这解释了为什么反复换“random/real”一直不能解决问题。
