# Q4 实验方案（v1 定稿）

目标：搞清楚 **EPLB 为什么变烂**，并验证 **冗余专家能不能修好**；同时拿到干净的
TTFT / TPOT / E2E 性能数字，以及"每个周期"的专家热度数据（PD 分开统计）。

> **这是任务 3 + 任务 4 的联合实验**：
> - 任务 3（PD 共置 + 热力采集 + 经典指标）：A 组给出 PD 共置的正式性能数字与逐周期热力；
> - 任务 4（EPLB 负优化归因 + 解法）：A/B/C 三组对比给出归因证据与冗余专家的验证。
> 一份数据，两个交付。

---

## 一、跑哪几组（4 组 × 2 种负载）

| 组 | EPLB | 记录器（采集） | 作用 |
|---|---|---|---|
| **A0** | 关 | **关** | **纯性能基线**（完全不受采集影响） |
| A | 关 | 开 | 热力基线；用来算"采集到底值多少秒" |
| B | 开 | 开 | 负优化的主证据 |
| C | 开 + 冗余 64 | 开 | 解法验证 |

4 组 × 2 负载 = 8 轮。**先跑 agentX 的 4 轮**，random 的 4 轮随后补。

---

## 二、负载

| 负载 | 参数 | 说明 |
|---|---|---|
| agentX | 输入 16384 / 输出 512 | 和上一轮完全一样，可直接对比 |
| random | 输入 8192 / 输出 64 | 长 prefill 短输出；token 是均匀随机的 |

要求：**固定数据集切片 + 固定请求顺序 + 固定并发**，4 组必须完全一致（否则不可比）。

---

## 三、每组收什么数据

1. **经典指标**：TTFT / TPOT / E2E（p50/p95）+ 排队时间。
   来源：服务端 `/metrics`（`queue_time` / `time_to_first_token` / `inter_token_latency` /
   `e2e_request_latency`），每 60 秒抓一次存原文。
   ⚠️ 注意：`TTFT` 已经包含排队时间，不要再加一次（上次"其他占 25%"很可能就是这个）。
2. **每个周期的热度矩阵**（三个层次，都要）：
   - 逻辑专家热力 `[层 × 256专家]`
   - 物理专家热力（开 EPLB / 冗余时不同，**必须单独存**）
   - rank 热力（= 每张卡上的物理槽加起来）
3. **PD 分开**：上面每一项都要 **prefill / decode / 合计** 三份。
   ⚠️ 两个阶段差 3 个数量级（prefill 一步几万个 token，decode 一步几十个），
   统计必须按 token 数加权，**不能按"步"平均**。
4. **映射**：每个周期生效的正向（physical→logical）+ 反向（logical→physical）；
   每次重排**前后各存一份**。没有反向表，冗余组就没法分析。
5. **重排事件**：时间、耗时（**分开记**："写窗口用多久" vs "搬权重用多久"）、改了哪些层。
6. **机器状态**：`npu-smi`（显存/利用率）每 60 秒一次；metrics 里的
   `num_retracted_reqs`（KV 不够被抢占）、`cache_hit_rate`、`num_running_reqs`。

## 四、为什么要 A0（最重要的一条）

上一轮我们自己的采集，**让服务停了约 58 秒 / 600 秒（≈10%）**：

```
00:15:21  2.7s     00:21:08  6.9s
00:16:21  0.5s     00:22:09  0.7s
00:17:57 36.0s     00:23:10  0.5s
00:19:01  3.8s     00:24:16  6.6s
00:20:02  0.4s     00:25:17  0.4s     合计 ≈ 58s
```

所以：**性能数字以 A0 为准**；A0 与 A 的差值 = 采集的代价。
另外，B/C 组改为**只在重排时落盘**（这本来就是 EPLB 自己会做的事）→ 我们的额外开销≈0，
B/C 的性能数字也就干净了。

## 五、周期怎么切、数据怎么拼

- **周期 = 两次重排之间**（开始-[周期1]-重排1-[周期2]-重排2-[周期3]…）
- 实测：共置服务里 **2000 步 ≈ 2.9 分钟**（decode 步占绝大多数）。
  → 15 分钟 ≈ 5 个周期。
- 记录器在每次重排时会 **reset**，而 EPLB 在重排时**自己会 dump 一次**
  → 所以"重排时的这份数据"正好 = 一个完整周期，不会丢。
- 把 `--expert-distribution-recorder-buffer-size` 从 1024 调到 **2000**
  （= 一个周期正好装得下）。
- 每个窗口额外记 `iteration_index / since_last_rebalance / rebalance_id`
  → 事后拼周期不用靠时间戳猜。
- "周期1、周期1+2、…全部之和"这种增量统计：直接把这些周期的矩阵相加即可。

⚠️ 注意：**prefill 阶段的步数很少**（一个 prompt 块只算 1 步，decode 每个 token 算 1 步）
→ 纯 prefill 负载几乎不会触发重排。所以要有足够多的 decode 步数才会有重排，
"长 prefill 短输出"时周期会变长变少。

## 六、时间与顺序

```
每轮 ≈ 4 分钟起服务 + 15 分钟负载 + 1 分钟收尾 = 20 分钟
agentX 4 组 ≈ 80 分钟 ；random 4 组 ≈ 80 分钟
```
- 起服务后先跑 2~3 分钟做预热，**预热段不计入统计**；
- 顺序：A0 → A → B → C（先 agentX，再 random）；
- 时间允许的话，最后再补一次 A0（检查机器漂移）。

---

## 七、自检与预期结果

**自检（最重要）**：A / B / C 三组的**逻辑专家热力必须一致**（同一份请求流、
路由不受摆放影响）。不一致 = 有 bug，先修再往下做。

| 组 | rank 负载 max/mean（预期） | 其他 |
|---|---|---|
| A0 / A | 1.3 ~ 1.5× | 无重排（A0 无数据） |
| B | ≈ 5.5× | 每层最热专家落 rank0 的层 ≥90% |
| C | ≈ 1.2× | 物理槽 320、每卡 5 槽；KV 变小 |

**random 负载的意义**：如果 random 没有明显热点，那 EPLB 就不该出现负优化
→ 这是对我们机制的**正面证伪/证实**实验。

**要小心的坑**：
- C 组专家权重 +25% → KV cache 变小 → 可能出现"抢占"（`num_retracted_reqs` 上升）。
  这个差异要单独说明，**不能算成 EPLB 的收益**。
- `/home` 只剩 21G，窗口文件 45MB/个（buffer 调大后更大）→ 数据落 `/data_lib`。
