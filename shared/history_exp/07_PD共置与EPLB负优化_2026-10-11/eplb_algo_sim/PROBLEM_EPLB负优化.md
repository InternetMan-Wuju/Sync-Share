# 问题陈述：MoE 专家并行下，开了 EPLB 反而更不均衡（实测 ≈1.34× → ≈5.62×）

> 这是一份自包含的问题描述，可以直接给别的模型/人看。
> 每一处都标注了【实测】【代码事实】【仿真】。

---

## 1. 部署与符号

* 模型：MoE 大模型（GLM-5.2 架构），**78 层**，每层 **256 个路由专家**，每个 token 选 top-8。
* 部署：4 台机器，共 **64 张卡**，**EP64**（专家并行 64 路）。每张卡（= 一个 EP rank）放 **4 个专家槽**：
  64 rank × 4 槽 = **256 个物理槽**。
* **物理槽 → rank 的映射【代码事实】**：槽 `p` 属于 `rank = p // 4`（rank-major，连续）。即 rank 0 拥有槽 0~3，rank 1 拥有槽 4~7，依此类推。
* **初始布局（不开 EPLB）【代码事实】**：槽 `p` 直接装逻辑专家 `p`（identity）。
  于是 rank r 装的是**连续的** 4 个专家 `{4r, 4r+1, 4r+2, 4r+3}`。
* **统计量**：在一次测试（600s、并发 8）里，逐步累计每个 (层, 专家) 被路由到的 **token 数**，
  得到热度矩阵 **W[78, 256]**（W[l][e] = 第 l 层专家 e 的 token 数）。
* **rank 负载** = 该 rank 的 4 个槽所装的 4 个专家在**所有层**上的 token 数之**和**。
* **指标**：`max_rank(负载) / mean_rank(负载)`（=1.0 表示完美均衡）。下面所有 "×" 都是这个比值。

---

## 2. 现象【实测】

同一套服务、同一份负载，只切换 EPLB 开/关：

| | rank 负载 max/mean | "每层最热专家落在 rank 0" 的层占比 |
|---|---|---|
| **不开 EPLB**（初始布局，identity） | **1.34×** | **0%**（0 / 150 个非空层） |
| **开 EPLB**（自动重排 2 次之后） | **5.62×** | **91%**（341 / 375 个非空层） |

开 EPLB 后**每 rank 负载（按 rank 编号 0→63）单调下降**：

```
rank:      0     1     2     3     4     5     6     7    ...    63
负载/均值: 5.62  3.97  3.13  2.66  2.24  1.96  1.75  1.66  ...   0.57
```

也就是说：**前几个 rank 被压满了，后面的 rank 反而很闲**。
（另一套口径下这两组数是 1.48× 与 6.16×，趋势一致。）

---

## 3. 为什么"单层"注定是歪的：物理下限【实测】

对每一层，取"最热专家的 token 数 ÷ 该层每 rank 平均 token 数"：

* 全 78 层的中位数 = **6.90 倍**，最大 ≈ **8.0 倍**。

原因很简单：**当冗余专家 = 0 时，每个逻辑专家只能占 1 个物理槽**，
所以那个最热的专家**只能待在某一个 rank 上**，它一个人就顶 6.9 个 rank 的平均量。
→ **任何摆放算法都不可能让"单层"的 max/mean 低于 ≈7×。这是物理下限。**

---

## 4. 那为什么"不开 EPLB"时总量反而是均衡的？

因为**跨层抵消**：不开 EPLB 时，每一层的最热专家是**不同的专家编号**，
分布在 256 个槽里 → 它们的 rank 也**散布在 64 个 rank 上**（实测：0% 落在 rank 0，基本均匀分布）。
于是"某一层把 rank 37 压重了"，另一层又把 rank 12 压重了，**加起来互相抵消** → 合计 1.34×。

---

## 5. 现行 EPLB 算法【代码事实】

服务用 `--eplb-algorithm auto`，在这个模型上（`n_group=1`，`nnodes=4`，`1 % 4 ≠ 0`）自动选中的是
**`deepseek`（非层级版）**。它的核心（`balanced_packing`）是：

```
对每一层 独立地：
    把这一层的 256 个专家按热度【从高到低】排序
    依次"发牌"：每张牌发给"当前总负载最轻、且还没装满"的包
                 （每个包 = 一个 rank，容量 = 每 rank 槽数 = 4）
                 （平局取编号最小的包）
```

另一个变体 `deepseek_vec` 是"排序 → 排成 (槽 × rank) 矩阵 → **奇数行反转（蛇形）** → 每列给一个 rank"。
**注意：蛇形只反转奇数行（第 1、3 行），第 0 行不反转 → 最热那个还是进 rank 0。**

```
逐层独立 + 每层都从"空包"开始 + 平局取最小编号
   ⇒ 每一层的第一个（最热）专家必然进 pack 0 = rank 0
   ⇒ 所有层的尖峰全部对齐到同一列
   ⇒ 跨层抵消消失
```

---

## 5.1 【已专门验证】EPLB 确实是"逐层独立"的

同一个问题经常被质疑："会不会其实层之间是有耦合的？"——我们专门验证过，**确实是逐层独立**。

**(a) 代码证据**：所有排序/求和/取最大都发生在**专家轴（dim=-1）**，层只是 batch 轴；每层的贪心状态在进入该层时**重新初始化**：

| 位置 | 关键代码 | 说明 |
|---|---|---|
| `balanced_packing`（deepseek） | `for i in range(num_layers): pack_weights=[0]*num_packs; pack_items=[0]*num_packs` | 每层开头清零，层间不共享负载 |
| `replicate_experts` | `logcnt` 形状 `[layers, experts]`；`(weight/logcnt).max(dim=-1)` | argmax 只在层内专家轴 |
| `deepseek_vec` | `score.argsort(-1)`、`indices[:,:,1::2,:].flip(-1)` | 排序/翻转都在层内 |
| ↑ 的 `values.sum(0)` / `tokens_per_expert.sum(0)` | 这里是 **step（时间）轴**，不是层轴 | 易被误读为跨层 |
| `pack_groups`（层级版） | `for layer in range(num_layers): node_tokens=[0]*num_nodes` | 同样每层清零 |
| `EPLBManager` / `expert_location_updater` | `for layer_id in update_layer_ids:` | 权重搬运也逐层做 |

唯一的全局量是 `average_utilization_rate_over_window`（配阈值 `eplb_min_rebalancing_utilization_threshold`），它只决定**这一轮要不要重排**，不参与"每层怎么摆"。

**(b) 操作性验证**（不靠读代码）：同一份数据三种跑法，逐层比对摆放结果 ——
A) L 层一起跑；B) 每次只喂 1 层、跑 L 次；C) 把 L 层打乱顺序再一起跑。

结果（真实 dump 数据 + 随机数据，各 5 条算法路径）：

| 算法路径 | 单层逐跑 | 打乱层序 |
|---|---|---|
| `deepseek`（实际跑的） | ✅ 逐层完全一致 | ✅ 逐层完全一致 |
| `deepseek hierarchical` | ✅ | ✅ |
| `deepseek_vec` | ✅ | ✅ |
| `deepseek_vec` 冗余=64 | ✅ | ✅ |
| `deepseek_vec hierarchical`（`pack_groups` 路径） | ✅ | ✅ |

即：**逐层单独跑 = 一起跑 = 打乱层序跑，每一行摆放结果一个数都不差** ⇒ 层间零耦合。
（脚本：`verify_layer_independence.py`）

**精确表述**：EPLB 的**摆放决策**逐层独立；计数是按 (层, 专家) 在窗口内累计、并对**时间轴**求和。
所以问题的根子可以写得很干净：

> 目标函数是「所有层求和**之后**」的最大 rank 负载，
> 而算法优化的是「每层各自」的最大 rank 负载 —— 两者不等价。
> 逐层独立 + 每层都从空包/rank 0 开始 ⇒ 每层尖峰对齐到同一列 ⇒ 跨层抵消消失。

## 6. 用 stock 算法在同一份真实数据上复算【仿真】

把实测的 W[78, 256] 直接喂给官方算法代码：

| 算法 | 合计 rank 负载 max/mean |
|---|---|
| `deepseek`（我们实际跑的，逐层贪心） | **6.32×** |
| `deepseek_vec`（带蛇形） | 6.46× |
| `deepseek_vec`（**去掉**蛇形） | 6.61× |
| 冗余专家 R=64（同算法） | **1.37×** |
| 冗余专家 R=128（同算法） | 1.08× |
| 参照：初始布局（identity，不开 EPLB） | 1.50× |

**加冗余专家有效**（把热专家复制成多份，拆开分给不同 rank → 单层下限被打掉）。
但注意 EP64 的硬约束：**`(256 + R) % 64 == 0` ⇒ R 最小是 64**（R=16 非法）。

## 7. 抽象成算法问题

```
输入:  W[L, E]        热图 (L=78 层, E=256 专家)，非负实数
       R = 64         rank 数
       k = E / R = 4  每个 rank 的槽数
约束:  摆放是一个双射 φ : {0..E-1} 个槽 → {0..E-1} 个专家
       （冗余 = 0：每个专家恰好占 1 个槽）
       rank r = 槽 {k·r, ..., k·r + k-1}  ← 槽到 rank 的映射固定
目标:  最小化  max_r ( Σ_l Σ_{p ∈ rank r} W[l, φ(p)] )  /  mean
```

**现行做法**：把 L 个子问题**独立**求解（每层各自最小化自己的不均衡）。
这等于优化了 L 个**单层**代理目标，而**完全忽略了跨层的和** ——
而最终指标恰恰是"跨层求和之后"的最大值。

**最小反例（4 rank / 每 rank 2 槽 / 8 专家 / 2 层）**：

```
层A 热度 = [100, 20, 10, 5, 1, 1, 1, 1]     (热点是专家 0)
层B 热度 = [1, 1, 1, 1, 5, 10, 20, 100]     (同一组数值，热点是专家 7)

① 不开 EPLB（槽 p 装专家 p）
     层A 负载 = [120, 15,  2,  2]   单层 3.45×
     层B 负载 = [  2,  2, 15, 120]   单层 3.45×
     合计     = [122, 17, 17, 122]  →  1.76×   ✅ 两层歪的方向相反，抵消了

② 开 EPLB（逐层独立，每层最热进 rank 0）
     层A 负载 = [101, 21, 11,  6]
     层B 负载 = [101, 21, 11,  6]
     合计     = [202, 42, 22, 12]  →  2.91×   ❌ 歪的方向被对齐，抵消消失
```

（可运行脚本：`demo_eplb_matrix.py`（上面的最小例）、`demo_eplb_random.py`（随机 4 层 × 32 专家、逐层分解成子矩阵并标注所属 rank）。）

## 8. 想请教的问题

1. **冗余 = 0 的前提下，是否存在确定性算法能把 5.6× 拉到 2× 以内？**
   （例如：既然每层最热只能待在一个 rank，能不能靠"让各层的最热落在**不同** rank"来重新制造抵消？）
2. 如果做**跨层联合优化**（把 78 行放在一起，最小化 `max_r Σ_l`），
   有什么可用的算法？（整数规划？贪心+局部搜索？拉格朗日？分层聚类？）
   规模 78×256、64 个包、每包 4 槽，**在服务器上几百毫秒内算完**是硬要求（要能在线跑）。
3. **"逐层贪心 + 轮换起点"**（第 l 层从 rank `l mod 64` 开始发牌，别都从 rank 0 开始）
   这种最小改动值多少？有没有理论保证/上界？
4. 有没有可能"逐层独立"是设计者有意的取舍（比如权重搬运成本、跨 rank 通信拓扑的约束）？
   有没有我漏掉的约束（例如：深层/浅层的专家不能随便换、rank 内 4 个槽有顺序要求等）？
5. 有没有相关文献/已知做法（EPLB、DeepSeek 的 eplb.py、MegaBlocks、各种 expert placement / 
   load-balancing 论文）讨论过"逐层独立 vs 跨层联合"这件事？EPLB 的 `balanced_packing` 为什么是逐层的？

## 附：证据与可复现性

* 数据：4 机 EP64（`--tp-size 64 --dp-size 4 --ep-size 64 --enable-dp-attention`）
  + EPLB（`--eplb-rebalance-num-iterations 2000`），agentX 裁剪数据集（16K 输入 / 512 输出），并发 8，600s。
  每 60s 以及每次自动重排时 dump 一份热度窗口（含该窗口生效的 `physical_to_logical_map`）。
* 逐层/逐 rank 的统计、每 rank 负载、单层下限，都是从窗口数据里直接算出来的（纯 CPU）。
* 算法代码是从镜像里原样取出的 stock 版本（`deepseek.py` / `deepseek_vec.py`），仿真时未做任何修改。
* 上述"实测"和"仿真"两条链路互相独立，结论一致：**EPLB 逐层独立 + 每层从 rank 0 开始 → 尖峰对齐 → 合计更歪。**
