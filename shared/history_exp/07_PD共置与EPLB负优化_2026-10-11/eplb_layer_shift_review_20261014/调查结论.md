# EPLB 层间偏移调查：累计均衡能否减少逐层等待？

2026-10-14，调查节点 `npu1-23`。全程只使用 CPU：读取历史记录、从已停止容器复制源码、检索公开资料、离线复算。没有启动推理服务，没有使用 NPU；所有新增文件均在 `/home/chengyetai/workspace` 内。

**结论：你的核心判断成立，但需要限定。** “整层 rank 偏移”是你提出的待验证设想，不是已有实现或真机实验结论。本次在 CPU 上构造这个对照：它能明显改善跨层累计 rank 负载，却严格保持每一步、每一层的 rank 负载集合和峰值不变。在当前主要按层推进的批次执行方式下，这种变化不能直接消除每层热点造成的等待。它是否还有通信、争用等方面的实际收益，尚没有性能实验给出答案。

之前报告把“跨层累计最大 rank 负载”称为真实优化目标，并据此把 EPLB 逐层独立视为性能退化根因，这一步需要修正。逐层独立、热点被放到 rank 0 的代码事实仍成立；从这些事实推出“逐层执行一定变慢”则证据不足。

**为什么跨层抵消不等于等待抵消。** 令 `H[s,l,r]` 为某个 forward 记录 s、第 l 层、rank r 的专家计算量。原报告主要计算的是：

```
累计均衡指标 A = max_r Σ_(s,l) H[s,l,r] / mean_r Σ_(s,l) H[s,l,r]
```

对逐层执行、同类设备、专家计算时间近似随 token 数变化的简化模型，更相关的是：

```
专家计算瓶颈代理 C = Σ_(s,l) max_r H[s,l,r]
归一化瓶颈指标 B = C / Σ_(s,l) mean_r H[s,l,r]
```

`max(求和)` 与 `求和(max)` 不相同。层间偏移是每一行上的 rank 置换 `π_l`，因此对每条记录都有 `max_r H[s,l,π_l(r)] = max_r H[s,l,r]`。A 可以下降，C 与 B 不变。这个性质不需要“层内负载近似降序”成立。

例如两张卡、两层：偏移前各层负载都是 `[100,10]`，累计为 `[200,20]`；偏移后变成 `[100,10]`、`[10,100]`，累计为 `[110,110]`。累计完全均衡，但按层等待的计算时间仍为 `100+100=200`；第二层多出来的空闲不能回填第一层已经发生的等待。

这里的 C、B 是**计算量代理，绝不是测得的毫秒延迟或吞吐倍数**。真实执行还受 GEMM 的非线性、小 batch 开销、dispatch/combine、attention、通信拓扑与交叠影响。层依赖本身也不等于每层都有一个显式全局 barrier；需要结合实际执行路径判断各 rank 能提前多少。

**23 节点上的执行证据。** 历史 `B_agentx` 服务日志记录了 `pp_size=1`、`enable_two_batch_overlap=False`、`enable_single_batch_overlap=False`、`enable_mixed_chunk=False`、`enable_pdmux=False`。`disable_overlap_schedule=False` 表示启用了调度交叠，不能据此认定不同 batch 的 MoE 层已经在设备上交错执行。启动脚本确有 NPU 多 stream 设置，也不能由此推导任意跨层专家计算可以重叠。

模型配置是 `GlmMoeDsaForCausalLM`，78 层、前 3 层 dense、每个 MoE 层 256 专家、top-8。同镜像标签的源码显示，该模型继承 DeepSeek 的执行路径；常规路径逐层把上一层的 `hidden_states` 传给下一层。专家执行遵循 `dispatch → run_moe_core → combine`。历史实际挂载的 DeepEP 补丁中，normal 模式在异步完成时等待 event，low-latency combine 调用接收 hook 或 `event.current_stream_wait()`；下一层不能消费尚未回传的专家结果。

这支持“当前层热点仍会挡住后续依赖它的计算”的判断。没有证据表明当时存在一个能让其他 rank 用下一层专家工作补足当前层空闲的通用调度机制。

**CPU 复算结果。** 读取 Q4 的 A/B/C × agentX/random 六轮数据，共 45 个非空窗口。使用原实验保存的 stock `deepseek.py`，在每个窗口拟合摆放，再用该窗口逐条记录评估。偏移以**整个 rank 的专家块**为单位：第 l 层的 64 个 rank 块循环移动 `l mod 64`，块内专家组合不变。

下表使用 `B_agentx` 的同一份逻辑热度。合计沿用原采集审计的 `prefill + decode/8` 修正；A 跨层跨记录累计，B 则先逐记录逐层取最大值再求和。它们都由记录推算，不是真机偏移实验。

| 离线构造的布局 | 累计均衡 A，越小越好 | 逐记录逐层瓶颈 B，越小越好 |
|---|---:|---:|
| identity，不重排 | 1.455 | 7.123 |
| stock EPLB，每层独立 | 6.147 | 6.366 |
| stock + 整层 rank 循环偏移 | **1.304** | **6.366，完全相同** |
| stock + 按累计负载安排各层 rank 置换 | **1.069** | **6.366，完全相同** |
| stock + 按物理槽偏移，改变 rank 内专家组合 | 1.936 | 6.495 |
| stock + 64 个冗余槽，假设副本均分流量 | 1.063 | 1.436 |

不仅总体比值相同：对六轮数据的 **3,436,574 个非空“记录×层”样本**，程序检查了整层偏移和累计优化置换前后的 rank 负载排序及最大值，均逐项完全一致。这里称“记录”，因为部分窗口的计数张量行数与时间戳条数存在差异，不能把每一行无条件视作一条精确对齐的硬件时间记录；该差异不影响置换不变性。

再用前一个窗口拟合、下一个窗口评估，避免同窗口拟合带来的乐观偏差：agentX 的累计指标从 **6.141 → 1.317**，瓶颈指标仍为 **6.374 → 6.374**。random 对照同样成立。

这些结果还有两点含义。第一，identity 的累计值虽然好，但在同一份热度上，stock 的逐层瓶颈代理实际更低，不能因为 stock 的累计 A 更差就认为它的逐层装箱更差。第二，如果偏移单位是**一个专家槽**而不是整个 rank 块，分组会改变，峰值也可能改变；本次这种槽偏移反而使 agentX 的 B 从 6.366 增到 6.495。不能把两类偏移混在一起。

**旧实验的吞吐下降还不能归因于热点对齐。** 原始 bench summary 中，A0→B 吞吐为 agentX `90.930→86.520 tok/s`，下降约 **4.85%**；random `43.979→41.303`，下降约 **6.08%**。B 的日志重排耗时合计分别约 **50.39s** 和 **48.75s**，占实际 bench wall time 的 **5.32%** 和 **5.39%**。这些计时包括 recorder dump、布局计算、权重更新与同步等操作；不能把日志耗时直接当作精确的全服务停顿时间，但它们已是同量级的重要混杂因素。

旧报告“每步都在等最热卡，所以吞吐下降 4%/7%”的归因超出了已有证据。还需要把重排开销与稳态 forward 时间分开。TPOT 中位数也没有显示同等比例的恶化，A0/B 的 agentX 为 50.3/50.0ms、random 为 50.2/49.8ms。有限样本和不同运行的 batch/cache 状态也限制了因果判断。

**冗余专家为何与整层偏移不同。** 无冗余时，单个热专家只能由一个 rank 承担，单层峰值至少不小于该专家的工作量。置换只能移动它。复制并把流量分给多份副本才能降低这个下限。EP64、256 个原始专家、均匀槽数的当前实现要求 `(256+R) % 64 == 0`，因此最小非零冗余槽数是 64，对专家权重存储增加 25%。

但本表的冗余结果是假设副本均匀分流的估计，逻辑计数不足以恢复真实副本负载。它也不保证每个阶段改善：在 random decode 上，这次同窗口拟合的冗余 B 为 7.276，stock 为 7.274，几乎相同；prefill 主导的统计和小 batch 离散路由会影响效果。不能把合计累计均衡或 prefill 的收益推广到 decode。

本次计算对每个布局执行负载守恒检查，冗余时除以副本数。早期 [walkforward_stale_snapshot.py](/home/chengyetai/workspace/current_exp/eplb_algo_sim/walkforward_stale_snapshot.py:53) 的 `load_of` 未除副本数；其冗余数值不能与本次守恒口径直接比较。后来的 Q4 `phys_heat` 已有均分处理。

**哪些情况下层间偏移仍可能有收益。** 如果多个独立 microbatch 的不同层真正同时争用同一组设备，或 rank/node 的通信成本不同，或存在 attention/共享专家交叠、其他服务争用，整层置换可能改变真实瓶颈。跨节点 rank 移动也会改变本地/远端流量、链路拥塞与拓扑成本。此时需要看同时在执行的工作及通信图，不能只看全模型累计 token 数；仅开启 TBO 或 PP 也不自动证明累计 A 是正确的性能目标。

当前证据足以支持：**整层 rank 偏移不能单独解决层内热点等待；若期待性能提升，需要找到它实际减少了哪项同时发生的计算或通信成本。** 不能据此声称它在所有执行模式下都没有价值。

如果未来允许做性能实验，最直接的对照是冻结三种布局：identity、stock、stock 的整层 rank 偏移。统一模型、batch、KV/cache、采集设置，关闭周期重排后比较稳态表现，prefill/decode 分开；记录每层专家 kernel、dispatch/combine 与等待时间，区分节点内和跨节点偏移。当前按要求只做 CPU 调查，此实验没有运行。

**公开资料与本地发现相符。** [DeepSeek EPLB 官方 README](https://github.com/deepseek-ai/EPLB) 将方法描述为复制热专家后装箱，不只是重排；[SGLang 大规模 EP 文章](https://lmsys.org/blog/2025-05-05-large-scale-ep/#expert-parallelism-load-balancer) 明确把 balancedness 定义为 **a MoE layer** 上各 GPU 的平均/最大计算时间，支持按层考察瓶颈。[SGLang EP 文档](https://docs.sglang.ai/advanced_features/expert_parallelism.html) 说明 TBO 是 microbatch 交错，而 SBO 是同 batch 内的计算通信交叠。[DeepEP 官方 README](https://github.com/deepseek-ai/DeepEP) 的示例也要求在消费 dispatch/combine 结果前等待完成。
