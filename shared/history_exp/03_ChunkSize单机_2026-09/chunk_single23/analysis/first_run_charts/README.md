# 第一次单机 Chunk Size 实验：经典指标可视化与缺口

分析对象：2026-09-26 的 23 节点 `chunk_single23/results/20260926_145836/`，比较 Chunk=8192 与 1024。原始输入是固定种子的随机 `input_ids`；主场景总输入 54,614 token，其中公共前缀 32,768 token、输出 300 token。每个 Chunk 的完整矩阵加冒烟共 **10 条测量请求**：6 条长请求、4 条背景 Decode；不含每轮 flush 和前缀预热。负载设 `ignore_eos=True`，故“全部达到指定输出长度”只能说明请求完成，不能说明回复正常。

分析脚本：[plot_first_run.py](plot_first_run.py)。只读取存档的 `smoke.jsonl`、`full.jsonl`、`metrics_timeline.jsonl`，不请求在线服务。派生数据见 [per_request.csv](per_request.csv) 和 [short_windows.csv](short_windows.csv)；历史口径见[原实验报告](../../doc/ChunkSize单机实验_2026-09-26.md)。每个散点是一条请求/一个短测量窗口；图中蓝色为 8192、橙色为 1024。同一场景仅 1–2 条请求，**不把两个点画成可信的 P95/P99**。

## 已画出的图

1. [TTFT、TPOT、E2E](01_latency.png)：分别展示 54.6K 冷、54.6K 暖独立、54.6K 暖加背景 Decode、32K/16K 暖、Decode 单独/混合。E2E 堆叠部分只有客户端能直接拆出的 `TTFT` 和“首 token 后直至结束”；短横线标示单条请求 E2E。
2. [输入速率近似值、Decode 速度、短窗口吞吐](02_rates_and_short_windows.png)：第一格是 `(prompt_tokens-cached_tokens)/TTFT`，**不是服务端纯 Prefill 速度**；第二格是 `1000/TPOT`。下两格为实验中仅 1 或 2 条请求的活动窗口内 `输出 token/窗口秒数` 与 `请求数/窗口秒数`，**不是稳定并发容量**。前缀预热和 flush 不计入窗口。
3. [Decode 客户端 ITL 与注入前后](03_client_itl_decode_interference.png)：逐条请求的最大 SSE 输出间隔和请求内 P99，以及首轮背景 Decode 在长请求注入附近的单次输出间隔。SSE `completion_tokens` 在这里每个记录事件恰好增加 1，可以恢复**客户端看到的逐 token 到达间隔**；横坐标 0 为发起长请求时刻，间隔落在后一个输出 token 的到达时间。它不等于设备内部每步计算时间。
4. [实测前缀命中与 KV 池](04_cache_and_kv_context.png)：长请求的 `cached_tokens/prompt_tokens` 和长请求运行期间 rank0 每约 3 秒采样到的最小可用 KV token 数。冒烟请求期间没有对应的采样，图上故意不补一个 KV 数值。

## 最值得注意的读数

| 观测 | Chunk 8192 | Chunk 1024 | 含义与样本量 |
|---|---:|---:|---|
| 54.6K 冷态 TTFT | 21.98 s | 38.32 s | 各一条；尚未隔离服务端 Prefill 耗时。 |
| 54.6K 60% 命中暖态、独立请求 TTFT | 9.92 s | 19.12 s | 各一条冒烟。 |
| 54.6K 暖态加背景 Decode 的长请求 TTFT 中位数 | 11.55 s | 18.67 s | 各两条。 |
| Decode 单独运行的最大客户端 ITL | 0.615–0.632 s | 0.592–0.609 s | 各两条 900 输出请求。 |
| 注入长 Prefill 时的最大客户端 ITL | **6.976–7.008 s** | **15.596–17.821 s** | 各两条背景 Decode；大停顿出现在注入后前几个输出 token。 |
| 混合阶段两条请求的短窗口输出速率 | 2.694、2.717 tok/s | 2.690、2.697 tok/s | 分母覆盖一条 900 输出的 Decode 从开始到结束，每个窗口另有一条 300 输出的长请求；不代表饱和吞吐。 |

**新发现**：旧报告只给出了背景 Decode 平均 TPOT 的变化（大约几个百分点）。客户端 ITL 补图显示，在两次长 Prefill 注入后都出现**一次数秒到十几秒的输出停顿**。P99 ITL 仍大致为 0.54–0.57 s，因为每条请求有 899 个间隔，而这种极长停顿很少；这正是必须看最长停顿而不能只看平均 TPOT 或 P99 的原因。既然两组均 `enable_mixed_chunk=False`，该现象不能被解释成“1K 必然会在块间给 Decode 更多执行机会”；但这里只做了两轮，不能推断稳定的尾延迟分布。

## 对照《AlwaysNeed.md》的逐项结论

| 经典指标 | 这份历史数据能否画图 | 严格边界 / 欠缺的测量 |
|---|---|---|
| TTFT | **可以**：逐请求首输出时间 | 含请求排队、输入处理和首 token；每场景仅 1–2 次，不能做可靠的请求级 P95/P99。 |
| TPOT | **可以**：`(E2E-TTFT)/(输出数-1)` | 每条请求的均值掩盖单次输出停顿；需要与 ITL 图合看。 |
| ITL、最长输出停顿 | **可以画客户端观察值**：逐 SSE 事件时间，相邻 `completion_tokens` 在本批数据均增 1 | 缺服务端逐 token 或逐调度步时间戳；若将来 SSE 合批，这种逐 token 还原不再成立。两次重复不能当成稳定尾延迟分布。 |
| E2E 及 breakdown | **能画 E2E、TTFT 和首 token 后时长** | 缺排队、纯 Prefill、首步 Decode、网络传输分别耗时；不可把 TTFT 直接标为“Prefill 时间”。 |
| Prefill 速度 | **只能画输入未命中数 / TTFT 的代理值** | 已有 `cached_tokens`，但缺每请求的服务端 Prefill 开始/结束时间与实际计算步计时；3 秒级全局 `/metrics` 采样不能干净地归因给混合场景的某一条请求。 |
| Decode 速度 | **可以画客户端平均值**：每请求 `1000/TPOT` | 缺服务端瞬时生成速率和可稳定复现的高并发总 Decode 吞吐。 |
| 端到端吞吐（tok/s、req/s） | **可以画 1–2 请求短窗口比值** | 无持续、不同并发/到达速率的固定测量窗口；不具备稳定服务容量的 tok/s 或 req/s，也没有负载阶梯/饱和点。混合窗口含 1200 输出、纯 Decode 窗口含 900 输出，不能用两组窗口比值直接判断容量变化。 |

**附加缺失**：没有每个配置启动/切换后对真实中文提示词的语义验收，也没有保存原始自然语言回复；测试只发送随机 token ID 且强制输出目标长度。2026-09-27 的真实文本检查暴露了“健康检查通过但可能输出异常文本”的问题，且有权重读出异常的单独记录。不能将这些**后来**的发现倒推成“2026-09-26 每次加载必然异常”，也不能用这份早期性能图作为语义正确模型的正式结论。对照[语义验收要求](../../../../common/AlwaysNeed.md)和[异常记录](../../doc/模型回复异常与只读权重外挂恢复_2026-09-28.md)。

## 对正式补测的建议

先在 23 的每种 Chunk 启动后做真实提示词检查，保存模型来源及回复，再固定权重来源、镜像、负载和采样设置。延长每个条件的重复次数，在**持续 Decode 流**中注入长 Prefill，分别统计单请求的最大 ITL、P95/P99 ITL 及请求级 TTFT/TPOT 的分布。要测真实 Prefill 速度，增加每请求服务端排队、Prefill 开始/结束时间；要测服务总吞吐，增加不同稳定并发的长时间请求窗口并保留成功请求数和实际输出 token 数。原始 2026-09-26 图可用来理解现象和确定补测项，正式性能结论应来自通过语义验收的新轮次。
