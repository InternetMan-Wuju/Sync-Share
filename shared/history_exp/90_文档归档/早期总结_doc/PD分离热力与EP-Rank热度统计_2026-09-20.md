## 1. 这次完成了什么

上一次只根据一个 `expert_distribution.pt`，把 `logical_count[T, 78, 256]`
沿着 `T` 相加，得到 Layer×Logical Expert 热度。缺少两部分：

1. 没有把 Prefill（P）与 Decode（D）分开统计。
2. 没有根据 EPLB 的实际物理布局统计 EP-Rank 热度。

更重要的是，EPLB 每次 rebalance 会调用 recorder 的 `dump_record(output_mode="object")`，
随后重置 recorder。旧脚本只保存最后一次手工 dump，所以可能只有“最后一个 EPLB 窗口”，
不是整个实验。

这次做了以下改动：

- Prefill0、Prefill1、Decode 三个服务分别启动 recorder。
- 每次 EPLB 自动 dump 时都保存一个窗口 PT。
- 每个窗口同时保存该窗口实际使用的 `physical_to_logical_map`。
- 实验结束后再保存最后一个手工窗口。
- 每个窗口先按自己的布局换算 EP-Rank 热度，再把所有窗口相加。
- P 的两个独立 EP16 服务分别分析，最后再组合成完整 Prefill 热力。
- 生成 Layer×Expert、Layer×EP-Rank、Rank 总热度图及原始 CSV/JSON。

最终三档实验都通过了完整覆盖检查，不再是只看最后一个窗口。

## 2. 为什么旧方法不能直接算 EP-Rank

`logical_count` 的最后一维是 Logical Expert 0..255，不是物理卡或 EP Rank。

EPLB 会改变 Logical Expert 到 Physical Expert Slot 的摆放位置。假设某一层当前布局是：

```text
physical slot 0 -> logical expert 18
physical slot 1 -> logical expert 90
...
```

那么 physical slot 0 的热度应该读取 logical expert 18 的计数，而不能默认读取
logical expert 0。

旧 `analyze_expert_heat.py` 按 Expert ID 顺序直接分组到 Rank，相当于默认布局永远是
identity mapping。EPLB rebalance 以后这个假设不成立。

另外，不能把“最终布局”套到整个实验上。每次 rebalance 前后的布局不同，必须对每个窗口
使用它自己的布局。

## 3. 完整窗口是怎样保存的

修改文件：

- `/home/chengyetai/workspace/current_exp/patches/full_window/expert_distribution_full_window_patched.py`

关键行为：

1. 显式调用 `start_expert_distribution_record` 时，把窗口编号重置为 0。
2. EPLB 自动 dump 时保存：
   - `logical_count`
   - `physical_to_logical_map`
   - `full_window_dump_index`
   - `dump_timestamp`
   - `window_kind="eplb_rebalance"`
3. 实验结束手工 dump 时保存同样的信息，并标记：
   - `window_kind="manual_final"`
4. 自动窗口编号依次为 0、1、2……，最后手工窗口使用下一个编号。

完整覆盖必须同时满足：

- 每个窗口都内嵌物理布局。
- 每个窗口都有编号和时间戳。
- 编号严格等于 `0..N`，不能缺号或重复。
- 编号顺序与时间顺序一致。
- 最后一个窗口必须是 `manual_final`。
- 前面的窗口必须全部是 `eplb_rebalance`。

这些检查写在：

- `/home/chengyetai/workspace/current_exp/analyze_pd_rank_heat.py`

## 4. 热度是怎样计算的

### 4.1 Layer×Logical Expert

每个窗口的 recorder 数据形状是：

```text
logical_count[T, Layer, LogicalExpert]
```

对窗口内的 `T` 求和：

```text
window_layer_expert[layer, expert]
    = sum_t logical_count[t, layer, expert]
```

再把所有窗口相加：

```text
full_layer_expert = sum_window window_layer_expert
```

### 4.2 Layer×Physical EP-Rank

对每个窗口单独处理。设该窗口的映射为：

```text
map[layer, physical_slot] = logical_expert
```

物理槽位热度为：

```text
physical_heat[layer, physical_slot]
    = window_layer_expert[layer, map[layer, physical_slot]]
```

然后按每个 Rank 拥有的物理槽位求和：

```text
rank_heat[layer, rank]
    = sum physical_heat[layer, slots owned by rank]
```

最后再跨窗口相加：

```text
full_rank_heat = sum_window rank_heat_window
```

本模型有 256 个 Logical/Physical Expert：

- Prefill 每个服务是 EP16，所以每个 Rank 对应 16 个 Physical Expert Slot。
- Decode 是 EP32，所以每个 Rank 对应 8 个 Physical Expert Slot。

### 4.3 Prefill 的两个服务怎样合并

P0 和 P1 是两个独立的 EP16 服务，不是一个跨两机的 EP32 服务。

- Logical Expert 热度：`P = P0 + P1`。
- Physical Rank 热度：不能把 P0-r0 与 P1-r0 相加，因为它们是不同物理服务。
- 图和 CSV 中按以下顺序拼接：
  - 列 0..15：P0-r0..P0-r15
  - 列 16..31：P1-r0..P1-r15

### 4.4 计数的含义

这里统计的是 recorder 记录的 **expert-token assignments**，不是“去重后的 token 数”。

一个 token 会经过多层 Routed MoE，并且每层可能路由到多个 Expert，因此 assignment 总数
会远大于请求的输入或输出 token 数。这个数用于比较热度分布，不应直接当作吞吐量。

## 13. 最容易混淆的几点

1. `logical_count` 是 Logical Expert 计数，不能直接按 Expert ID 除以每卡 Expert 数得到 EPLB Rank。
2. 不能用最终物理布局解释 rebalance 之前的计数。
3. EPLB 自动 dump 会 reset recorder，所以只保存最终 PT 会漏掉前面的窗口。
4. Prefill 这次只有一个窗口不是漏数据，而是 recorder steps 没达到自动 rebalance 周期。
5. P0-r0 和 P1-r0 是两台独立服务上的 Rank，不能相加成同一个 Rank。
6. assignment 总数不是请求 token 数，也不是吞吐量。
7. 正式结论应读取本目录的新结果，不要使用旧的 final-window-only 分析目录。
