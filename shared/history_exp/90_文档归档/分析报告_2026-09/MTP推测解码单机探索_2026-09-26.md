> 本轮为晚上讨论前的探索，不是正式跑数。2026-09-26 18:10–19:57（北京时间）完成兼容性验证与 ON/OFF 对照；逐请求结果、逐次 `/metrics` 和启动日志均归档在 [`../mtp_preview25/results/20260926_181500/`](../mtp_preview25/results/20260926_181500/)；目录名是运行标识，实际 ON/OFF 重启时间以各自 `manifest.txt` 为准。

## 一、问题和实验口径

- **MTP**：GLM-5.2 配置 `num_nextn_predict_layers=1`，包含用于猜测后续 token 的预测层。SGLang 的 `NEXTN` 使用预测层提出若干 draft token，目标模型验证后接纳前缀，并输出下一 token。接受多少 draft 与实际速度需分别测量；不能只凭接受率推断吞吐。
- 本轮使用 `--speculative-algorithm NEXTN --speculative-draft-model-quantization unquant --speculative-num-steps 3 --speculative-eagle-topk 1 --speculative-num-draft-tokens 4`。其中最多提出 3 个 draft token，**`spec_accept_length` 包含一次验证产生的 bonus token**，而 **`spec_accept_rate` 仅统计接受的 draft / 提出的 draft**。精确定义取自本轮镜像 `/sgl-workspace/sglang/python/sglang/srt/managers/tokenizer_manager.py` 的 `add_spec_info_to_meta_info` 函数、`observability/metrics_collector.py`。若请求流 `meta_info` 含 `spec_verify_ct`、`spec_num_correct_drafts`、`spec_num_proposed_drafts` 和 `spec_correct_drafts_histogram`，可以计算请求加权的平均接受长度与接受率；`/metrics` 的两个值是瞬时 gauge，不能直接当全程均值。
- 一台 npu1-25，16×Ascend 910C，TP16/EP16/DP1，同一份 GLM-5.2 ModelSlim W8A8 权重 `/mnt/raid/user/data/models/glm-qq`；镜像 `sglang-glm52-pd:fe694986`，镜像 ID `sha256:30b20a3c29e8699be3323472deb3259d67ad6c53771824c2950a68902ac9251d`。与上一轮 Chunk 实验一样，挂载只改变加载超时阈值的源码补丁。MTP ON→OFF 依次在 25 单机运行，固定 chunk=8192、mem-fraction-static=0.88、max-running-requests=4、context=131072、DeepEP normal、greedy、`ignore_eos=True`。保留 23 上上一轮的 Chunk 服务，避免打断它。
- 25 上同名工作目录与当前机器**不实时共享**。启动脚本和补丁复制到 25 的 `/home/chengyetai/workspace/current_exp/`，日志同步回本地 `current_exp`；本轮无文件落在此目录之外的实验工作产物。

### 请求和指标

| 场景 | 输入 token | 输出 token | 前缀 / cache | 此轮关注 |
|---|---:|---:|---|---|
| Decode 探索 | 1024 | 2048 | 先 `/flush_cache`，随机 token | 接受长度、TPOT、输出吞吐。正式口径的 **1K/32K** 在脚本 `--plan full` 中提供，本轮以 2048 输出缩短探索时间 |
| Prefill+Decode | 8192 | 1024 | 先 `/flush_cache` | 8K/1K，TTFT 与输出吞吐 |
| 长上下文 | 32768 | 300 | 19661 token 共享前缀，先 flush 并预热，理论比率 60.0006% | 实测 `cached_tokens / prompt_tokens`，TTFT、TPOT |

每场景每模式 2 个串行测量请求，随机种子 20260926。开始请求至首个有输出 token 的流事件为 TTFT；首个事件至结束的时间除以 `(实际输出数 - 1)` 为 TPOT（按 token 归一的平均间隔，并非完整 ITL 分布）；每个请求的输出 token 数除以 wall time 为**含 Prefill 的单请求吞吐**。请求日志里保留每一事件的时间、输出 token、原始 `meta_info`，方便复核。关闭缓存后预热公共前缀的一次请求不计入测量结果。公共前缀 19661 token 仅是构造目标，最终使用服务端报告的命中量核对；流量很小，**绝不可把 2 个请求的 p95 当作稳定性能结论**。

## 三、观察结果

### 兼容性与容量检查

- 初次启动 `mem-fraction-static=0.85` 时，服务端计算 `max_total_num_tokens=22144`，小于 32768+300；保存原日志为 `on/server_085.log`。因此先只发一条 1024 输入/32 输出短请求，并将响应保存在 `on/initial_smoke_085.json`：TTFT 5.321 s、TPOT 136.086 ms（单次，仅用于确认功能）；8 次验证、24/24 个 draft 被接受，接受长度 4.0，接受直方图 `[0,0,0,8]`。这说明当前镜像的 `unquant` MTP 草稿层确实可以加载并产生请求级接受统计；**不能**将本条随机 ID 短响应的接受率 100% 外推到其他请求。
- 为涵盖 32K 长输入，ON/OFF 实验统一重启为 `mem-fraction-static=0.88`。新启动日志记录 MTP ON `max_total_num_tokens=43008`、OFF `63616`，ON 少 20608 个 KV token（约 32.4%）；本轮三种单请求均可容纳。两边主模型各 rank 加载约 47.97 GiB，ON 又加载约 1.72 GiB/rank 的 NextN 草稿模型，并增加推测验证所需的 KV/工作空间。

**结论：**这轮单请求贪心解码里，MTP 的主要收益出现在 Decode：三种工作负载的平均 TPOT 约缩短到 OFF 的 27%，按请求端到端时间计算的单请求输出吞吐提高约 3.3–3.6 倍。ON 的 TTFT 没有降低：1K/2048 的 ON 均值高 43%（6.077/1.124 秒对 OFF 3.960/1.068 秒），8K/1K 高 5.7%，32K/300 高 2.3%。只有每格两条且按 ON→OFF 顺序运行，首次冷态差异、设备状态与时间漂移未排除；不能把 TTFT 增量视作稳定效应。这里的输出吞吐是**单请求**输出/完整墙钟时间，并非多并发服务容量。

### 容量和端到端开销

与 OFF 相比，ON 在相同 `mem-fraction-static=0.88` 下少 20608 个可用 KV token：**43008 对 63616**。本轮三种请求能装入 ON 容量；多并发或完整的 1K/32K 长输出需要重新核查动态缓存使用、是否触发驱逐或 OOM。输出较短的 32K/300 场景 ON 的输出吞吐倍率 **3.30×** 小于长 Decode 的 **3.61×**，因为约 6–7 秒的 TTFT 在总耗时中占比较大；不能把 Decode 的 TPOT 倍率直接当作整请求吞吐倍率。

## 四、与正式实验的边界

1. 此轮使用随机 token ID 测架构与调度路径；真实业务文本的草稿接受分布可能不同。正式实验要固定代表性业务数据集，记录 prompt、温度、EOS 策略和并发到达率。
2. 2048 token 只是 1K/32K 的兼容性与趋势探索，不能推断 32K 连续输出的延迟与吞吐；正式轮要完整跑 32768 token，监视 KV、随上下文增长的 TPOT 和实际是否稳定完成。
3. 本轮每格串行 2 请求，没有测并发吞吐/大样本分位数；正式轮应加多并发和重复轮次，报告请求错误率、卡利用率、异步采样到达率和 P50/P95/P99。
4. 历史报告 `history_exp/glm52_ep64_chengyetai/fixed_tests/test1_evalscope_multiturn/result.md` 的旧 `W13='FLOAT', W2='FLOAT'` ModelSlim 启动错误，仅能说明那次量化路径失败。本次通过 `--speculative-draft-model-quantization unquant` 重新验证，不以旧记录代替当前结论。
