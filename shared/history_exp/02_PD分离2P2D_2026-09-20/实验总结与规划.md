# GLM-5.2 EP / EPLB 实验：总结与规划

> 本文是当前进度的**总纲**：先说清"我们到底做了什么、卡在哪、怎么解的"，
> 再给出一份可执行的**实验规划**。详细执行日志见 `FinalTest.md`，旧方案见
> `ep_exp2.md` / `datasets_run.md` / `固定测试转移方案.md` / `Pre_FinalTest.md`。

## 一、一句话结论

1. **乱码根因已经找到并解决**：是 `/mnt/raid/user/data/models/glm-q` 这份权重本身有问题，
   换成 `/mnt/raid/user/data/models/glm-qq`（正确的重拷贝）后，PD 分离输出完全正常。
2. 我们**不是零实验**，但要分两段看：
   - **统一服务模式**的 EP 实验（EP32/64 + EPLB）是做过、有数据产出的；
   - **固定测试（PD 分离）阶段**，到目前为止**一个正式实验都还没跑成**，时间全花在解决乱码/部署上。

## 二、我们到底做了什么（复盘）

### 2.1 有产出的部分

- **统一服务的 EP / EPLB 实验**：EP=64/EP=32、EPLB 开/关、补丁/NZ 组合，跑过 Dolly 混合
  数据集，采集了 expert 分布、TTFT/TPOT/e2e、AICore 占用等（产物在
  `glm52_ep64_chengyetai/dataset/ep_runs/`）。
- **数据集与压测工具**：三份数据集（dolly / dolly-zh / alpaca-en，共 11.8 万条）已备好，
  压测脚本 `dataset/bench_multi.py`、`dataset/run_multi.sh` 已就绪（详见 `datasets_run.md`）。
- **TTFT 残差分析**：定位了 e2e 里"queue + prefill + 中间时长 + decode"四段中，
  "中间时长"的来源是 tokenizer ↔ scheduler 的 IPC（见 `TTFT残差分析.md`）。

### 2.2 卡了很久的部分（现已解决）

固定测试里的**测试4（PD 分离）**，从搭 PD 部署开始就一直卡在"输出乱码"：

- 症状：`让我 //</ //</ ...`（token 66810 死循环），第一个 token 正常、第二个起退化。
- 中间排查并排除了一堆变量：镜像（v0.5.16 / v0.5.18 / main）、load-balance 方法、
  deepep mode、shared-expert fusion、NaN、MoE 后端、speculative（NEXTN）、DP 大小（4/16）……
  还误判过是"GLM-5.2 DSA indexer 在 PD 下的 SGLang bug"（对应上游 PR #30839/#32209）。
- **真正根因**：`glm-q` 权重是旧的/有问题的量化产物（`.msc` 头部坏字节、缺 `rot.weight` 等）；
  `glm-qq` 是正确重拷贝（含 msmodelslim 的 GLM-5.2 支持补丁 + 正确量化配置）。
- **验证结果**：换 `glm-qq` 后，PD + EP 输出完全正常（完整中文回答）。

### 2.3 已跑通的最小配置（服务现已停，下次从 §4.4 第①步重启验证）

- 模型：`MODEL=/mnt/raid/user/data/models/glm-qq`
- 镜像：`quay.io/ascend/sglang:main-cann9.0.0-a3`
- prefill（1 机）：`--tp-size 16 --dp-size 4`，无 EP，deepep normal，禁 graph，
  `SPEC=off`，去掉 `--moe-dense-tp 1`。
- decode（1 机）：`--tp-size 16 --ep-size 16 --dp-size 4`，deepep low_latency，graph 开，
  `SPEC=off`。
- load-balance：`round_robin`。

> 注意：上面的 `SPEC=off`、去掉 `moe-dense-tp` 是为了绕过 prefill 加载慢/卡住临时用的，
> 后续要按官方配置逐步回填验证（见 §4.4）。

## 四、实验规划

### 4.1 实验目标

量化**大 EP 下专家负载不均衡**，并测量**开启 EPLB 后的性能与 rebalance 开销**
（本轮不跑 EPLB 关闭对照组）。核心指标：

- Prefill token/s、TPOT、E2E 四段（queue + prefill + 中间时长 + decode）。
- EPLB 的 rebalance 开销（次数、每次耗时，日志千万别删）。
- Expert×Layer 热力图（总热度 + 4 个随机时刻 snapshot）。
- rank 负载（min/max/mean/CV、peak/mean、max/min）。

### 4.2 实验线（只看 PD 分离）

统一服务的 EP/EPLB 实验（`ep_exp2.md`）**已经做过了，不再继续**。后续只做
**PD 分离（固定测试4）**这一条线：

- 参考：4 节点 A3，GLM-5.1 W8A8，2 prefill + 2 decode，UCM 前缀缓存。
- 我们按 GLM-5.2 + 自己的 SGLang 部署复刻 workload，指标横向对比。

### 4.3 测试4 的完整方案（本阶段核心）

**部署形态**：2 机 prefill + 2 机 decode（2P2D），graph 必须开。

- prefill：2 机，每机 TP16 + DP4，无 EP（官方 `--moe-dense-tp 1`，待验证）。
- decode：2 机 32 卡，`TP=EP=32`（deepep 强制 EP=TP），DP 待定（先验证 32）。
- 场景：EP=32、EP=64 两档，**只跑 EPLB 开**。

**Workload（照官方测试4）**：

- 输入/输出长度：**只做 64K 输入 / 1024 输出**（128K 太长，不做）。
- TPOT 延迟上限：30ms。
- 前缀缓存命中率：90%（每请求约 90% 的输入 token 命中公共前缀，不是 90% 请求命中）。
- KV 缓存前缀多样性：取并发值的一半（并发 20 → 10 种前缀，模拟 Agent 多请求共享前缀）。
- 并发：10、20、30；**请求次数固定 = 并发 × 4**（与参考原文一致，不因数据长而减少）。

#### 数据集筛选规定（agentx / cc-traces）

数据源：`/mnt/raid/user/data/dataset/cc-traces-weka-062126-256k/traces.jsonl`
（393 个 trace、30141 个 top-level 请求）。字段：`in`/`out` 是 token 数，
`hash_ids` 是每 64 token 一块的内容 hash，`type` 区分 main（`s`/`n`）与 subagent。

实测分布（top-level main 请求）：

- 输入：全量偏长（mean≈129.5K、P50≈129.7K），但 **64K 档（`in ∈ [49152, 65536]`）约 2333 条**，够用。
- 输出：mean≈1067、P50≈434（天然接近 1024 输出）。
- 前缀复用：相邻 main 请求命中率 mean≈90.8%、P50≈98.8%，命中率 ≥85% 占 91%——
  **天然就是官方"90% 前缀缓存"场景，按 session 顺序回放即可，无需人造前缀**。

筛选规则（只筛一部分，不跑全部）：

1. 只用 top-level `type in ('s','n')` 的 main 请求。
2. 只筛 64K 档：`in ∈ [49152, 65536]`（128K 太长，不做）。
3. 输出对齐 1024：`out ∈ [512, 1024]`。
4. 前缀缓存与多样性：选 K 个 trace（K = 并发 / 2），每个 trace 取**连续 8 个 main 请求**
   （共 8K 个 = 并发 × 4），按时间顺序回放，靠 hash_ids 天然 ~90% 命中。
   注意：同一 trace 内输入长度随多轮累积而**递增**，所以分档定位按"连续段的**末端** in 落在档位"
   来选（找末端 ~64K 的段），不要求段内每个请求长度相同。
5. 并发 10/20/30 → 前缀多样性 5/10/15 → 请求 40/80/120。
6. 跑前记录实际 token 统计（in/out 的 total/mean/min/max/P50/P90/P99）+ 实际前缀命中率。

**每个实验必须产出**（对齐 `Pre_FinalTest.md` 要求）：

0. 数据集形式（来源、条数、实际 token 统计：prompt/completion 的 total/mean/P50/P90/P99）。
1. 运行时全部命令和参数。
2. EP=32/64 下的 Prefill token/s、TPOT token/s、E2E 四段。
3. EPLB 开时的 EPLB cost（`rebalance start/end` 日志，**保留**）。
4. Expert×Layer 热力图（总热度 + 4 个随机时刻 snapshot）。

### 4.4 下一步执行顺序

0. **任务0（最高优先）：profiling 坐实 `TTFT - queue - prefill` 残差**
   - 背景：`TTFT残差分析.md` 已把这段残差（约 18-20s，占 TTFT 34-46%）定位到
     "请求进 scheduler + 首 token 回传"，排除了 tokenize / IPC send（都毫秒级），
     但仍是"埋点反推"，**没有用 profiling 直接坐实**。
   - **先做小测试**：用最小服务 + 少量请求先跑一次 profiling 冒烟，确认能采到想要的
     profiling trace / 时间线（而不是等正式实验才发现采不到），再把它插进正式实验。
   - 要求：用 profiling（`torch_npu.profiler` / SGLang profile）在最小服务上实测，
     把这段残差拆成具体 kernel / 操作，逐项给出耗时；**不能含糊地叫"通信或其他等待"**，
     必须落到 profiling trace 里的具体项（哪个 kernel、哪个 IPC 环节、各占多少 ms）。
   - 产出：profiling trace + 时间线表（每段具体耗时与占比）。
1. **回填官方配置验证 glm-qq**（先做，成本低）：
   - 分别验证 prefill 能否恢复 `SPEC=on`、`--moe-dense-tp 1`；
   - 确认 glm-qq 在官方配置下也正常（而不是只有最小配置正常）。
2. **搭 2 机 decode（EP32/DP32）**：验证 glm-qq 在 2 机形态下正常 + 不再 OOM（每卡权重约减半）。
3. **搭完整 2P2D**（2 prefill + 2 decode）+ router。
4. **构造测试4 数据**：64K 输入 / 1024 输出 + 90% 前缀缓存 + 前缀多样性（并发一半）。
5. **先做小测试（冒烟）**：每档场景先用极少量请求（单请求或并发 1）跑通一遍，
   确认服务正常、请求能完成、四段时延 / 专家热度 / EPLB cost 都能采到，再进正式矩阵。
6. **跑正式实验**：按并发 10/20/30 × (EP32/64) × EPLB 开 出矩阵，逐个采集 §4.3 的数据。
   **每个实验限制约 30 分钟**（非硬上限，保证每条请求都跑完；请求次数固定 = 并发 × 4，
   不因数据长而砍请求）。
7. 每跑完一个立即做"产物齐全检查"，关键文件/指标缺一就停下，不盲目进下一个。
