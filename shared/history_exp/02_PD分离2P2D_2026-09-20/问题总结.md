# 问题总结（当前实验 all issues）

> 本文汇总 GLM-5.2 PD 分离实验到目前为止遇到的所有问题，按"已解决 / 未解决 / 根本约束"
> 分类，作为下次继续的起点。时间：2026-09-14。

## 一、已解决 ✅

### 1. 乱码（token 66810 `//</` 循环）—— 最大阻塞，已解决

- 现象：PD + EP 下输出 `//</ //</ ...`，第一个 token 正常、第二个起退化。
- 排查过程：排除镜像 / load-balance / deepep-mode / fusion / NaN / MoE 后端 / speculative / DP 大小，
  一度误判为 SGLang 的 DSA indexer bug。
- 真根因：`/mnt/raid/user/data/models/glm-q` 权重本身有问题（`.msc` 坏字节、缺 `rot.weight`）。
  换 `/mnt/raid/user/data/models/glm-qq`（正确重拷贝）后输出正常。
- 教训：先怀疑数据/权重，再怀疑框架；两份同大小权重要 checksum 对比，不能只看 config。

### 2. CUDA Graph "卡死" —— 实为误判

- 之前以为 graph capture 卡死，实际是配置错：ep_size 漏写（默认=1）、MEM 给太高、mfstore 没起、
  用了 `--cuda-graph-max-bs` 而非 `--cuda-graph-bs`。修好后 graph capture ~12 秒正常。

### 3. 单机 decode DP16 OOM

- 原因：`--enable-dp-attention` 下 DP16 会把注意力权重在每个 DP rank 复制一份，
  单机 16 卡权重顶到 ~99% 装不下。单机只能用 DP4。

### 4. 两个脚本配置 bug（已修）

- `ASCEND_MF_STORE_URL` 硬编码指向 23，prefill 换机器后要跟着改。
- decode 单机残留 `--dist-init-addr`（为 2 机加的），导致单机 HCCL 初始化去连别机卡死。
  已改为只有 `DECODE_NNODES>1` 才加 dist-init-addr。

## 二、未解决 ❌（阻塞实验）

### 1. 跨 2 机 decode（EP32）rank1 卡死 —— 核心阻塞

- 现象：31+32 跨 2 机 decode（TP32/EP32）时，rank0（31）`ready to roll`，rank1（32）卡死，
  16 个 rank CPU 忙等。
- py-spy 精确定位：rank1 卡在 `dp_attn.py` 的 `prepare_mlp_sync_batch_raw → all_gather_into_tensor`
  （DP attention 的 MLP sync 跨机 all_gather）。
- 这与上游 PR #32209「Fix PD decode hang with DP attention and GLM-5.2 MTP」的崩溃点
  `crash at dp_attn all_gather_into_tensor` 完全一致；我们的 main 镜像（0.5.19.dev684）还没包含该修复。
- 尝试过、都失败的 workaround：
  - DP32 / DP16 / DP1：都卡死。
  - `SGLANG_SCHEDULER_SKIP_ALL_GATHER=1`：跳过 all_gather 后报
    `DP CUDA graph replay requires raw per-rank request counts`（graph 依赖 gather 结果）；
    再关 graph 又报 `cumsum() got NoneType`（后续计算依赖 gather 结果）。
  - 关 `--enable-dp-attention`：报 `multi-node data parallel is not supported unless dp attention`。
  - 关 dp-attention + DP1：报 `AssertionError: capture_bs=[]`。
- 结论：跨 2 机 decode 的 DP-attention 同步是深层次 bug，需要上 PR #32209 补丁（改代码）。

### 2. 单机 prefill 装不下长输入（KV 余量太小）

- 现象：单机 prefill（TP16 DP4）权重占 ~86%（MEM=0.90 已接近上限），KV 余量只剩 ~400MB。
- 结果：16K 输入就 OOM（`NPU out of memory, 已分配 55.76 GiB`），prefill detokenizer 心跳停、
  服务变 unhealthy，router 返回 503。64K/128K 更不可能。
- 这正是 FinalTest.md 早有的结论：单机 EP16 对 64K/128K 基本不可行。

### 3. 死结（这两个问题互相锁死）

- 64K 输入 → 需要跨 2 机 EP32 → 但跨 2 机 decode 卡死（问题1）。
- 单机 EP16 → 能跑不卡死 → 但装不下 64K（问题2）。
- 所以：测试4 的 64K 输入，目前没有任何一条路能跑。

## 三、根本约束（记住这些，别重踩）

| 约束 | 数值 |
|---|---|
| 单机 EP16 权重占比 | ~86%（MEM 至少 0.86） |
| 单机 KV 余量 | ~400MB（装不下 9K+ 输入） |
| 跨 2 机 EP32 权重 | ~74%（能装下，但 rank1 卡死） |
| prefill 加载 glm-qq | ~8 分钟（load_weight≈491s，别误判成卡死） |
| decode 加载 glm-qq | ~1-2 分钟（2 机时偶发 10 分钟） |

## 四、下一步（按优先级）

1. 攻 PR #32209：跨 2 机 decode 的 dp_attn all_gather 卡死。这是跑 64K/EP32 的唯一出路。
   方案：拉含 #32209 的镜像，或手动把补丁 port 到当前镜像。
2. 若短期内攻不下 EP32：降低输入长度（比如 2K-4K）+ 单机 EP16，先把任务0（profiling 残差）
   和压测流程跑通、出数据（虽然输入不是 64K）。
3. 任务0 的 profiling 方案已就绪：挂 `glm52_ep64_chengyetai/patches/tokenizer_manager_instrumented.py`
   埋点 + `breakdown_ttft.py` 四段分解 + `torch_npu.profiler`。
4. 官方配置回填（SPEC=on、moe_dense_tp=1）还没验证。
5. 正式实验矩阵（并发 × EP × EPLB 开）还没跑。
