# 2 机退化实验方案（1P1D + EP16）

> 本文 = 原方案（`实验总结与规划.md`）的**退化配置版**：除"部署形态从 4 机 2P2D
> 退化为 2 机 1P1D、EP 从 32/64 退化为 16、decode DP 固定为 4"之外，其余
> 目标、指标、workload、数据集、产出清单、定时、检查流程**与原来完全一致**。

## 一、退化说明（相对原方案改了什么）

| 项 | 原方案 | 退化方案 |
|---|---|---|
| 机器数 | 4 机 | **2 机** |
| PD 形态 | 2 prefill + 2 decode | **1 prefill + 1 decode** |
| decode | 2 机 32 卡，TP=EP=32 | **1 机 16 卡，TP=EP=16，DP=4** |
| EP 档位 | EP32 / EP64 | **EP16（单档）** |

其余（模型 glm-qq、镜像 main、只跑 EPLB 开、64K/1024、90% 前缀缓存、
并发 10/20/30、请求数=并发×4、限时 30 分钟、四段分解、EPLB cost、热力图）
**全部不变**。

## 二、环境与最小配置（已验证）

- 硬件：**2 机**（npu1-31 + npu1-32）× 16 卡 Ascend 910C。
- 模型：`/mnt/raid/user/data/models/glm-qq`（**必须 glm-qq，不是 glm-q**）。
- 镜像：`quay.io/ascend/sglang:main-cann9.0.0-a3`。
- 拓扑：**31 = prefill**（16 卡）、**32 = decode**（16 卡）、router 放 31（可互换）。
- 操作方式：从 23 通过 SSH 远程操作 31 / 32（已确认连通 + sudo docker + glm-qq 权重齐全）。
- 已跑通配置：
  - prefill：`--tp-size 16 --dp-size 4`，无 EP，deepep normal，禁 graph，
    `SPEC=off`，去掉 `--moe-dense-tp 1`。
  - decode：`--tp-size 16 --ep-size 16 --dp-size 4`，deepep low_latency，graph 开，
    `SPEC=off`。
  - `load-balance-method round_robin`。
- 说明：`SPEC=off`、去掉 `moe-dense-tp` 是绕过 prefill 卡住的临时手段，后续要按官方配置
  回填验证（见 §四 第 1 步）。

## 三、实验目标与核心指标

量化 **EP16 下**专家负载不均衡，并测量**开启 EPLB 后的性能与 rebalance 开销**
（不跑 EPLB 关闭对照组）。核心指标：

- Prefill token/s、TPOT、E2E 四段（queue + prefill + 中间时长 + decode）。
- EPLB 的 rebalance 开销（次数、每次耗时，日志千万别删）。
- Expert×Layer 热力图（总热度 + 4 个随机时刻 snapshot）。
- rank 负载（min/max/mean/CV、peak/mean、max/min）。

## 四、下一步执行顺序

0. **任务0（最高优先）：profiling 分解 `TTFT - queue - prefill` 中间残差**
   - 背景：`TTFT残差分析.md` 已把这段残差（约 18-20s，占 TTFT 34-46%）定位到
     "请求进 scheduler + 首 token 回传"，但仍是"埋点反推"，没坐实。
   - **先做小测试**：最小服务 + 少量请求先跑一次 profiling 冒烟，确认能采到
     profiling trace / 时间线，再进正式。
   - 要求：用 profiling（`torch_npu.profiler` / SGLang profile）把中间段**逐项拆成
     具体 kernel / IPC 环节**（哪个 kernel、哪个 IPC、各占多少 ms + 占比），
     **不能含糊叫"通信或其他等待"**。
   - 产出：profiling trace + 时间线表。
1. **回填官方配置验证 glm-qq**：
   - 分别验证 prefill 能否恢复 `SPEC=on`、`--moe-dense-tp 1`。
2. **搭完整 1P1D**（1 prefill + 1 decode）+ router（decode EP16/DP4 已跑通）。
3. **构造/复用测试4 数据**：`dataset/test4_requests/requests.json`（已筛好），
   64K 输入 / 1024 输出 + 90% 前缀缓存 + 前缀多样性（并发一半）。
4. **先做小测试（冒烟）**：每档场景先用极少量请求（单请求或并发 1）跑通，
   确认四段时延 / 专家热度 / EPLB cost 都能采到，再进正式矩阵。
5. **跑正式实验**：并发 10/20/30 × **EP16** × EPLB 开 出矩阵，逐个采集。
   **每个实验限制约 30 分钟**（非硬上限，保证每条请求都跑完；请求次数固定 = 并发 × 4）。
6. 每跑完一个立即做"产物齐全检查"，关键文件/指标缺一就停下。

## 五、Workload（照官方测试4）

- 输入/输出：**64K / 1024**（128K 太长，不做）。
- TPOT 延迟上限：30ms（官方参考，我们实测报告）。
- 前缀缓存命中率：90%。
- KV 前缀多样性：并发的一半（并发 20 → 10 种前缀）。
- 并发 10/20/30，请求次数固定 = 并发 × 4。

## 六、数据集筛选（agentx / cc-traces）

数据源：`/mnt/raid/user/data/dataset/cc-traces-weka-062126-256k/traces.jsonl`
（393 trace / 30141 top-level 请求；字段 `in`/`out` 是 token 数，`hash_ids` 是每 64 token
一块的 hash，`type` 区分 main 与 subagent）。已筛好的结果在
`dataset/test4_requests/requests.json`。

- 输入 64K 档：`in ∈ [49152, 65536]`（约 2333 条，够用）。
- 输出对齐 1024：`out ∈ [512, 1024]`。
- 前缀复用：相邻 main 请求命中率 mean≈90.8%，天然 90% 前缀缓存。
- 前缀多样性 = 并发/2，选 K 个 trace 各取连续 8 个 main 请求（请求总数 = 并发 × 4）。
- 压测用随机 token + 90% 前缀构造（对齐官方 UCM），agentx 只用于背书参数。

## 七、每个实验必须产出（对齐 Pre_FinalTest.md）
