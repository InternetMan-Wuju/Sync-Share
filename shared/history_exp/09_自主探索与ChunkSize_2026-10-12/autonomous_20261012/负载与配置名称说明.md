# 报告里的测试场景和服务配置怎么读

**“测试场景”说的是给模型什么输入、要求它输出多长；“服务配置”说的是用哪套软件和参数运行模型。** `mtp-v16-auto-cap64-mem87-hccl650` 属于服务配置。同一套配置可以测试随机输入、真实聊天等多个场景。

报告正文、明细表和图使用中文名称；原始代号可在本页查找，也可通过每行的原始结果链接找到。长度单位均为 **token（模型处理文本的单位，不等于汉字数）**，1K＝1024，8K＝8192，32K＝32768。

## 你问的这个名字

`mtp-v16-auto-cap64-mem87-hccl650` 在报告中写作 **“旧镜像，双路分流、自动通信，静态显存87%方案”**。

| 片段 | 人话 | 实际参数或依据 |
|---|---|---|
| `mtp` | 开启多token预测加速：草稿先猜后续token，主模型检查后采纳 | 启动使用NEXTN，3步草稿；一轮最多输出3个草稿token加1个主模型token |
| `v16` | 使用标签为SGLang 0.5.16的旧软件镜像 | 是镜像标签，不是“第16次实验”；服务实际自报版本为`0.5.17.dev386+gc5bd3d7dc` |
| `auto` | DeepEP自动选择专家之间的通信模式 | `--deepep-mode auto`；不是“自动选择测试负载” |
| `cap64` | 每个通信进程的token分发容量设为64 | `SGLANG_DEEPEP_NUM_MAX_DISPATCH_TOKENS_PER_RANK=64`；不是客户端并发64，也不是输出64个token |
| `mem87` | 静态显存分配比例设为87%，主要供模型权重和KV缓存使用 | `--mem-fraction-static 0.87`；不是测到显存占用87%，也不是87GB |
| `hccl650` | 昇腾通信库HCCL的缓冲区配置为650 MB | `HCCL_BUFFSIZE=650`；不是带宽650，也不是超时650秒 |

这个名字没有写出的实际条件还有：数据并行2路、启用DP attention/LM head、服务同时运行请求上限8、开启小批次计算图（捕获批次1/2/4/8）。**数据并行2路**可理解为请求分成两路处理，不表示完整模型简单复制两份；**计算图**是把固定形状的计算流程预先记录，供后续重复执行。

解释依据：[保存的启动命令](logs/cyt-auto-mtp-v16-auto-cap64-mem87-hccl650/launch.sh)、[启动配置](logs/cyt-auto-mtp-v16-auto-cap64-mem87-hccl650/config.json)、[服务实际信息](logs/cyt-auto-mtp-v16-auto-cap64-mem87-hccl650/ready_server_info.json)。

## 四类标准测试场景

| 原代号 | 报告中的中文名称 | 实际在测什么 |
|---|---|---|
| `w1_8k_1k` / W1 | 输入8192 → 输出1024 | 较长输入、较短输出 |
| `w2_32k_1k` / W2 | 输入32768 → 输出1024 | 更长输入、较短输出，观察处理长输入的成本 |
| `w3_1k_32k` / W3 | 输入1024 → 目标输出32768 | 短输入、很长输出，主要观察持续生成的表现 |
| `w4_prefix32k_300` / W4 | 总输入32768 → 输出300，前缀缓存60% | 总输入中的约60%共享前缀已预热，可复用计算；不是额外再加60%的输入 |

四组标准压测使用随机输入。历史表中也有自写独立随机ID版本，输入生成方式要看该行来源；同样长度不保证是同一份输入。历史某些W3记录实际只要求输出2048，中文表会明确写出“实际目标输出2048”，不能当作32768输出已完成。

`C2` 表示客户端并发2，即最多同时有2个请求在途；`C4` 表示并发4。它们不同于请求总数，也不同于服务器某一时刻真正执行的批次大小。

`Chunk8192` 表示一次输入处理分块的大小设置为8192个token。比如`w1_8k_1k_chunk8192_c2_repeat2`会写成：**“W1：输入8192 → 输出1024；每块8192；并发2；第2轮复测”**。分块大小是设置值，实际批次可能更小；以服务信息和批次日志为准。

## 短诊断与真实聊天

| 原代号 | 人话 |
|---|---|
| `native_exact_1k256` | 原生随机ID直接发送，输入1024、强制输出256；短诊断 |
| `native_exact_eos_1k256` | 同类随机输入，最多输出256，允许模型提前结束 |
| `native_longinput_1k1024` | 从长输出场景取出的短诊断，输入1024、输出1024；不是完整W3 |
| `native_default_text_roundtrip_256` | 随机ID先转成文本、再重新分词，输出256；实际输入长度会变化 |
| `native_random_body_chatframed_256` | 给随机正文加上聊天角色模板，最多输出256，允许提前结束 |
| `framing_pair_raw_eos256` / `framing_pair_chat_eos256` | 同一份随机正文，比较直接续写与加聊天边界；两边输出上限都是256、都允许提前结束 |
| `sharegpt_chat_eos` | 真实聊天短窗口，最多输出256，允许提前结束；本次仍都碰到长度上限 |
| `sharegpt_chat_forced` | 真实聊天短窗口，强制输出256，忽略结束标记 |
| `sharegpt_chat_complete` | 真实聊天完整回复，上限2048、允许提前结束；本次两条问题均自然结束 |
| `sanity_chat` | 问候与算术功能检查，确认服务基本能回答 |
| `_business` 后缀 | 在同一服务配置下另测真实聊天，不代表换了模型 |

EOS是模型的结束标记。“允许提前结束”并不保证本次已经自然结束；要看实际结束原因。原生random-ids是随机起点的连续词表ID序列；自写独立随机ID则是独立抽取，两者不同，也都不等于真实聊天。

## 看表时常见的其他缩写

| 缩写 | 人话 |
|---|---|
| MTP ON / OFF | 多token预测加速开启 / 关闭 |
| AL | 每轮主模型验证平均产出多少个token，含主模型token；不是百分比或直接加速倍数 |
| P1 / P2 / P3 | 全部验证轮中，至少采纳1 / 2 / 3个草稿token的比例 |
| TTFT | 从发出请求到收到第一个token，等了多久 |
| TPOT | 首个token之后，平均每生成一个token花多久 |
| E2E | 从发出请求到整个回复结束，总共花多久 |
| tok/s | 每秒输出多少个token；本报告为整套服务总吞吐 |
| Prefill / Decode | 处理输入 / 逐步生成输出 |
| KV缓存 | 保存已经算过的上下文中间结果，减少重复计算 |
| TP16 / EP16 / DP1或DP2 | 张量并行16路 / 专家并行16路 / 数据并行1或2路；是运行布局，不是请求并发数 |
| MRR8或16 | 服务器同时运行请求的上限设为8或16；与客户端并发单列 |
| CTX131072 | 单请求上下文长度上限设为131072个token，实际还受KV缓存容量限制 |

名称改写只解释各条实验的含义。测量结果、完成状态、历史截断与配置偏离仍以对应报告及原始数据为准。
