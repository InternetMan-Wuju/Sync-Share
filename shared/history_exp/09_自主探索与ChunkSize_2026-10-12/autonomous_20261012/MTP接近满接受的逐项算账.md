# 一条真实高接受率请求的逐项算账

原始结果：[result.json](/home/chengyetai/workspace/current_exp/autonomous_20261012/results/mtp-v19-dp2-no-plan-lp-safe/native_longinput_1k1024/result.json)。下面是实际终态计数，不是模拟。

输入为SGLang原生random-ids的同一1024个ID。输出1024个token，实际文本开头为换行，之后反复“制表符 + #”。从输出位置1开始的1023token形成两token周期，占99.90%。这条请求没有EOS，不是忽略EOS后才进入循环。

| 项目 | 实际值 |
|---|---|
| 验证轮数V | 258 |
| 接受0/1/2/3个草稿的轮数 | [3, 0, 0, 255] |
| 总接受草稿token | 765 |
| 总提出草稿token | 774 |
| 最终输出token | 1024 |
| AL：输出/V | 3.968992 |
| P1/P2/P3 | 0.988372 / 0.988372 / 0.988372 |

意思是：绝大多数轮都把3个草稿全部接受，少数轮拒绝。终态直方图不能定位这3轮在原始时间线上发生在哪里。草稿不是在回答一个困难的新问题，而是在续写已经非常确定的重复模式。后续稳定循环的独立续写窗口可以全接受；这类长循环会稀释少量拒绝，接受率接近满值。

独立证据是：公开源恢复后的权重仍有此轨迹；另一成功配置的主模型prefill核对前128token完全一致，top1概率中位数约0.996；在保存轨迹位置32/128/512重新续写，输出仍相同且每个窗口AL=4。最新DP2 normal配置的同样三个后续窗口也都是AL=4，但其bulk-prefill前128有1处差异，不能说所有前向都完全一致。

当前能确定的是这条接近满接受的具体机制，以及原生随机正文容易触发这种轨迹。不能从单条请求证明全部输入都如此。完整真实对话已有自然结束、无周期而AL>3的例子；参考2.11缺少同条件输入和配置，不能作为所有请求的上限。
