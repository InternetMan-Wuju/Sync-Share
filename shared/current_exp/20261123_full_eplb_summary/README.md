# 大 EP MoE 专家负载均衡：人读总结

## 一句话回答

在大 EP 下，router 确实会产生少数热点专家；当热点仍然只能落在一个 rank 上时，单层完成时间由最忙的 rank 决定，所以只做专家位置重排不够。原生 EPLB 在没有复制时可能把“逐层热点对齐到同一个 rank”，在某些 EP64 服务上甚至比不开 EPLB 更差。我们最终走的是**全 EP 组共享 K 个真实备用槽、在 dispatch 前改道、同一轮 DeepEP 通信内计算并合并**的路线；当前已验证 K=1/2、layer49/50、EP16/EP32，在线 EPLB +32 也已在两机 EP32 上真实重排成功。

在 `d0b351d` 的当前条件下，**调好布局后的在线 EPLB +32 最快，原版其次；我方 K=2 的 TTFT 比原版慢约 4%～5%**。这是当前配置和样本范围内的结论，不是生产 p95。

## 发现了什么

- EP64 decode 的基线热力中，logical expert 的 CV 约 `3.59`、peak/mean 约 `58.6`；按 rank 聚合后仍约 `CV=0.846`、peak/mean `5.71`。
- EP64、256 个逻辑专家、每 rank 4 个槽、无冗余时，单层最热专家的物理下限约为该层 rank 平均负载的 6.9 倍。没有复制时，算法只能移动热点，不能消除它的单卡工作量。
- `07_PD共置与EPLB负优化` 的 EP64 服务实测中，rank 负载 max/mean 从约 `1.33×` 变为 `5.63～5.69×`，约 91% 的层热点落在 rank0；这说明“逐层独立装箱”可能把跨层抵消破坏掉。
- Prefill 和 Decode 不能混为一谈：Prefill 的 token 任务更大，复制/分流有较大的计算空间；Decode 的 batch1 任务很少，固定开销和通信更容易吃掉收益。早期 profile 中，Prefill 约 67% 时间在 DSA attention，Decode 的 MoE low-latency dispatch/combine 约占 15.5%。

## 试过什么，为什么改方向

1. **先做热度采集和原生 EPLB。** EP64/EP16/EP32 的窗口热力和 rank 热力图证明热点存在；但原生 EPLB 的逐层独立装箱会把热点对齐，且在 EP16/EP64 上遇到 NZ `storage_offset`、P2P 死锁、recorder OOM 等问题。修复后可完成重排，但服务收益仍不稳定，甚至出现 4%～7% 的吞吐负优化。
2. **再做复制和分流。** 64K chunk replay 在真实 routed-expert 子链上曾得到约 19% 的局部净收益，但 8K/16K/32K 往往不值得复制；两卡正式配对中冷复制大多为负收益，只有已驻留副本偶尔为正。这说明复制必须选对热点、批量和时机，不能只追求“多复制”。
3. **改为全组共享 K 槽。** 一个 EP 组只保留 K 个真实额外专家状态，槽跨层复用，不再要求每 rank 一份；K=1/2 已用真实 GLM expert、W8A8 和 NPU 验证。早期 K1 服务受 `(256+R) % EP == 0` 的均匀布局限制，后来用独立通信编号和外部槽解耦。
4. **从本地回填走到单次 DeepEP 改道。** 失败路径曾在额外 replica dispatcher 的 combine 报 `Invalid attr=601`，32K 连续请求也因 rank 槽复用分支不一致挂起。`bd80f52` 改为同一轮 DeepEP dispatch/combine，修复 owner 状态全组一致决定和 BF16 combine 输出；K=2 的 32K 隔离/连续请求和 EP16/EP32 功能矩阵通过。

## 当前方案

- `K` 是整个 EP 组跨层共享的真实备用槽总数，由配置指定，不是每 rank 一份；K 不要求是 EP 数量的倍数。
- 在 layer49/50，选中的热点 top-k 任务在 dispatch 前改写通信目的地；原专家保留剩余任务，owner 的外部槽接手副本任务。
- 主专家和副本使用同一次 DeepEP dispatch/combine；`topk_weights` 和逻辑专家不变。
- owner 上报真实 `(owner, local_slot)`、layer、expert、generation、ready 和 storage pointer，全组在收发前一致决定 reuse/install。
- 已验证：EP16 K=1/2、EP32 K=2；layer49/50；两机 32 die 单 EP32。EP32 K=2 的跨节点权重源为 rank20/rank16，槽 storage 可跨层复用。
- 仍未完成：K 的动态落点调整、完整 75 层 K 服务、真实 Decode K 服务、生产 graph 封装和更大 K/更多拓扑。

## 当前三组性能

主性能表来自 `d0b351d`：原版和 K=2 引用 `bf94982`，EPLB +32 为 1000 迭代重测。每组每档 n=10，表内为 TTFT 中位数，括号内为整次请求耗时中位数。

| 输入 | 原版（bf94982） | 在线 EPLB +32（d0b351d） | 我方 K=2（bf94982） |
|---|---:|---:|---:|
| 8K | 2.8025 s（3.3236 s） | **2.5969 s（3.1665 s）** | 2.9358 s（3.4774 s） |
| 16K | 5.7147 s（6.2401 s） | **5.3072 s（5.8814 s）** | 5.9785 s（6.4972 s） |
| 32K | 11.7875 s（12.3165 s） | **11.2183 s（11.7814 s）** | 12.3013 s（12.8586 s） |

`d0b351d` 的 EPLB +32 相对原版 TTFT 为 **-7.34% / -7.09% / -4.85%**；K=2 相对原版 TTFT 为约 **+4.72% / +4.53% / +4.42%**。原版和 K=2 来自上一批运行，不是本轮重新启动，不能忽略这个跨批边界。

## 最重要的限制

- 所有 AgentX 输入只有块哈希/长度，使用确定性 token 物化；不是原始人类文本或原始模型 token ID。
- K=2 的 8K output IDs 与原版不同；16K/32K 输出 ID 一致。K=2 的 8K 只能按数值容差和任务守恒解释，不能称 token-exact。
- `bf94982` 的 EPLB 每 2 个调度迭代重排，长请求经常跨重排；不能拿它和 `d0b351d` 的 1000 迭代结果混为同一稳态性能。
- `d0b351d` 的 EPLB 正式样本没有重排重叠，因为重排已在独立校准流量中完成；校准每轮 496 条 64-token 请求，单轮重排约 24.4～24.7 s。重排成本没有摊入正式中位数。
- 目前 K 的功能验证主要是 layer49/50 和固定 owner；不是完整模型所有层、真实 Decode、动态槽位置或生产 p95。
