# 大 EP MoE 专家负载均衡调研小结

我们最初要解决的问题是：大 EP 下少数专家过热，承担这些专家的 rank 会变慢，而一层要等所有 rank 完成，所以整层被最忙的卡拖住。

历史数据里，EP64 decode 的专家负载很不均，按 rank 聚合后 max/mean 仍有约 5.71；没有冗余时，单层最热专家只能放在一个 rank 上，单靠重排消不掉这部分计算。更麻烦的是，原生 EPLB 的逐层独立装箱曾把热点对齐到同一个 rank，EP64 实测 rank max/mean 从约 1.33 变成 5.63～5.69，吞吐反而下降 4%～7%。这个结果让我们转向复制和分流。

中间试过原生 EPLB、冗余专家和按当前路由复制。局部回放里，大 chunk 的复制有时能回本，但 8K/16K/32K 的冷复制大多不划算；两卡完整子链实验里也没有找到稳定回本点。于是方案改成全 EP 组共享 K 个真实备用槽：K 由配置决定，不是每 rank 一份，槽可以跨层复用。

现在的工作路径是：热点任务在 dispatch 前改写通信目标，主专家和副本使用同一次 DeepEP dispatch/combine。原专家实际少算，副本从 owner 的外部槽计算，结果按原 token 和 top-k 位置合并。已验证 EP16 K=1/2、EP32 K=2、layer49/50；32K 连续请求也已跑通。

当前三组表来自 `d0b351d`，原版和 K=2 引用 `bf94982`。每组每档 n=10，表中为 TTFT 中位数，括号内为整次请求耗时中位数。

| 输入 | 原版 | 在线 EPLB +32 | K=2 |
|---|---:|---:|---:|
| 8K | 2.8025 s（3.3236 s） | **2.5969 s（3.1665 s）** | 2.9358 s（3.4774 s） |
| 16K | 5.7147 s（6.2401 s） | **5.3072 s（5.8814 s）** | 5.9785 s（6.4972 s） |
| 32K | 11.7875 s（12.3165 s） | **11.2183 s（11.7814 s）** | 12.3013 s（12.8586 s） |

这次条件下，调好布局后的 EPLB +32 最快，原版其次，K=2 的 TTFT 比原版慢约 4%～5%。

几个边界仍需保留：AgentX 输入是块哈希派生的确定性 token，不是原文；K=2 的 8K 输出与原版不同，16K/32K 一致；EPLB 的 1000 迭代重排在正式计时前完成，重排成本未计入表中；K 目前只验证了 layer49/50 和固定 owner。
