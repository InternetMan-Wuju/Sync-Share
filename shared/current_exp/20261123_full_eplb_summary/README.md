# 大 EP MoE 专家负载均衡调研小结

我们最初要解决的是一个很具体的问题：大 EP 下，某些 MoE 专家明显更热，落在它们身上的 rank 就会比其他 rank 慢。一个层要等所有 rank 完成，所以即使平均负载看起来正常，只要有一张卡被热点拖住，整层还是要等它。我们沿着这条线试过原生 EPLB、专家复制和分流，最后走到全 EP 组共享 K 个真实备用槽的方案。

## 问题并不是“平均一下”这么简单

EP64 decode 的热力数据里，逻辑专家负载的 CV 约 3.59，max/mean 约 58.6；按 rank 聚合后仍不均衡，CV 约 0.846、max/mean 约 5.71。没有冗余时，一个最热专家只能放在一个 rank 上；在当时的 EP64 布局里，单层最热专家理论上就可能让最忙 rank 承担约 6.9 倍于平均的任务。只调整专家位置能换一张卡继续忙，不能把这个单卡工作量消掉。

这也解释了后来一个反直觉的结果：原生 EPLB 打开了，服务反而更慢。EP64 的 PD 共置实验里，rank 负载 max/mean 从约 1.33 变成 5.63～5.69，约 91% 的非空层热点都落到 rank0；吞吐下降约 4%～7%。原因是原生算法逐层独立装箱，每层都把最热专家放到当前最轻的 rank，但每一层重新开始，最后反而把热点对齐到了同一列。这个负结果让我们不再把“开 EPLB”当成目标，开始寻找复制和分流。

Prefill 和 Decode 也有明显差别。Prefill 的 chunk 大，热点专家能积累很多 token 任务，复制后的计算收益有机会覆盖一部分开销；Decode 的 batch1 任务很少，固定 kernel 启动和通信成本占比高，收益窗口窄得多。早期 profile 中，Prefill 约 67% 的时间在 DSA attention，Decode 的 MoE low-latency dispatch/combine 约占 15.5%，这也说明不能拿 MoE 子链的收益直接代替整层或整请求结论。

## 我们一路试过什么

最早是热力采集和原生 EPLB。EP64/EP16/EP32 的窗口数据都确认了热点存在，但当时也踩到了两个 NPU 问题：EPLB 直接发送 FRACTAL_NZ 专家切片时报 `storage_offset must be 0`；改成 ND 后又遇到 P2P 收发死锁，`rebalance start` 有日志但迟迟没有 `rebalance end`。后来用专家状态转 ND/收完转回 NZ，以及原子 `batch_isend_irecv` 补丁解决了这两个问题。EP16 的冗余组还出现过 recorder 和临时转换显存不足，说明重排本身也要算资源成本。

接着试复制和分流。2026-11-09 的 64K chunk replay 在真实 routed-expert 子链上得到过约 19% 的局部净收益，但 8K/16K/32K 往往不值得复制；后来的两卡完整子链实验里，`n={512,4096,8192}` 和多种配额下，冷复制都没有形成稳定正收益，已有副本也只有少数组为正。这段经历说明：复制并非“越多越好”，必须先把热点、批量、复制等待和返回成本算清楚。

再往后，我们把“每 rank 一个槽”的 EPLB 思路改成全组共享 K 槽。一个 EP 组只保留 K 份真实额外专家状态，槽可以跨层复用，因此 K 不必是 EP 数，也不需要每个 rank 都留一块备用权重。2026-11-16 的 `GlobalSlotPool` 先用小尺寸 W8A8 和两卡实验证明了槽生命周期、跨层复用和外部槽计算；2026-11-22/23 又逐步补上真实 GLM 专家、owner 状态校验、失败回收和统一 adapter。

最后一关是让副本真正进入服务分发。早期“另开副本 dispatcher”和本地回填方案在 combine 处报过 `Invalid attr=601`，这时副本虽然算出来了，但没有和主专家在同一次 DeepEP 通信里合并。`bd80f52` 改成同一轮 dispatch/combine：dispatch 前改写热点任务的通信目标，主专家留在原路径，owner 从真实外部槽计算副本，最后走原 combine。这个版本还修复了 32K 连续请求的 rank 槽复用分支不一致问题；现在已跑通 EP16 K=1/2、EP32 K=2、layer49/50 和两机 32 die 的完整服务请求。

## 现在的方案

当前配置里，K 是整个 EP 组所有层共享的真实备用槽总数，由配置指定，不是每 rank 一份。以 EP32 K=2 为例，owner 是 rank0/rank1，各持有一个 `37,810,176 bytes` 的真实槽；其他 rank 不分配一份同样的权重。槽跨 layer49/50 复用时，storage pointer 不变，generation 递增。

任务处理过程是：

```text
真实 router/top-k（逻辑专家和权重不变）
→ 选出热点任务及配额
→ dispatch 前把任务目标改成 owner 的额外通信编号
→ 一次 DeepEP dispatch
主专家走原模型权重，副本走 owner 的外部槽
→ 同一次 DeepEP combine
→ 按原 token 和 top-k 位置合并
```

所以原专家是真的少算了，副本也是真的接过了任务，不是把主路径权重置零后再本地补回来。EP32 K=2 的任务账本里，32K 首个 chunk 的 expert163 有 383 个逻辑任务，其中 181 个交给 owner0，原专家实际算 202 个；expert133 有 6 个任务，2 个交给 owner1，原专家实际算 4 个。

## 需要记住的限制

- AgentX 源只有长度和 64-token 块哈希，当前输入是确定性 token 物化，不是原始人类文本或原始 token ID。
- K=2 的 8K output IDs 与原版不同；16K/32K 输出 ID 一致。8K 只能按数值容差和任务守恒解释，不能叫 token-exact。
- `bf94982` 的 EPLB 每 2 个调度迭代重排，长请求经常跨重排；它只适合作为重排频率过高的历史对照，不能和 1000 迭代结果混在一起。
- `d0b351d` 的正式 EPLB 样本没有重排重叠，因为重排在独立校准流量中已经完成。每轮 496 条 64-token 校准请求，单轮重排约 24.4～24.7 s；这些成本没有摊进正式中位数。
- K 功能目前主要验证了 layer49/50、固定 owner 和单请求，不等于完整 75 层服务、真实 Decode K 或生产 p95。
