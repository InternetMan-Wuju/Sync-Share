**一句话结论：本轮范围内均未回本；`n={512,4096,8192}`、`q={n/4,n/2,3n/4}` 的 9 个正式点中，临时复制没有任何 12/12 正收益组，已有副本最多只有 5/12 正收益组，未达到稳定回本确认门槛。**

## 1. 这一轮改了什么

相对上一轮：

1. 原路径不再构造 q 拆分和外部槽，直接对 n 个任务执行完整源卡专家链。
2. 诊断计时与正式计时共用同一功能操作，但诊断模式在阶段边界强制同步；正式模式只在通信完成、权重 ready、结果回填、槽安全归还等依赖处等待。
3. 正式模式允许源卡计算与权重/activation 异步发送重叠。
4. 临时复制包含真实 NZ→ND 转换、打包、跨卡传输、目标槽接收和 ready。
5. 已有副本在计时外安装并记录安装成本，单次使用结束后按相同边界归还。
6. 修正 CPU 搜索候选、零收益复制、等价状态去重和槽释放竞争保护。

因此，新数字不能全部归因于“去掉同步”：原路径清理和异步重叠也改变了执行节奏。

## 2. 容量扫描：单专家任务数增长曲线

使用真实权重上的合成任务批次。n 是 expert43 收到的 token 任务数，不是请求输入长度。

每个形状每张卡 3 次预热、12 次固定正式记录，全部样本在 `COMPUTE_CURVES.csv`。

| n | 源卡 bank 中位数 | 目标卡外部槽中位数 |
|---:|---:|---:|
| 512 | 0.3579 ms | 0.3632 ms |
| 1024 | 0.4562 ms | 0.4382 ms |
| 2048 | 0.6322 ms | 0.6202 ms |
| 4096 | 1.1264 ms | 1.1331 ms |
| 8192 | 2.0949 ms | 2.1055 ms |

两张卡的链时间接近。小规模主要受算子启动成本支配，512 到 1024 并没有近似翻倍；大规模才明显随任务数增长。

中间规模按文档固定规则选择：

```text
G(n, n/2) = source_full(n) - max(source(n/2), target(n/2))
```

| n | source full | max(source half, target half) | 乐观半分节省 G |
|---:|---:|---:|---:|
| 1024 | 0.4562 ms | 0.3632 ms | 0.0930 ms |
| 2048 | 0.6322 ms | 0.4562 ms | 0.1760 ms |
| 4096 | 1.1264 ms | 0.6322 ms | **0.4942 ms** |

因此固定选择：

```text
n = 512, 4096, 8192
q = n/4, n/2, 3n/4
```

以上 G 只是目标卡空闲、计算重叠的乐观参考，没有扣复制、分发、返回和同步成本。

### 自然 Prefill 频率参考

复用了旧 NPU 路由聚合，不重跑服务：

- layer49 expert43：calibration 4 个 Prefill step 共 `4062` 个任务；
- holdout 4 个 Prefill step 共 `4066` 个任务；
- 平均约 `1015.5`、`1016.5` 任务/step；
- 原始逐 step 和原始 dump 已不在现存路径，因此不能给出逐 step 最小/最大值。

这说明本轮 512/1024/4096 量级有实际路由背景；8192 是高于该窗口平均 step 的高负载压力点。

## 3. 诊断计时与正式计时对照

诊断只采少量样本：n=6 和 n=512，q=n/2，每个点 3 个样本。正式值取同一负载正式配对中位数；n=6 使用已保留的正式 smoke 运行。

| n/q | 模式 | 诊断统一时间 | 正式统一时间 | 正式相对诊断 |

| 6/3 | cold | 2.6899 ms | 1.7388 ms | -35.4% |

诊断阶段中位数见 `DIAGNOSTIC_TIMELINE.json`。诊断阶段不能相加后当作正式总时间。

短时间线验证了两卡计算区间确实可以重叠：

| n/q | 源卡工作区间 | 目标卡计算区间 | 重叠区间 |

源卡区间包含异步 activation send 的在途完成等待，因此它不是纯算子时间；它用于证明两卡工作可以重叠，不进入正式收益计算。

## 6. CPU 小修正

新增回归见 `tests/test_expert_search.py`、`tests/test_slot_identity.py` 和 `artifacts/cpu_expert_search_oracle.json`。

### 6.1 分流候选

- legacy 候选 `{1,n/2,n}` 保留为对照；
- 新有限候选加入源/目标预计完成时间交点及相邻整数；
- `[12,4]` 现在选择 `q=4`，评分 `12.25 -> 10.50`；
- legacy 在同一案例仍返回不动；
- 新有限候选没有候选遗漏；beam=1 仍有 1 个剪枝遗漏案例，已如实保留。

### 6.2 零收益

`[4,0]`、复制费 2、`active_expert_cost=0` 的平局案例：

- 不动：4.0；
- q=2 分流加复制费：4.0；
- 搜索与 oracle 都选择不动，不因计算最大值下降而选择零净收益复制。

### 6.3 去重

搜索按 `(counts, slot identity/counts, copies, layer, active cost)` 去重。验证 11 个案例、0 个非法状态；每案例搜索时间和去重数量单独输出，不混成一个生产 p95。

### 6.4 槽释放竞争

槽释放改为：

1. 先进入 `RELEASING`，拒绝新 `use` 和 `acquire`；
2. 等待其他线程已有 use 退出；
3. 执行设备同步；
4. 最后转为 FREE。

同步失败时槽保持 `RELEASING`，不会被下一代租约复用。CPU 交错测试覆盖：

- 同步期间新 use/acquire 被拒；
- 其他线程 use 未退出时 release 等待；
- 同线程 use 中 release 立即拒绝，避免自锁；
- release 同步失败后安全重试。

12 个槽身份/生命周期测试全部通过。

## 7. 有限确认规则

文档要求某模式在某一 `(n,q)` 达到 `12/12` 正收益，才允许用新进程和新输入种子复测。本轮：

- cold：0 个合格点；
- existing：0 个合格点；
- 因此没有启动确认复测；
- 不把 5/12 或 9/12 正收益点写成回本候选。

## 11. 下一步判断

本轮数据说明：

- 512 任务规模的分流基本没有可覆盖通信的计算节省；
- 4096/8192 任务确实出现更大的计算节省，但当前串行依赖、activation 返回、回填和控制成本仍把已有副本压成接近持平或负收益；
- 临时复制还额外承担约 37.8 MB 权重传输，离回本更远。

若后续继续，应另开一轮先拆解已有副本在 8192/2048 的 activation send/recv、结果返回、回填和控制固定成本，并验证真实跨请求自然复用；不能把本轮接近持平写成已回本。
